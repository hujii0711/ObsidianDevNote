설계 단계는 기획에서 정의한 "무엇을, 왜"를 받아서 "**어떻게**"로 번역하는 단계입니다. 기획이 _문제 정의_라면 설계는 _해결 방법의 청사진_입니다.

특히 Claude Code로 개발할 거라면, 설계 산출물의 품질이 코드 품질을 거의 결정합니다. AI는 명확한 설계가 있을 때 가장 잘 작동하고, 설계가 모호하면 매번 다른 결정을 내려 일관성이 깨집니다.

## 설계 단계의 구체적 작업

### 1. 아키텍처 설계 (System Architecture)

가장 큰 그림부터 그립니다. "이 시스템은 어떤 조각들로 이루어져 있고, 어떻게 상호작용하는가."

- **아키텍처 스타일 결정**: 모놀리식 / 마이크로서비스 / 서버리스 / 클라이언트-서버 / 정적 사이트 등
- **주요 컴포넌트 식별**: 프론트엔드, 백엔드, DB, 캐시, 메시지 큐, 외부 서비스 등
- **컴포넌트 간 통신 방식**: REST / GraphQL / WebSocket / gRPC / 이벤트 기반
- **배포 환경**: 클라우드(AWS/GCP/Azure), VPS, 컨테이너(Docker/K8s), 서버리스

산출물: **시스템 아키텍처 다이어그램** (박스와 화살표로 충분합니다. excalidraw, draw.io, mermaid 등)

규모가 작다면 "Next.js + Supabase + Vercel" 같은 한 줄짜리 결정도 아키텍처입니다. 과하게 그릴 필요 없습니다.

### 2. 기술 스택 결정 (Tech Stack)

각 컴포넌트에 어떤 기술을 쓸지 정합니다.

- **언어 & 프레임워크**: 프론트(React/Vue/Svelte), 백(Node/Python/Go), 모바일(React Native/Flutter/네이티브)
- **데이터베이스**: 관계형(PostgreSQL/MySQL) / 문서형(MongoDB) / KV(Redis) / 시계열 등
- **인증**: 자체 구현 / Auth0 / Clerk / Supabase Auth
- **결제**: Stripe / Toss / PortOne 등
- **호스팅 & CI/CD**: Vercel / Netlify / Railway / AWS / GitHub Actions
- **모니터링**: Sentry / Datadog / PostHog

**중요**: 각 선택에 대한 **근거를 짧게라도 기록**하세요. "왜 PostgreSQL인가? → 관계형 데이터 + JSONB 지원 + 팀 친숙도." 이 결정 로그가 나중에 Claude가 코드를 재해석하다 엉뚱한 마이그레이션을 제안하는 걸 막아줍니다.

### 3. 데이터 모델 설계 (Data Model)

거의 모든 앱은 데이터를 다룹니다. 이걸 먼저 정리하면 API와 UI 설계가 훨씬 쉬워집니다.

- **엔티티 식별**: User, Post, Comment, Order 등 핵심 객체
- **속성(필드) 정의**: 각 엔티티가 가진 데이터
- **관계(Relationship)**: 1:1, 1:N, N:M 관계 표시
- **제약 조건**: Unique, NotNull, 외래 키, 인덱스
- **상태 머신**: 상태 필드가 있다면 가능한 상태와 전이를 정의 (예: 주문 → pending → paid → shipped → delivered)

산출물: **ERD(Entity Relationship Diagram)** 또는 **스키마 정의 파일**

```
User (id, email, name, created_at)
  └─ has many → Post (id, user_id, title, content, status, created_at)
       └─ has many → Comment (id, post_id, user_id, content, created_at)
```

데이터 모델은 한번 잘못 잡으면 바꾸기가 매우 어렵습니다. 시간을 가장 많이 써야 할 부분입니다.

### 4. API 설계 (API Contract)

프론트와 백, 또는 클라이언트와 서버 사이의 약속을 정합니다.

- **엔드포인트 목록**: `GET /api/posts`, `POST /api/posts/:id/comments` 등
- **요청 형식**: 헤더, 파라미터, 바디 스키마
- **응답 형식**: 성공/실패 케이스 모두
- **상태 코드 규칙**: 200/201/400/401/403/404/500 사용 기준
- **인증/인가 방식**: JWT, 세션, API 키
- **버전 관리**: `/api/v1/` 같은 버저닝 전략
- **에러 응답 표준**: 모든 에러가 같은 구조를 갖도록

산출물: **OpenAPI(Swagger) 스펙** 또는 간단한 API 문서. GraphQL이면 스키마 파일.

Claude Code 관점에서 API 스펙은 황금입니다. 스펙을 주면 그대로 구현하므로, 손으로 짜는 것보다 훨씬 정확합니다.

### 5. UI/UX 설계 (Interface Design)

- **정보 구조(IA)**: 화면 계층, 메뉴 구조
- **사용자 흐름(User Flow)**: 핵심 작업의 단계별 화면 이동
- **와이어프레임**: 저충실도 화면 구성 (Figma, Excalidraw, 손그림 모두 OK)
- **디자인 시스템**: 색상 팔레트, 폰트, 간격 규칙, 컴포넌트 라이브러리(shadcn/ui, MUI 등)
- **반응형 전략**: 모바일/태블릿/데스크톱 대응
- **접근성(a11y)**: 키보드 네비게이션, 스크린 리더, 명도 대비

산출물: **와이어프레임 + 디자인 시스템 문서**

완성도 높은 디자인 시안까지는 필요 없을 수도 있습니다. 와이어프레임 수준에서 "어떤 화면이 있고, 어떤 정보가 어디 놓이는가"만 정해도 충분합니다.

### 6. 폴더 구조 & 코드 컨벤션 (Project Structure)

이게 Claude Code 환경에서 **결정적으로 중요**한 부분입니다.

- **디렉토리 구조**: 기능별(feature-based) vs 레이어별(layer-based)
- **파일 명명 규칙**: kebab-case / camelCase / PascalCase
- **모듈 경계**: 도메인별로 어떻게 나눌지
- **공통 코드 위치**: utils, lib, shared 등
- **테스트 파일 위치**: 옆에 둘지(`Component.test.tsx`), `__tests__` 폴더에 둘지

산출물: **빈 프로젝트의 폴더 구조 예시** + **컨벤션 문서**

```
src/
  features/
    auth/
      components/
      hooks/
      api/
      types.ts
    posts/
      ...
  shared/
    components/
    lib/
    types/
  app/
```

### 7. 핵심 로직 / 알고리즘 설계

복잡한 비즈니스 로직이 있다면, 코드를 짜기 전에 **의사 코드(pseudo-code)나 순서도**로 정리합니다.

- 결제 흐름, 권한 체크 로직, 추천 알고리즘, 가격 계산 등
- 엣지 케이스를 미리 나열
- 동시성 이슈가 있는 부분은 락/트랜잭션 전략

이 단계를 건너뛰면 Claude가 "그럴듯하지만 틀린" 로직을 자신 있게 구현하는 경우가 많습니다.

### 8. 외부 의존성 & 통합 (External Integrations)

- 사용할 외부 API 목록 (결제, 지도, 이메일, SMS, OAuth 등)
- 각 API의 인증 방식, 요금제, 사용량 한도
- 실패 시 대응 전략 (재시도, 폴백, 회로 차단기)
- 키/시크릿 관리 방식 (.env, AWS Secrets Manager, Vault)

### 9. 보안 설계 (Security)

- **인증/인가**: 누가 무엇을 할 수 있는가
- **데이터 보호**: 암호화(저장 시/전송 시), 비밀번호 해싱
- **입력 검증**: SQL 인젝션, XSS, CSRF 방어
- **시크릿 관리**: 환경 변수, 비밀 키 노출 방지
- **개인정보**: 어떤 데이터를 수집하고, 어떻게 보관/삭제하는가
- **레이트 리미팅**: 남용 방지

보안은 나중에 끼워 넣기 매우 어렵습니다. 설계 단계에서 큰 그림을 잡아두는 게 좋습니다.

### 10. 성능 & 확장성 (Performance & Scalability)

- **예상 트래픽**: DAU, RPS 추정치
- **병목 예상 지점**: DB 쿼리, 외부 API 호출, 큰 페이로드
- **캐싱 전략**: CDN, Redis, 브라우저 캐시, React Query 등
- **DB 인덱스 계획**: 자주 조회되는 컬럼
- **확장 전략**: 수직(스펙업) vs 수평(서버 추가) 확장

초기 단계에선 "예상 트래픽이 적으므로 단순 구성으로 시작, N에 도달하면 X를 도입"처럼 **단계별 계획**으로 충분합니다. 조기 최적화는 피해야 합니다.

### 11. 에러 처리 & 로깅 전략

- **에러 분류**: 사용자 에러 / 시스템 에러 / 외부 의존성 에러
- **사용자에게 보여줄 메시지 규칙**
- **로그 레벨**: debug / info / warn / error
- **로그에 남길 것 / 남기면 안 되는 것** (개인정보, 비밀번호, 토큰 절대 금지)
- **에러 추적 도구**: Sentry 등

### 12. 테스트 전략 (Test Strategy)

테스트는 다음 단계 일이지만, "어떻게 테스트할 것인가"는 설계에서 정해야 합니다.

- **테스트 피라미드**: 단위/통합/E2E의 비율
- **각 레이어에서 무엇을 테스트할지**
- **테스트 도구**: Jest/Vitest, Playwright/Cypress 등
- **CI에서 어떤 테스트를 돌릴지**

### 13. 배포 & 운영 설계

- **환경 구분**: dev / staging / production
- **배포 방식**: 자동 배포 트리거, 롤백 전략
- **환경 변수 관리**
- **데이터베이스 마이그레이션 전략**
- **모니터링 & 알림 채널**

## Claude Code 관점의 특별 강조

설계 단계 산출물은 결국 **AI에게 줄 컨텍스트**입니다. 다음을 권장합니다:

1. **`docs/` 폴더에 설계 문서를 모두 넣기**: `architecture.md`, `data-model.md`, `api-spec.md`, `conventions.md` 등
    
2. **`CLAUDE.md` 또는 `AGENTS.md` 작성**: 프로젝트 루트에 Claude Code가 항상 참조할 핵심 규칙을 요약. 예:
    
    - 사용 기술 스택
    - 폴더 구조 원칙
    - 명명 규칙
    - 절대 하면 안 되는 것 (예: "절대 console.log를 커밋하지 말 것", "절대 any 타입 쓰지 말 것")
3. **결정 로그(ADR: Architecture Decision Record)**: 중요한 기술 선택의 근거를 남기는 짧은 문서. 한 결정당 한 파일, 한 페이지 분량.
    
    ```
    # ADR-001: 데이터베이스로 PostgreSQL 선택
    ## 맥락
    ## 결정
    ## 대안
    ## 결과
    ```
    
4. **명시적인 안티 패턴 목록**: "이건 하지 마세요" 리스트. 예: "전역 상태 라이브러리를 도입하지 말 것. React Context로 충분."
    
5. **샘플 코드 한두 개**: 컴포넌트, API 핸들러, 테스트의 "모범 예시"를 하나씩 만들어두면, Claude가 그 패턴을 복제합니다.

## 한 가지 조언

설계를 **완벽하게 하려고 하면 영원히 끝나지 않습니다**. "코드 첫 줄 쓰기 전에 결정해야 후회하지 않을 것"과 "나중에 바꿔도 큰 비용이 들지 않는 것"을 구분하세요.

- **바꾸기 어려운 것** (= 지금 결정): 데이터 모델, 인증 방식, 핵심 아키텍처, 폴더 구조
- **나중에 바꿀 수 있는 것** (= 일단 시작): UI 디테일, 마이너 라이브러리, 비핵심 알고리즘

규모가 큰 프로젝트라면 위 항목 전부, 작은 사이드 프로젝트라면 데이터 모델 + API 스펙 + 폴더 구조 + `CLAUDE.md`만 잘 잡아도 90%는 됩니다.

만들려는 앱의 구체적인 종류나 규모를 알려주시면, 그 맥락에 맞는 설계 문서 템플릿이나 `CLAUDE.md` 샘플을 직접 작성해드릴 수 있습니다.
