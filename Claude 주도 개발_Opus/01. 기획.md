기획 단계는 "무엇을, 왜, 누구를 위해, 어떤 기준으로 성공이라 부를지"를 결정하는 단계입니다. 이 단계가 부실하면 이후 모든 단계가 흔들리기 때문에, 코드를 한 줄도 쓰기 전에 충분히 시간을 투자할 가치가 있습니다.

특히 **Claude Code로 개발**할 거라면, 기획 산출물이 곧 AI에게 줄 컨텍스트가 됩니다. 사람이 보기에 충분한 기획서가 아니라, **AI가 읽고 일관된 결정을 내릴 수 있을 만큼 명시적인 기획서**를 만든다는 관점이 중요합니다.

## 기획 단계의 구체적 작업

### 1. 문제 정의 (Problem Statement)

가장 먼저 할 일은 "왜 이걸 만드는가"에 대한 답을 글로 정리하는 것입니다.

- **해결하려는 문제**: 어떤 불편함, 비효율, 기회가 있는가?
- **현재의 대안**: 사용자는 지금 이 문제를 어떻게 해결하고 있는가? (경쟁 제품, 수동 작업, 우회 방법)
- **우리만의 차별점**: 왜 새로 만들어야 하는가? 기존 도구로 안 되는 이유는?

한 문장으로 정리해보는 연습이 좋습니다. 예: _"바쁜 직장인이 매일 영양제 복용을 빠뜨리지 않도록, 시간대별 알림과 복용 기록을 한 화면에서 관리하는 모바일 앱."_

### 2. 타깃 사용자 정의 (Target Users / Personas)

- **주 사용자(Primary)**: 가장 자주, 깊게 쓸 사람. 1~2명의 페르소나로 구체화 (이름, 나이, 직업, 사용 맥락까지).
- **부 사용자(Secondary)**: 가끔 쓰거나 부수적으로 영향받는 사람.
- **비사용자**: 이 제품의 타깃이 _아닌_ 사람을 명시하면 의외로 범위가 또렷해집니다.

### 3. 핵심 가치 & 성공 지표 (Value Proposition & KPI)

- **사용자 가치**: 이 앱을 쓰면 사용자가 무엇을 얻는가? (시간 절약, 비용 절감, 즐거움 등)
- **비즈니스 가치**: 만드는 쪽에 어떤 의미가 있는가?
- **성공의 측정 기준**:
    - 정량 지표: DAU, 재방문율, 작업 완료 시간, 전환율 등
    - 정성 지표: 사용자 만족도, NPS, 인터뷰 피드백
- **언제 성공/실패로 판단하는가**: 출시 후 N주 안에 어떤 수치가 나와야 하는가?

### 4. 범위 정의 (Scope: In / Out)

이 단계가 **가장 자주 생략되는데, 가장 중요한** 부분입니다.

- **MVP에 포함되는 기능 (In-Scope)**: 반드시 들어가야 할 최소 기능 목록
- **명시적으로 제외되는 기능 (Out-of-Scope)**: "이번엔 안 합니다" 리스트
- **나중에 할 것 (Future / Nice-to-have)**: 다음 버전에서 고려

Claude Code 관점에서는 Out-of-Scope를 적어두는 게 특히 중요합니다. 그렇지 않으면 AI가 "친절하게" 요청하지도 않은 기능을 자꾸 추가합니다.

### 5. 사용자 스토리 / 유스케이스 작성

각 핵심 기능을 사용자 관점의 시나리오로 풀어 씁니다.

형식 예시:

> _"[사용자 유형]으로서, [어떤 행동]을 하고 싶다, 왜냐하면 [어떤 가치]를 얻기 위해서다."_

예: _"바쁜 직장인으로서, 아침에 영양제를 먹었는지 한 번에 확인하고 싶다, 중복 복용을 피하기 위해서다."_

각 스토리에는 **수용 기준(Acceptance Criteria)**을 붙입니다. "이 조건이 만족되면 이 기능은 완성된 것"이라는 체크리스트가 곧 나중에 테스트 케이스로 변환됩니다.

### 6. 우선순위 결정 (Prioritization)

모든 기능이 똑같이 중요하지는 않습니다. 흔히 쓰는 프레임워크:

- **MoSCoW**: Must / Should / Could / Won't
- **RICE 점수**: Reach × Impact × Confidence ÷ Effort
- **Kano 모델**: 기본 / 성능 / 매력 기능 구분

처음 만드는 거라면 MoSCoW가 가장 단순하고 실용적입니다.

### 7. 제약 조건 & 가정 (Constraints & Assumptions)

- **기술 제약**: 특정 플랫폼, 언어, 인프라 요구 사항
- **시간 제약**: 출시 데드라인
- **예산 제약**: 인프라 비용, 외부 API 비용
- **법/규제**: 개인정보 보호(GDPR, 개인정보보호법), 결제, 의료 등
- **가정**: "사용자가 인터넷에 항상 연결되어 있다고 가정한다" 같은 명시적 가정. 가정은 나중에 깨질 수 있으니 적어두면 위험 관리가 됩니다.

### 8. 위험 식별 (Risk Assessment)

- 기술적 위험: "이 라이브러리가 우리 요구사항을 진짜 지원할까?"
- 일정 위험: 의존성, 외부 검토 등
- 사용자 위험: "정말 이 기능을 원할까?"

각 위험에 대해 **완화 방안**을 한 줄씩 적습니다.

### 9. 산출물 정리 (Documentation)

기획 단계가 끝나면 다음 문서들이 생겨야 합니다:

- **PRD (Product Requirements Document)**: 위 1~8을 한 문서로 정리
- **사용자 스토리 목록**: 우선순위 포함
- **제약/가정/위험 리스트**

Claude Code로 개발할 거라면, 이 문서들을 프로젝트 루트의 `docs/` 폴더나 `CLAUDE.md`에 넣어두세요. 매 세션마다 Claude가 컨텍스트를 잃기 때문에, 기획 문서가 디스크에 있어야 일관된 결정을 유지할 수 있습니다.

## Claude Code 작업 시 특별 팁

1. **AI에게 기획을 함께 시키기**: 기획 단계 자체를 Claude와 대화하며 진행하면 좋습니다. "이 PRD에서 빠진 게 뭐야?", "이 스토리의 엣지 케이스는?" 같은 질문이 강력합니다.
    
2. **명시적 ≫ 암시적**: 사람끼리는 "당연한" 부분도 AI에게는 명시해야 합니다. 예를 들어 "로그인은 이메일+비밀번호 방식"이라고 적지 않으면, 어느 날 갑자기 OAuth 코드가 들어와 있을 수 있습니다.
    
3. **결정 로그(Decision Log) 만들기**: "왜 A 대신 B를 선택했는가"를 짧게 기록해두면, 나중에 Claude가 "왜 이렇게 했지?"라고 자기 코드를 재해석해서 망가뜨리는 걸 막을 수 있습니다.
    

## 정리

기획 단계의 최종 체크리스트는 이렇습니다:

- [ ] 문제 정의 한 문장으로 표현됨
- [ ] 타깃 사용자 페르소나 1~2개
- [ ] 성공 지표 정량/정성 정의
- [ ] MVP 범위 In/Out 명시
- [ ] 핵심 사용자 스토리 + 수용 기준
- [ ] 우선순위(MoSCoW 등) 적용
- [ ] 제약/가정/위험 문서화
- [ ] PRD 문서로 정리되어 Claude가 읽을 수 있는 위치에 저장

기획 문서 양이 부담스럽다면, 사이드 프로젝트는 위 항목들을 **각각 2~3문장씩**으로 짧게 써도 충분합니다. 중요한 건 _형식_이 아니라 _생각이 정리되었는가_입니다.

혹시 만들려는 앱이 구체적으로 어떤 것인지 알려주시면, 그 앱에 맞는 PRD 템플릿이나 사용자 스토리 예시를 함께 작성해드릴 수 있습니다.
