테스트 단계는 "구현한 것이 정말로 의도대로 동작하는가, 그리고 미래의 변경에도 깨지지 않을 안전망이 있는가"를 검증하는 단계입니다. 흔히 "기능 다 만들고 마지막에 한꺼번에" 하는 단계로 오해되지만, 실제로는 **개발과 거의 동시에 일어나야** 효율적입니다.

특히 Claude Code 환경에서는 테스트의 의미가 한 단계 더 중요해집니다. AI는 그럴듯하지만 미묘하게 틀린 코드를 만들 수 있기 때문에, **테스트가 곧 사양의 실행 가능한 형태**가 되어줍니다. 테스트가 통과한다 = 사양을 만족한다 라는 등식이 성립하면, AI에게 일을 시키고 검증하는 사이클이 매우 빨라집니다.

## 테스트 단계의 구체적 작업

### 1. 테스트 전략 확정 (Test Strategy)

설계 단계에서 잡은 전략을 구체화합니다.

- **테스트 피라미드의 비율 결정**:
    - 단위 테스트(많이, 빠르게)
    - 통합 테스트(중간, DB/API 포함)
    - E2E 테스트(적게, 실제 사용자 흐름)
- **각 레이어에서 무엇을 검증할지** 명시
    - 단위: 순수 함수, 비즈니스 로직, 유틸
    - 통합: API 엔드포인트, DB 트랜잭션, 외부 서비스 모킹
    - E2E: 핵심 사용자 시나리오 (로그인 → 주문 → 결제)
- **커버리지 목표 설정**: 100%는 비현실적, 핵심 도메인 80%+, 전체 60~70% 정도가 일반적
- **테스트 우선순위**: 깨지면 치명적인 부분부터

### 2. 단위 테스트 (Unit Tests)

가장 많이 작성하게 될 테스트입니다.

**무엇을 테스트하는가**:

- 순수 함수의 입력→출력
- 비즈니스 로직 (가격 계산, 상태 전이, 권한 체크)
- 유틸리티 함수
- React Hook, 컴포넌트 로직 (렌더링은 RTL로)

**좋은 단위 테스트의 조건**:

- **빠르다** (밀리초 단위)
- **독립적이다** (다른 테스트 영향 X)
- **결정적이다** (랜덤/시간/네트워크 의존 X)
- **읽기 쉽다** (AAA 패턴: Arrange-Act-Assert)
- **하나의 동작만 검증한다**

**테스트 케이스 종류**:

- 정상 케이스 (Happy path)
- 경계값 (0, 음수, 빈 배열, 매우 큰 값)
- 에러 케이스 (잘못된 입력, 예외 상황)
- 엣지 케이스 (null, undefined, 동시성)

### 3. 통합 테스트 (Integration Tests)

여러 컴포넌트가 함께 동작하는지 검증합니다.

**무엇을 테스트하는가**:

- API 엔드포인트 (요청→응답 전체 흐름)
- DB와의 상호작용 (실제 DB 또는 테스트용 DB)
- 외부 서비스 통합 (모킹/스텁 사용)
- 인증/인가 흐름

**필요한 인프라**:

- 테스트 DB (Docker로 띄우거나 SQLite 인메모리)
- 시드 데이터 / 픽스처
- 테스트 전후 DB 초기화 로직
- API 클라이언트 (supertest 등)
- 외부 API 모킹 (MSW, nock)

### 4. E2E 테스트 (End-to-End)

실제 사용자가 브라우저에서 하는 행동을 자동화합니다.

**무엇을 테스트하는가**:

- **핵심 사용자 여정**만 (모든 화면이 아님!)
- 회원가입 → 로그인 → 핵심 기능 → 로그아웃
- 결제 같은 치명적 흐름

**도구**: Playwright, Cypress

**주의점**:

- 느리고 깨지기 쉬움 → 적게 유지
- 셀렉터는 `data-testid` 등 안정적인 것 사용
- 테스트 간 격리 (각 테스트는 독립 사용자/데이터)
- 비결정성 제거 (명시적 대기 사용, 시간 기반 대기 금지)

### 5. 기타 테스트 유형

프로젝트 성격에 따라 추가:

- **스냅샷 테스트**: UI 렌더링 결과 비교 (남용 주의)
- **시각적 회귀 테스트**: Chromatic, Percy
- **접근성 테스트**: axe-core, jest-axe
- **성능 테스트**: Lighthouse CI, k6, Artillery
- **부하 테스트**: 동시 사용자 시뮬레이션
- **보안 테스트**: OWASP ZAP, npm audit, Snyk
- **계약 테스트(Contract Testing)**: Pact (마이크로서비스 간)
- **속성 기반 테스트(Property-based)**: fast-check, Hypothesis
- **돌연변이 테스트(Mutation Testing)**: Stryker (테스트의 테스트)

### 6. 테스트 데이터 관리

테스트의 안정성은 데이터 관리에 크게 좌우됩니다.

- **픽스처(Fixtures)**: 고정된 테스트 데이터
- **팩토리(Factory)**: 필요할 때마다 데이터 생성 (Factory Bot 패턴)
- **Faker 라이브러리**: 현실적인 더미 데이터
- **빌더 패턴**: 복잡한 객체를 가독성 있게 생성
- **테스트 간 격리**: 각 테스트가 자기 데이터를 만들고 정리

```typescript
// 좋은 예: 팩토리 + 빌더
const user = userFactory.build({ email: 'test@example.com' });
const order = orderFactory.build({ user, status: 'pending' });
```

### 7. 모킹 전략 (Mocking)

무엇을 모킹할지가 테스트 품질을 결정합니다.

**모킹해야 하는 것**:

- 외부 API (네트워크 의존 제거)
- 시간 (`Date.now()`, 타이머)
- 랜덤 값
- 파일 시스템 (단위 테스트 한정)
- 비싼 연산

**모킹하면 안 되는 것**:

- 테스트 대상 자체
- 자기 코드의 내부 구현 디테일 (리팩토링 시 깨짐)
- 단순 값 객체

**원칙**: "외부 경계는 모킹, 내부는 실제 사용"

### 8. 테스트 실행 자동화

**로컬 실행**:

- watch 모드 (`vitest --watch`)로 파일 저장 시 자동 실행
- pre-commit 훅에서 변경된 파일 관련 테스트만 실행
- pre-push 훅에서 전체 단위 테스트 실행

**CI 실행**:

- PR마다 모든 단위/통합 테스트 실행
- main 브랜치에 E2E 테스트 추가 실행
- 야간에 부하/보안 테스트
- 병렬 실행으로 시간 단축
- 캐싱 (의존성, 빌드 결과)

### 9. 커버리지 측정 & 보고

- **도구**: Istanbul/c8 (JS), coverage.py (Python)
- **메트릭**: 라인/브랜치/함수 커버리지
- **임계값 설정**: 일정 수치 이하면 CI 실패
- **변경된 코드의 커버리지** 우선 (전체보다 의미 있음)
- **시각화**: Codecov, Coveralls에 업로드

**주의**: 커버리지 100%가 품질을 보장하지 않습니다. 의미 없는 테스트로 숫자만 채울 수 있으니, **무엇을** 테스트하는지가 더 중요합니다.

### 10. 회귀 테스트 (Regression Tests)

버그가 발견되면:

1. **버그를 재현하는 테스트를 먼저 작성** (실패해야 함)
2. 그 버그를 수정
3. 테스트가 통과하면 수정 완료
4. 이 테스트는 영구히 회귀 방지 역할

이 방식이 "고쳤다고 했는데 또 같은 버그 터지는" 사고를 막아줍니다.

### 11. 플레이키 테스트(Flaky Test) 관리

가끔 통과/실패하는 테스트는 신뢰를 무너뜨립니다.

- **즉시 격리**: skip 처리 후 별도 이슈로 추적
- **원인 분석**: 비결정성 원천 찾기 (시간, 순서, 네트워크, DB 상태)
- **수정 또는 삭제**: 못 고치면 차라리 삭제
- **재시도(retry)는 마지막 수단**: 근본 해결이 아니라 증상 가림

### 12. 테스트 리뷰 & 유지보수

테스트도 코드입니다. 같이 리뷰하고 리팩토링합니다.

- **테스트 자체에 대한 코드 리뷰**: 명확한 이름, 적절한 추상화
- **중복 제거**: 헬퍼 함수, 공통 셋업 추출
- **사양 변경 시 테스트 업데이트**
- **죽은 테스트 제거**: 사용하지 않는 기능의 테스트

### 13. 테스트 문서화

- **각 테스트 파일 상단에 의도 주석** (필요 시)
- **테스트 이름은 사양처럼**: `describe('User signup')` > `it('rejects duplicate email')`
- **테스트 보고서 생성**: CI에서 JUnit XML 같은 형식으로

## 서브에이전트 활용 방안

테스트 단계는 서브에이전트를 가장 효과적으로 쓸 수 있는 단계 중 하나입니다. 반복적이고, 패턴이 명확하고, 컨텍스트가 격리되기 쉬운 작업이 많기 때문입니다.

### 패턴 1: 테스트 케이스 설계자 (Test Designer)

**역할**: "주어진 함수/기능에 대해 어떤 테스트 케이스가 필요한지 나열"

코드를 받고 **테스트 케이스의 목록만** 반환합니다. 실제 코드는 아직 안 짭니다.

시스템 프롬프트 예시:

> "당신은 QA 엔지니어다. 주어진 함수에 대해 다음을 분류해서 나열하라: 정상 케이스, 경계값, 에러 케이스, 엣지 케이스, 보안 관련 케이스. 각 케이스는 한 줄로 표현하라. 코드는 작성하지 마라."

**효과**: 메인 에이전트가 "어떤 케이스를 빠뜨렸을까?"를 고민하지 않아도 됩니다. 사람과 AI 모두 정상 케이스만 떠올리는 경향이 있는데, 이 에이전트가 강제로 엣지 케이스를 발굴합니다.

### 패턴 2: 단위 테스트 작성자 (Unit Test Writer)

**역할**: "케이스 목록과 대상 함수를 받아 실제 테스트 코드 작성"

시스템 프롬프트에 박아둘 것:

- 프레임워크 (Vitest/Jest 등)
- 테스트 파일 위치 규칙
- 명명 규칙
- AAA 패턴 강제
- 사용할 모킹 라이브러리
- 절대 하지 말 것 (예: 내부 구현 모킹 금지)

**효과**: 매번 "Vitest로 짜줘, AAA 패턴으로, 파일은 *.test.ts로..." 같은 지시를 반복하지 않아도 됩니다. 일관된 스타일의 테스트가 대량 생산됩니다.

### 패턴 3: 통합 테스트 작성자 (Integration Test Writer)

**역할**: "API 엔드포인트나 DB 트랜잭션에 대한 통합 테스트 작성"

별도 에이전트로 분리하는 이유: 단위 테스트와 다른 패턴(테스트 DB 셋업, 시드 데이터, 클린업)이 필요하기 때문.

시스템 프롬프트에:

- 테스트 DB 셋업 방법
- 시드/팩토리 사용 패턴
- 인증된 요청 만드는 헬퍼
- 트랜잭션 롤백 패턴

### 패턴 4: E2E 시나리오 작성자 (E2E Scenario Writer)

**역할**: "사용자 스토리를 받아 Playwright/Cypress 테스트로 변환"

시스템 프롬프트에:

- 사용할 셀렉터 전략 (`data-testid` 우선)
- 명시적 대기 패턴
- 각 테스트의 독립성 보장 방법
- Page Object 패턴 사용 여부

### 패턴 5: 모킹 설계자 (Mock Designer)

**역할**: "외부 의존성을 식별하고 모킹 코드 작성"

대상 코드를 분석해서:

- 모킹해야 할 외부 호출 목록
- 각각의 모킹 코드
- 시간/랜덤 등 비결정성 제거 방법

### 패턴 6: 테스트 리뷰어 (Test Reviewer)

**역할**: "작성된 테스트가 의미 있는지, 안티패턴이 없는지 검토"

체크 항목:

- 내부 구현 모킹 안 했는가
- 단언(assertion)이 너무 약하지 않은가 (예: `expect(result).toBeDefined()`만)
- 단언이 누락된 테스트는 없는가
- 테스트 이름이 사양을 표현하는가
- 한 테스트가 너무 많은 걸 검증하지 않는가
- 플레이키할 가능성이 있는가 (시간, 랜덤, 순서 의존)

**왜 별도 에이전트인가**: 테스트 작성자와 다른 시각이 필요합니다. 같은 에이전트는 자기 코드의 약점을 잘 못 봅니다.

### 패턴 7: 회귀 테스트 생성기 (Regression Test Generator)

**역할**: "버그 리포트나 픽스 PR을 받아 회귀 테스트 작성"

입력:

- 버그 재현 단계
- 수정 전후 코드
- 원인 분석

출력:

- 수정 전 코드에서는 실패하고, 수정 후 코드에서는 통과하는 테스트

이 에이전트를 두면 "버그 픽스마다 회귀 테스트 추가"라는 좋은 습관이 자동화됩니다.

### 패턴 8: 커버리지 분석가 (Coverage Analyzer)

**역할**: "커버리지 리포트를 분석하고 우선 보강할 곳 추천"

입력:

- 커버리지 리포트
- 코드 변경 이력

출력:

- 커버리지가 낮으면서 변경이 잦은 파일 = 우선순위 높음
- 어떤 종류의 테스트가 부족한지 (단위 vs 통합)
- 구체적인 추천 케이스

### 패턴 9: 플레이키 테스트 헌터 (Flaky Test Hunter)

**역할**: "테스트 실행 로그를 받아 플레이키 테스트 식별 및 원인 분석"

여러 번의 CI 실행 결과를 비교해서:

- 어떤 테스트가 가끔 실패하는지
- 실패의 공통점 (시간대, 부하, 다른 테스트와의 순서)
- 의심되는 원인과 수정 제안

### 패턴 10: 보안 테스트 에이전트 (Security Test Agent)

**역할**: "OWASP Top 10 등 보안 관점의 테스트 케이스 생성"

시스템 프롬프트에 OWASP, CWE 패턴을 박아두고, API 엔드포인트나 폼을 받으면:

- SQL 인젝션 테스트
- XSS 테스트
- 인증/인가 우회 테스트
- 레이트 리미팅 테스트

### 실전 워크플로: "결제 환불 기능 테스트"

```
1. 메인이 환불 기능 구현 완료
2. → Test Designer: "환불 함수의 테스트 케이스 나열"
   → 정상 1개, 경계값 3개, 에러 4개, 엣지 2개 목록 받음
3. → Mock Designer: "환불은 Stripe API 호출함. 모킹 코드 작성"
   → 모킹 셋업 코드 받음
4. → Unit Test Writer: 케이스 목록 + 모킹 코드 + 대상 함수 전달
   → 단위 테스트 파일 받음
5. → Integration Test Writer: "POST /api/refunds 엔드포인트 통합 테스트"
   → 통합 테스트 파일 받음
6. → Security Test Agent: "환불 API의 보안 케이스"
   → 권한 우회/금액 변조 시나리오 받음
7. → Test Reviewer: 작성된 모든 테스트 검토
   → 약한 단언 2개, 모킹 안티패턴 1개 지적
8. → 메인이 수정, 테스트 실행, 통과 확인
9. → Coverage Analyzer: 보강할 곳 있는지 분석
   → 환불 취소 분기 미커버 발견 → 케이스 추가
```

한 명의 개발자가 순차적으로 했다면 컨텍스트가 폭발했을 작업이, 역할 분담으로 깔끔하게 정리됩니다.

### 서브에이전트 운영 팁

1. **`.claude/agents/` 폴더로 표준화**: 팀 전체가 같은 에이전트 셋 공유
    
    ```
    .claude/agents/
      test-designer.md
      unit-test-writer.md
      integration-test-writer.md
      e2e-scenario-writer.md
      test-reviewer.md
      mock-designer.md
      regression-test-generator.md
      coverage-analyzer.md
      security-test-agent.md
    ```
    
2. **에이전트끼리 직접 대화시키지 말 것**: 무한 루프나 컨텍스트 혼란 위험. 메인이 중재자 역할.
    
3. **출력 포맷 표준화**: 다음 에이전트가 받을 입력 형식을 미리 정해두면 파이프라인이 됩니다.
    
4. **검증 가능한 결과 요구**: "테스트를 작성했다"가 아니라 "테스트가 실행되어 N개 통과, M개 실패"로 보고하게 합니다.
    
5. **사람의 최종 검토**: AI가 만든 테스트도 사람이 한 번은 봐야 합니다. 특히 단언이 사양을 정확히 표현하는지.

## 테스트 단계 체크리스트

- [ ] 테스트 전략 문서화 (피라미드 비율, 커버리지 목표)
- [ ] 단위 테스트: 핵심 로직 + 엣지 케이스 커버
- [ ] 통합 테스트: 주요 API 엔드포인트
- [ ] E2E 테스트: 핵심 사용자 여정 1~3개
- [ ] 테스트 데이터 관리 (팩토리/픽스처)
- [ ] 외부 의존성 모킹 전략 일관성
- [ ] CI에서 자동 실행
- [ ] 커버리지 측정 + 임계값 설정
- [ ] 발견된 버그마다 회귀 테스트 추가
- [ ] 플레이키 테스트 0개 유지
- [ ] 테스트 자체에 대한 코드 리뷰
- [ ] (선택) 보안/성능/접근성 테스트
- [ ] 서브에이전트로 테스트 케이스 발굴 + 작성 + 리뷰 분리

## 한 가지 조언

테스트에서 가장 흔한 실수는 **"많이 짜기"에 집착하는 것**입니다. 의미 없는 테스트 1000개보다 핵심을 정확히 검증하는 테스트 100개가 낫습니다.

좋은 테스트의 기준:

1. **실패할 때 무엇이 잘못됐는지 즉시 알려준다** — 이름과 단언이 명확
2. **사양을 표현한다** — 테스트만 읽어도 기능을 이해할 수 있다
3. **리팩토링 시에도 안 깨진다** — 동작을 테스트하지, 구현을 테스트하지 않는다
4. **빠르다** — 단위 테스트는 밀리초, 전체 스위트는 분 단위
5. **결정적이다** — 같은 입력에 항상 같은 결과

특히 **"테스트가 사양이다"** 라는 마인드셋이 Claude Code 환경에서 결정적입니다. 테스트를 잘 짜두면, AI에게 "이 테스트들이 통과하도록 구현해줘"라고 시키는 게 가능해집니다. 그러면 검증이 자동화되고, 개발 속도가 비약적으로 빨라집니다.

혹시 진행 중인 프로젝트의 테스트 프레임워크와 현재 커버리지 상황을 알려주시면, 그에 맞는 서브에이전트 정의 파일과 우선 보강할 테스트 영역을 구체적으로 제안해드릴 수 있습니다.
