### 파운데이션 모델의 도메인 파인튜닝과 할루시네이션 문제

### 1\. 결론

파운데이션 모델(Foundation Model)에 특정 도메인의 지식을 파인튜닝(Fine-tuning)하더라도 할루시네이션(Hallucination)을 완전히 방지할 수는 없다.

다만 적절한 학습 데이터와 학습 방법을 사용하면 해당 도메인에 대한 이해도와 답변 정확도를 상당히 높일 수 있다.

핵심은 다음과 같다.

* 파인튜닝은 모델의 지식과 답변 능력을 개선하는 방법이다.

* 파인튜닝은 모델이 사실만 말하도록 보장하는 방법이 아니다.

* RAG를 결합하면 실제 원본 문서를 근거로 답변하도록 유도할 수 있다.

* 근거가 부족할 때 답변을 거부하는 기능까지 구현해야 할루시네이션을 효과적으로 줄일 수 있다.

### 2\. 도메인 지식을 파인튜닝하면 어떤 일이 발생할까?

예를 들어 금융·보험 도메인의 지식으로 파인튜닝한다고 가정한다.

학습 데이터에 다음과 같은 내용이 포함되어 있다고 가정하자.

### 학습 데이터 예시

```text
질문:
보험계약의 청약철회 가능 기간은?

답변:
보험계약자는 일반적으로 보험증권을 받은 날부터
15일 이내에 청약을 철회할 수 있습니다.

다만 관련 법령과 계약 유형에 따라 예외가 있을 수 있습니다.
```

이와 같은 데이터를 대량으로 학습하면 모델은 다음과 같은 능력을 개선할 수 있다.

| 항목             | 파인튜닝 효과           |
| -------------- | ----------------- |
| 도메인 용어 이해      | 크게 개선 가능          |
| 도메인 관련 질문 이해   | 개선 가능             |
| 답변 형식과 표현      | 크게 개선 가능          |
| 학습한 사실의 회상     | 개선 가능하지만 보장되지 않음  |
| 새로운 질문에 대한 일반화 | 학습 데이터 품질과 범위에 좌우 |
| 할루시네이션 방지      | 완전히 해결할 수 없음      |

특히 주의해야 할 부분은 학습 데이터에 포함된 사실을 언제나 정확하게 기억하고 답변하는 것은 아니라는 점이다.

### 3\. 파인튜닝을 해도 할루시네이션이 발생하는 이유

대표적으로 네 가지 이유가 있다.

### 3.1. 모델은 데이터베이스가 아니다.

파인튜닝을 통해 지식을 모델의 파라미터에 반영하지만, 모델 내부에 문서를 원본 그대로 저장하고 검색하는 것은 아니다.

학습된 패턴을 바탕으로 다음에 나올 가능성이 높은 토큰을 생성한다.

따라서 학습한 내용과 유사한 질문에서도 잘못된 내용을 생성할 수 있다.

### 3.2. 학습 데이터에 없는 질문에도 답변하려고 한다.

예를 들어 보험 약관에 A 상품의 청약철회 조건만 학습했는데 B 상품에 대한 질문을 받으면 A 상품의 조건을 B 상품에도 적용할 수 있다.

### 3.3. 학습 지식 간에 충돌이 발생할 수 있다.

기존 파운데이션 모델이 가지고 있던 일반 지식과 파인튜닝 데이터가 충돌하면 잘못된 답변을 생성할 수 있다.

### 3.4. 시간에 따라 변하는 지식이 있다.

금융상품, 보험 약관, 법령, 회사 내부 규정처럼 변경되는 지식은 파인튜닝만으로 최신 상태를 유지하기 어렵다.

### 4\. 파인튜닝과 RAG의 차이

도메인 지식을 모델에 적용하는 방법으로 파인튜닝과 RAG를 구분할 필요가 있다.

### 4.1. 파인튜닝(Fine-tuning)

파인튜닝은 도메인 관련 학습 데이터를 이용해 기존 파운데이션 모델의 파라미터를 조정하는 방법이다.

```text
                 도메인 학습 데이터
                        |
                        v
                  파인튜닝 과정
                        |
                        v
                 파인튜닝된 LLM
                        |
                        v
                   사용자 질문
                        |
                        v
                    답변 생성
```

특징

* 도메인 용어와 개념에 대한 이해도 향상

* 특정 도메인의 질문에 적합한 답변 생성

* 특정 업무에 최적화된 답변 형식 학습

* 반복적인 업무 패턴과 추론 방식 학습

* 학습 데이터에 없는 사실에 대한 할루시네이션은 여전히 발생 가능

### 4.2. RAG(Retrieval-Augmented Generation)

RAG는 LLM이 답변을 생성하기 전에 외부 지식 저장소에서 관련 문서를 검색하고, 검색된 내용을 참고하여 답변을 생성하는 방법이다.

```text
                  도메인 원본 문서
                        |
                        v
                  문서 전처리
                        |
                        v
                 Embedding 생성
                        |
                        v
                  Vector Database
                        |
                        |
사용자 질문 --------+
    |                   |
    v                   v
질문 분석          관련 문서 검색
                        |
                        v
                  검색 결과 구성
                        |
                        v
                  LLM + 검색 문서
                        |
                        v
                    답변 생성
```

특징

* 원본 문서를 기반으로 답변 생성

* 문서가 변경되면 재학습 없이 지식 갱신 가능

* 답변의 근거가 되는 문서와 출처 제시 가능

* 도메인 지식의 최신성 유지에 유리

* 검색 오류나 문서 해석 오류로 할루시네이션이 발생할 수 있음

### 4.3. 파인튜닝과 RAG 비교

| 비교 항목    | 파인튜닝          | RAG            |
| -------- | ------------- | -------------- |
| 핵심 목적    | 모델의 능력 개선     | 외부 지식 활용       |
| 지식 저장    | 모델 파라미터       | 외부 데이터베이스      |
| 도메인 이해   | 개선 가능         | 기본 모델에 의존      |
| 최신 지식 반영 | 재학습 필요        | 문서 갱신으로 가능     |
| 원본 문서 확인 | 어려움           | 가능             |
| 출처 제시    | 기본적으로 어려움     | 가능             |
| 할루시네이션   | 발생 가능         | 발생 가능          |
| 운영 비용    | 학습 및 모델 관리 비용 | 검색 인프라 및 추론 비용 |

근본적인 차이는 다음과 같다.

* 파인튜닝: 모델이 도메인 지식을 잘 이해하고 활용하도록 만든다.

* RAG: 모델이 답변할 때 실제 도메인 문서를 참고하도록 만든다.

### 5\. 가장 좋은 방법은 파인튜닝과 RAG를 결합하는 것

실제 기업의 전문 도메인 시스템이라면 파인튜닝과 RAG를 결합하는 하이브리드 아키텍처를 추천한다.

### 5.1. 하이브리드 아키텍처

```text
                  사용자 질문
                       |
                       v
              +------------------+
              |   도메인 LLM     |
              |  (Fine-tuning)   |
              +------------------+
                       |
                       v
                질문 의도 분석
                       |
                       v
              +------------------+
              |    RAG 검색      |
              |                  |
              |  BM25 Search     |
              |  Vector Search   |
              |  Hybrid Search   |
              +------------------+
                       |
                       v
              +------------------+
              |    Reranking     |
              +------------------+
                       |
                       v
                 관련 문서 추출
                       |
                       v
              +------------------+
              |  LLM 답변 생성   |
              |                  |
              | 질문 + 검색 문서 |
              +------------------+
                       |
                       v
              +------------------+
              |   답변 검증      |
              |                  |
              | 근거 일치 여부   |
              | 출처 확인        |
              +------------------+
                       |
                       v
                최종 답변 생성
                       |
                       v
                  사용자 응답
```

### 5.2. 각 구성 요소의 역할

| 구성 요소         | 담당 역할                |
| ------------- | -------------------- |
| Fine-tuning   | 도메인 이해, 전문 용어, 답변 방식 |
| RAG           | 최신 원본 지식 제공          |
| BM25          | 키워드 기반 문서 검색         |
| Vector Search | 의미 기반 문서 검색          |
| Reranker      | 검색 문서의 관련성 향상        |
| 답변 검증         | 근거와 생성된 답변의 일치 여부 확인 |
| Abstention    | 근거가 부족하면 답변하지 않도록 처리 |

여기서 중요한 것은 모델이 답변을 생성하는 것과 답변이 사실인지 검증하는 것을 별도의 단계로 분리하는 것이다.

### 6\. 할루시네이션을 얼마나 줄였는지 어떻게 검증할까?

파인튜닝이나 RAG를 도입한 뒤에는 반드시 별도의 평가 데이터셋으로 성능을 측정해야 한다.

### 6.1. 주요 평가 항목

| 평가 항목                | 검증 내용                      |
| -------------------- | -------------------------- |
| 정답 정확도               | 답변이 실제 사실과 일치하는가?          |
| 근거 충실도(Faithfulness) | 검색된 원문에 없는 내용을 만들어 내지 않는가? |
| 출처 정확도               | 제시한 문서와 페이지가 실제 근거인가?      |
| 답변 거부 정확도            | 근거가 없을 때 답변을 보류하는가?        |
| 최신성                  | 현재 적용되는 규정과 일치하는가?         |

### 6.2. 문서에 없는 질문으로 테스트하기

특히 중요한 테스트는 학습 데이터나 RAG 문서에 존재하지 않는 질문을 던지는 것이다.

예를 들어 문서에 존재하지 않는 보험 상품의 약관을 질문했을 때 다음과 같이 응답해야 한다.

```text
제공된 문서에서는 해당 보험 상품의
청약철회 조건을 확인할 수 없습니다.

정확한 답변을 위해 해당 상품의 약관이 필요합니다.
```

이러한 능력을 일반적으로 Abstention(답변 거부 또는 보류)이라고 한다.

단순히 정답을 잘 맞히는 것뿐만 아니라, 모르는 질문에 대해서 모른다고 답할 수 있는 능력도 중요하다.

### 7\. 실제 프로젝트에 적용한다면?

금융·보험 SI 및 사내 기술 문서를 대상으로 전문 도메인 AI를 개발한다면 다음과 같은 단계로 진행하는 것을 추천한다.

### 1단계: RAG 구축

기존 파운데이션 모델을 사용하고 Elasticsearch의 BM25와 Vector Search를 결합한다.

* 문서 수집 및 전처리

* 문서 Chunking

* Embedding 생성

* Elasticsearch 인덱싱

* Hybrid Search

* Reranking

* 검색 문서 기반 답변 생성

### 2단계: 도메인 파인튜닝

실제 사용자 질문과 검증된 답변 데이터를 이용해 모델을 학습시킨다.

단순히 문서 내용을 주입하기보다는 다음과 같은 능력을 학습시키는 것이 좋다.

* 도메인 용어 이해

* 질문 의도 파악

* 도메인 특화 추론

* 답변 형식 및 구조

* 근거가 부족할 때의 응답 방법

### 3단계: 하이브리드 구성

파인튜닝된 모델이 RAG 검색 결과를 활용하도록 연결한다.

### 4단계: 할루시네이션 평가

* 검색된 문서에 없는 내용을 생성하는지 측정

* 답변의 사실 정확도 측정

* 출처와 답변의 일치 여부 확인

* 답변 거부 성능 측정

* 지속적인 평가 및 개선

### 8\. 최종 결론

파운데이션 모델에 특정 도메인의 지식을 파인튜닝한다고 해서 해당 도메인에 대한 할루시네이션이 사라지는 것은 아니다.

가장 중요한 것은 각 기술의 역할을 명확히 구분하는 것이다.

| 기술                  | 목표                       |
| ------------------- | ------------------------ |
| Fine-tuning         | 모델이 도메인을 이해하도록 한다.       |
| RAG                 | 모델이 정확한 원본 문서를 참고하도록 한다. |
| Reranking           | 검색된 문서의 정확도를 높인다.        |
| Answer Verification | 생성된 답변이 근거와 일치하는지 검증한다.  |
| Abstention          | 근거가 부족하면 답변하지 않도록 한다.    |

추천 아키텍처: Fine-tuning + RAG + Answer Verification + Abstention

특히 금융·보험처럼 잘못된 정보가 실질적인 업무 리스크로 연결되는 분야에서는 이 네 가지를 함께 적용하는 것이 적합하다.

궁극적인 목표는 할루시네이션이 전혀 없는 모델을 만드는 것이 아니라, 모델이 근거가 있는 내용만 답변하고 근거가 부족한 경우에는 답변을 보류하도록 시스템 전체를 설계하는 것이다.
