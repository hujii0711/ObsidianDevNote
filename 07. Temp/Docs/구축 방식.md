학습용이므로 **조합 A(전부 무료)**로 진행하겠습니다. 로컬 Qwen, Tavily, Pexels와 mflux, edge-tts, moviepy/ffmpeg를 쓰고, 업로드는 비공개로 올리거나 생략합니다.

## 역할별 에이전트 (어느 방식으로 연결하든 공통)

| 역할 | 하는 일 | 사용 도구 | 형태 |
|---|---|---|---|
| ① **리서처** | 주제 후보와 사실 자료 수집 | Tavily, YouTube Data API | LLM 에이전트 (도구 호출) |
| ② **작가** | 훅과 대본 작성 (60초, 약 300자) | — | LLM (구조화 출력) |
| ③ **검수자** | 대본의 길이, 훅 강도, 사실관계를 점검하고 기준 미달이면 작가에게 되돌림 | — | LLM (판정) |
| ④ **스토리보더** | 장면 JSON 생성 (대사, 화면 설명, 검색 키워드, 길이) | — | LLM (구조화 출력) |
| ⑤ **비주얼 담당** | 장면마다 Pexels에서 검색할지, mflux로 생성할지 판단해 실행 | Pexels, mflux | LLM 에이전트 (도구 호출) |
| ⑥ **보이스** | 장면별 TTS 생성과 단어 단위 타이밍 수집 | edge-tts | **일반 노드 (LLM 없음)** |
| ⑦ **편집자** | 타이밍으로 srt를 만들고 9:16 영상으로 렌더링 | moviepy, ffmpeg | **일반 노드 (LLM 없음)** |
| ⑧ **퍼블리셔** | 제목, 설명, 해시태그 작성과 (선택) 비공개 업로드 | YouTube API | LLM과 도구 |

⑥·⑦은 판단할 일이 없습니다. 그래서 LLM을 쓰지 않는 함수 노드로 두는 것을 제안합니다. 로컬 모델이 실수할 여지도 줄어듭니다.

## 연결 방식

**1. 고정 파이프라인 + 루프 (추천)**
```
리서처 → [사람 확인: 주제 선택] → 작가 ⇄ 검수자 → 스토리보더
   → Send로 장면별 병렬 실행 (비주얼 + 보이스) → 편집자 → 퍼블리셔
```
- 장점
  - 흐름이 결정적이라 디버깅하기 쉽습니다.
  - 로컬 35B 모델에게 순서를 맡기지 않으므로 안정적입니다.
  - 지금까지 배우신 `StateGraph`, 조건부 엣지, `Send`, `interrupt`, 체크포인터를 한 프로젝트에서 모두 써볼 수 있습니다.
- 단점
  - "에이전트가 알아서 판단해 다음 담당을 고르는" 맛은 적습니다.

**2. Supervisor 패턴 (`langgraph-supervisor`)**
- 감독 에이전트가 ①~⑧을 도구처럼 골라 호출합니다.
- 장점
  - 멀티 에이전트다운 구조이고, ch11에서 배우신 패턴입니다.
- 단점
  - 이 작업은 순서가 사실상 정해져 있어서 감독이 할 판단이 거의 없습니다.
  - 로컬 모델은 라우팅 실수(단계 건너뛰기, 반복 호출)가 잦아 디버깅 부담이 큽니다.

**3. 계층형 팀 (상위 감독 → 기획팀 ①~④ / 제작팀 ⑤~⑧ 서브그래프)**
- 장점
  - 서브그래프와 계층 구조를 공부하기에 가장 좋습니다.
- 단점
  - 규모에 비해 구조가 무겁습니다. 2의 라우팅 문제도 두 겹으로 생깁니다.

**추천은 1번입니다.** 다만 ①리서처와 ⑤비주얼 담당 안쪽은 `create_agent`로 만든 도구 호출 에이전트로 둡니다. 이렇게 하면 "에이전트다운 판단"도 함께 경험할 수 있습니다. Supervisor는 나중에 확장 과제로 1번 위에 얹어 보실 수 있습니다.
