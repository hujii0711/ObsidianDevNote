## 1. 도메인 배경 ? 은행 영업점 창구단말이란

### 1-1. 창구단말(Teller Terminal)의 위치

```
[창구직원 PC]                    [은행 전산센터]
 단말 앱(iWorks) ──HTTP 전문──▶ MCA/MCI 게이트웨이(WebLogic) ──▶ 계정계(코어뱅킹)
   │                                                              대외계, 정보계
   ├─ 통장프린터, 핀패드, 스캐너 (주변장치)
   └─ 저널(거래기록) 로컬 저장
```

- **MCA/MCI**(Multi-Channel Architecture/Integration): 창구·ATM·인터넷뱅킹 등 여러 채널의 요청을 표준화된 "전문"으로 받아 코어뱅킹에 중계하는 중간 계층. 이 프로젝트에서는 [IztnGiant.xml](IztnGiant.xml)의 `http://fadapd.kbstar.com:11186/CAAManagerWEB/mci.do`(WebLogic)가 그 접점입니다.
- **전문(電文)**: 금융권 용어로 "고정 포맷의 거래 메시지". `.trn` 파일의 `<INPUT><Fld id= pos= len=>`처럼 **필드 위치·길이가 정의된 구조화 메시지**를 뜻합니다. `HostTran("거래코드")` 한 줄이 화면 데이터를 전문으로 조립→송신→응답 언패킹까지 수행합니다.
- **저널(Journal)**: 창구 거래의 법적 증빙 기록. [Data/Journal/](Data/Journal/)에 **일자별 Access `.mdb`** 로 암호화 저장되며, 이것이 프로젝트에 `JETCOMP.exe`(Jet DB 압축기)가 있는 이유입니다.

### 1-2. 창구 업무 특유의 개념 (스크립트 API에 그대로 반영됨)

| 용어 | 의미 | 관련 API |
|---|---|---|

| **연속거래(Mass)** | 공과금 수납처럼 같은 거래를 반복 실행 | `SetMassTran`, `MassNext`, `MassCancel`, `IsMassStop` |

## 2. 핵심 기술 ① ? MFC (Microsoft Foundation Classes)

이 프로젝트의 C++ 소스는 전부 MFC 관용구로 작성되어 있습니다.

- **MFC**는 Win32 API를 감싼 C++ 프레임워크. `CWinApp`(앱 진입점), `CCmdTarget`(메시지/디스패치 수신 가능 객체), `CString` 등이 기본 어휘입니다.
- **매크로 기반 테이블**이 MFC의 핵심 문법입니다. 분석 시 반드시 읽을 줄 알아야 합니다:
  - `DECLARE_DISPATCH_MAP` / `BEGIN_DISPATCH_MAP` ... `DISP_FUNCTION_ID(클래스, "스크립트이름", dispid, C++메서드, 반환형, 파라미터형)` ? **스크립트 함수명 ↔ C++ 구현의 매핑표**. [ScriptFunction.cpp](IztScript/ScriptFunction.cpp)의 107행부터 325개 항목이 이것이며, 이 테이블이 곧 "내장함수 구현 색인"입니다.
  - `IMPLEMENT_DYNCREATE`, `BEGIN_MESSAGE_MAP` 등도 같은 패턴.
- MFC의 `CCmdTarget`은 `IDispatch`를 자동 구현해 주므로, **MFC 클래스 하나가 곧 COM 오토메이션 객체**가 됩니다. 이 프로젝트가 ATL 대신 MFC로 COM을 만든 이유입니다.

이 프로젝트 전체를 관통하는 접착제입니다. 최소한 다음 개념이 필요합니다.

### 3-1. 기본 개념

| 개념 | 설명 | 프로젝트 내 실물 |

| **dispinterface** | IDispatch 전용 인터페이스 선언 (vtable 없음) | [IztScript.idl:15](IztScript/IztScript.idl#L15) |

| **자기등록(Self-registration)** | DLL이 `DllRegisterServer` 익스포트로 자신을 레지스트리에 등록 (`regsvr32`) | [IztScript.cpp](IztScript/IztScript.cpp), [IztScript.def](IztScript/IztScript.def), [Config/ActiveXList.xml](Config/ActiveXList.xml) |
| **BSTR/VARIANT/SAFEARRAY** | 오토메이션 표준 타입: 길이 프리픽스 유니코드 문자열, 만능 타입, 배열 | IDL 파라미터 전반 |

## 4. 핵심 기술 ③ ? 스크립트 엔진 계층 (이 프로젝트의 심장)

```
화면 .scn 내부의 <SCRIPT> (JScript, ES3 수준)
      ↓ 실행
MS Script Control (msscript.ocx)  ← COleDispatchDriver로 래핑 (ScriptControl.h)
      ↓ 내부적으로
Windows Active Scripting (IActiveScript + JScript.dll 엔진)
      ↓ 전역객체 주입 (AddObject)
_ScriptFunction (= CScriptFunction, IDispatch)  ← 내장함수 340개
      ↓ 위임
IIztScreenAPI / IIztPlatformAPI (IztScreen.dll 등 형제 DLL, 소스 없음)
```

알아야 할 배경:

1. **Active Scripting**: Windows의 표준 스크립트 호스팅 규약(1996~). 호스트 앱이 `IActiveScript`로 JScript/VBScript 엔진을 로드하고, `AddNamedItem`으로 자기 객체를 전역에 주입하는 구조. IE의 JavaScript, ASP, WSH가 모두 이 방식입니다.
2. **MS Script Control**(`msscript.ocx`): Active Scripting을 더 쉽게 쓰도록 감싼 컨트롤. [ScriptControl.h](IztScript/ScriptControl.h)가 `#import "msscript.ocx"`로 이를 사용 ? 즉 **엔진을 직접 만들지 않고 Windows 내장 JScript를 빌려 씁니다.**
3. **JScript는 ES3 수준**: `let`, 화살표 함수, JSON 객체 없음. 화면 스크립트([Config/CommonFunction*.xml](Config/), `.scn` 내부)를 읽을 때 1999년식 JavaScript 문법을 기준으로 봐야 합니다.
4. **전역객체 패턴**: 스크립트에서 `Alert(...)`, `System.xxx`, `Global.Set(...)`처럼 보이는 모든 것은 사실 주입된 COM 객체의 IDispatch 호출입니다. `SystemInfo`/`GlobalData` 등 5종은 IDL에 메서드가 비어 있는데, 이는 **`IDispatch::GetIDsOfNames`를 동적으로 처리하는 Property Bag**(임의 키-값 저장소)이기 때문입니다.

## 5. 핵심 기술 ④ ? XML 메타데이터 화면 프레임워크 (로우코드)

업무 화면은 C++가 아니라 **독자 XML 포맷 + 내장 스크립트**로 개발됩니다. 요즘 용어로 "로우코드 플랫폼"입니다.

| 확장자 | 역할 | 구조 |
|---|---|---|
| `.scn` | 화면 정의 | `<SCREEN><BODY ScreenNo=...>` + 컨트롤 트리 + `<SCRIPT>`(JScript) |
| `.frm` | 프레임(외곽 레이아웃) | `<FRAME><TOP><PANE><CONTROL CType="Panel">` ? [KBFrame.frm](Solution/System/Frame/) |
| `.trn` | 거래 전문 매핑 | `<TRANSACTION TranClass=... SvcCode=...><INPUT><Fld id= pos= len=>` |
| `.prn` | 통장/장표 인자 화면 | `CustomClass="PassbookScreen"` |
| `.act` | 사용자 컨트롤 → ProgID 등록 | 1줄짜리 UTF-16 매핑 |
| `.dat` (Code/) | 공통코드 테이블 | EUC-KR INI 형식 `[ALL]` `코드=라벨` |

- 개발 도구는 [iWorks/PowerDev.exe](iWorks/) / `nGiantDev.exe`(화면 디자이너)이며, 운영 런타임은 `nGiantWorks2.exe`/`PowerWorks.exe`입니다.

## 6. 배포/업데이트 아키텍처 (금융단말 특유의 구조)

은행 단말 수천 대에 설치본을 유지하는 **CRC 기반 델타 자동배포** 체계입니다.

```
Config.xml (Dev/Test/Real 환경 선택, 현재 start="DEV")
   ↓
Bin\IZTnGiantAgent2.exe (부트스트랩 에이전트)
   ↓ IztnGiant.xml 매니페스트 → 서버(fadapd.kbstar.com)와 버전 비교

   ↓ CRC 불일치 파일만 다운로드
Config / Code / Solution / Image / Device / iWorks 폴더 채움
   ↓
PWS.exe → 단말 본체 기동, SMUpdate2.exe는 에이전트 자신을 갱신
```

- 배경 지식: 이런 구조에서는 **git 같은 형상관리가 아니라 매니페스트 XML이 "버전의 진실"** 입니다. 어떤 파일이 배포 대상인지, 어느 환경(운영/개발/TheK)용인지는 `IztnGiant.xml` vs `IztnGiantDev.xml`, `version-works.xml` vs `version-dev.xml` 쌍을 비교해 판단합니다.

## 10. 보안/암호화 (금융 규제 배경)

- **문서 DRM** ? `DSCSDacEncryptFile` API (파일을 사내 DRM으로 암호화)
- 저널 `.mdb`도 암호화 저장, `Bin\key.xml`이 키 관련 설정

분석 시 함의: **데이터 파일을 열어봤는데 깨져 보이면 인코딩 문제가 아니라 암호화일 수 있음**을 구분해야 합니다.

## 11. 문자 인코딩 ? EUC-KR/CP949와 MBCS (분석 실무의 최대 함정)

- 이 프로젝트의 소스·설정·데이터는 대부분 **EUC-KR(CP949)** 저장입니다. UTF-8로 읽으면 주석이 `????`로 깨집니다. VSCode "Reopen with Encoding → Korean(EUC-KR)"로 열어야 합니다.
- C++ 빌드도 **MBCS**(멀티바이트) 설정입니다. 유니코드(`wchar_t`) 빌드가 아니므로 `CString`이 char 기반이며, 한글 1자=2바이트입니다. `SystemByteLength` 같은 API가 존재하는 이유(전문 필드 길이는 바이트 단위)이기도 합니다.
- 단, COM 경계의 `BSTR`은 항상 UTF-16이므로 **내부(MBCS) ↔ COM(유니코드) 변환이 코드 전반에 깔려 있음**을 전제로 읽어야 합니다. 일부 파일(`.act`)은 UTF-16 저장입니다.

## 12. 빌드/개발 환경

- [IztScript.sln](IztScript/IztScript.sln)+`.vcproj`는 **VS.NET 2003(VC7.1)** 시절 원본, [IztScript.vcxproj](IztScript/IztScript.vcxproj)는 **VS2015(v140 툴셋)** 로 마이그레이션된 것 ? 20년간 컴파일러만 올려온 전형적 레거시입니다. 런타임도 `msvcp140.dll`+VB6 런타임이 공존합니다.
- **이 디렉터리 단독으로는 빌드 불가**: `ScriptFunction.h`가 `..\..\IztUtil\Utility.h`를 참조하고, 링크는 [iWorks/Lib/](iWorks/Lib/)의 형제 프로젝트 임포트 라이브러리(`IztScreen.lib`, `IztTran.lib`, `ToolkitPro1710vc140U.lib` 등)에 의존합니다. 즉 원래는 `IztUtil/IztScreen/IztTran/...`이 나란히 있는 멀티 프로젝트 소스 트리의 한 조각입니다.
- 구현 패턴: `CScriptFunction`의 메서드 대부분이 `m_pScreenAPI`/`m_pPlatformAPI` 인터페이스 포인터로 **위임(delegation)** 합니다. 소스가 없는 형제 DLL의 동작은 이 인터페이스 시그니처와 호출 문맥으로 추정해야 합니다.

## 14. 분석 실무 가이드 (요약 치트시트)

1. **기능의 정본 목록**은 [IztScript.idl](IztScript/IztScript.idl)(계약) + [ScriptFunction.cpp](IztScript/ScriptFunction.cpp)의 `DISP_FUNCTION_ID` 테이블(구현 색인). Function.xml(49개)은 문서화된 일부일 뿐.
2. **업무 로직을 찾을 때**: `Solution\**\*.scn`의 `<SCRIPT>` → `Config\CommonFunction_*.xml` → 내장함수(IztScript.dll) 순으로 내려감.
3. **거래 흐름을 찾을 때**: `.scn`에서 `SetTranID`/`HostTran` 호출 → 같은 이름의 `.trn` 필드 매핑 → MCI 서비스코드.
4. **엔진 동작이 궁금할 때**: IztScript 소스에서 `m_pScreenAPI->...` 호출부까지 추적 가능, 그 너머는 바이너리(`IztScreen.dll` 등)라 인터페이스 시그니처로 추정.
5. **파일이 깨져 보일 때**: ① EUC-KR 인코딩 문제인지 ② 암호화 파일인지 ③ 바이너리(컴파일된 .dat)인지 구분.
6. **연대 추정**: 소스 주석의 `이니셜+날짜`(sms070416 ~ KJM 2026.06.08), IDL의 dispid 증가 순서가 곧 기능 증축의 연표.
7. **환경 구분**: 운영(iWorks/Solution/IztnGiant.xml) vs 개발(iWorksD/SolutionT/IztnGiantDev.xml) 쌍을 항상 의식할 것. 현재 [Config.xml](Config.xml)은 `start="DEV"`.
