## 1. 전제 (결정 필요 사항 1건 포함)

- **타깃 런타임**: 웹 브라우저(SPA) 기준으로 수립하되, 장치 제어가 필수이므로 **"브라우저 UI + 로컬 브리지(Agent)" 하이브리드**를 권장. Electron 단일 앱이라면 Phase 3의 브리지가 IPC로 단순화됨 → **이 결정만 착수 전 확정 필요**
- 변환 단위는 "내장함수 라이브러리"이며, 업무 스크립트(CommonFunction/scn) 변환은 후속 과제로 분리하되 Phase 4에서 호환성을 검증

## 2. Phase 0 ― API 인벤토리 자동화 (1~2일)

1. [IztScript.idl](IztScript/IztScript.idl) 파싱 → **함수 카탈로그 자동 생성** (이름·시그니처·dispid·파라미터 타입)
2. `ScriptFunction.cpp` 구현부와 대조해 실동작 주석 추출 (한글 주석 다수 존재, EUC-KR 변환 필요)
3. 위 사용 빈도 실측치를 조인 → **`docs/api-inventory.md` 우선순위 매트릭스** 산출
4. `GlobalData` 등 5개 데이터 객체 + `Image`·`Device` 하위 메서드 포함

## 3. Phase 1 ― 분류 및 변환 전략 결정 (2~3일)

290개 함수를 4계층으로 분류하고 계층별 전략을 적용:

| 계층 | 예시 | 예상 규모 | 변환 전략 |
|------|------|-----------|-----------|
| **A. 순수 로직** | `Trim`, `HexToDec`, `GetDate`, `GetRGBValue`, `RGB2HtmlColor`, `IndexToString` | ~15% | **순수 JS 재구현** (가장 쉬움, 즉시 착수) |
| **B. UI/화면 제어** | `Alert`, `Popup`, `Message*`, `ScreenOpen/Close`, `CommonButton*`, `Dlg*` | ~45% | **웹 UI 컴포넌트 매핑** (모달, 토스트, 라우팅). 사용 빈도 TOP이 몰려있는 계층 |
| **C. 장치/OS/파일** | `Device.*`(핀패드·통장프린터·즉발기), `ReadFileData`, `WinPExecEx`, `ScreenCapture` | ~25% | **로컬 브리지 경유** ― WebSocket/HTTP로 기존 장치 DLL 재사용하는 Agent 호출 |
| **D. 외부 시스템 연동** | `CallOzViewer*`(Oz리포트), `RequestRpa`, `FTF*`·`*Video*`(화상), `HostTran`(전문) | ~15% | **어댑터 모듈** 별도 설계, 대상 시스템별 후순위 |

## 4. Phase 2 ― 호환 라이브러리 아키텍처 설계 (3~5일)

```
iworks-compat/  (TypeScript)
├─ core/        전역 함수 (Alert, Message, Log, Trace …)  ← 기존 이름 그대로 전역 노출
├─ data/        GlobalData·LocalData·LinkData·SystemInfo·UserInfo (Proxy 기반 K-V)
├─ screen/      ScreenOpen/Close/Popup → SPA 라우터 어댑터
├─ device/      Device.* → 브리지 RPC 스텁
├─ image/       Image.* (Rotate/Cut/Merge는 Canvas, OCR/ICR은 서버 API 위임)
└─ report/      Oz·Excel·RPA·화상 어댑터
```

**핵심 기술 결정 ― 동기→비동기 전환**: 기존 JScript는 `Pass.Value = Device.padRead(...)`처럼 **블로킹 호출**이지만 브라우저 JS는 비동기입니다. 대응:
- 전 함수를 `async` 로 구현하고, 기존 스크립트 이식 시 **자동 `await` 삽입 변환기**(codemod)를 Phase 4에서 제공
- Electron 선택 시 일부는 sync IPC로 원형 유지 가능 (결정 사항과 연동)

## 5. Phase 3 ― 단계별 구현 (우선순위 기반)

| 순서 | 범위 | 산출물 | 예상 |
|------|------|--------|------|
| 3-1 | **A계층 전체 + 데이터 객체 5종** | core/data 모듈 + 단위테스트 | 1주 |
| 3-2 | **B계층 TOP 30** (호출량 80% 커버: Alert/Popup/Message/ScreenOpen …) | screen/ui 모듈 | 2~3주 |
| 3-3 | **C계층 장치 브리지** ― 로컬 Agent(기존 `Device/DLL/*.dll` 래핑) + WebSocket 프로토콜 | device 모듈 + Agent | 3~4주 |
| 3-4 | **B계층 잔여 + D계층 어댑터** (Oz, RPA, 화상 ― 대상 시스템 협의 필요) | report 모듈 | 시스템별 협의 |
| 3-5 | 미사용 함수(빈도 0, 약 200여 개)는 **스텁 + 경고 로그**로 처리 후 요청 시 구현 | 스텁 자동 생성 | 병행 |

## 6. Phase 4 ― 검증 (병행 진행)

1. **골든 테스트**: [Config/CommonFunction.xml](Config/CommonFunction.xml)의 실제 함수(예: `getTime`)를 신규 런타임에서 실행 → 구엔진 결과와 비교
2. **호환성 리포트**: 290개 함수 × (구현됨/스텁/미지원) 대시보드 자동 생성
3. 파일럿 화면 2~3개(.scn)를 선정해 end-to-end 이식 검증
