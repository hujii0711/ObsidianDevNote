운영·모니터링 단계는 "배포된 시스템이 실제 사용자 환경에서 계속 건강하게 동작하도록 지키고, 문제가 발생하면 빠르게 발견·대응하며, 학습한 것을 다음 사이클로 환원하는" 단계입니다.

많은 팀이 "배포하면 끝"이라고 생각하지만, 실제로는 **배포 이후가 진짜 시작**입니다. 사용자가 실제로 쓰는 순간부터 진짜 데이터가 쌓이고, 진짜 문제가 드러납니다. 이 단계의 품질이 곧 **제품의 신뢰성**입니다.

Claude Code 환경에서는 이 단계가 한층 더 중요합니다. 배포 빈도가 높아질수록 모니터링 부담도 커지고, 모든 변경의 영향을 사람이 일일이 추적하기 어려워집니다. AI 서브에이전트가 1차 감시자/분석가 역할을 맡으면 그 부담을 크게 줄일 수 있습니다.

## 운영·모니터링 단계의 구체적 작업

### 1. 관찰 가능성(Observability) 구축

"문제가 있는지 모르는" 상태가 가장 위험합니다. 시스템 내부 상태를 외부에서 알 수 있도록 만드는 것이 출발점입니다.

**관찰 가능성의 3대 축**:

- **메트릭(Metrics)**: 수치 데이터, 시계열
    
    - 인프라: CPU, 메모리, 디스크, 네트워크
    - 애플리케이션: 요청 수, 응답 시간, 에러율
    - 비즈니스: 가입 수, 결제 수, 활성 사용자
    - 도구: Prometheus, Datadog, CloudWatch, New Relic
- **로그(Logs)**: 이벤트의 시간순 기록
    
    - 구조화된 로그 (JSON 형식 권장)
    - 로그 레벨 (debug/info/warn/error)
    - 상관 관계 ID(correlation ID)로 요청 추적
    - 도구: Datadog Logs, Loki, ELK, CloudWatch Logs
- **트레이스(Traces)**: 분산 시스템에서 요청의 흐름 추적
    
    - 마이크로서비스에서 특히 중요
    - 어느 서비스에서 얼마나 시간이 걸렸는지
    - 도구: Jaeger, Tempo, Datadog APM, OpenTelemetry

추가로 **이벤트(Events)** 와 **프로파일링(Profiling)** 도 활용합니다.

### 2. 핵심 메트릭 정의 (Key Metrics)

모든 걸 모니터링하면 결국 아무것도 못 봅니다. 우선순위가 필요합니다.

**4 Golden Signals** (Google SRE):

- **Latency**: 응답 시간 (p50, p95, p99)
- **Traffic**: 요청량
- **Errors**: 에러율
- **Saturation**: 자원 포화도

**RED 메트릭** (마이크로서비스 친화):

- **Rate**: 초당 요청 수
- **Errors**: 에러 비율
- **Duration**: 응답 시간 분포

**USE 메트릭** (자원 중심):

- **Utilization**: 사용률
- **Saturation**: 대기열/포화도
- **Errors**: 에러 수

**비즈니스 메트릭**도 함께:

- DAU/MAU
- 전환율
- 결제 성공률
- 핵심 기능 사용률

### 3. SLO/SLI/SLA 정의

"시스템이 잘 돌고 있다"의 기준을 명시적으로 정합니다.

- **SLI(Service Level Indicator)**: 측정 가능한 지표
    - 예: "성공 요청 / 전체 요청"
- **SLO(Service Level Objective)**: 목표 수치
    - 예: "30일간 가용성 99.9%"
- **SLA(Service Level Agreement)**: 외부와의 계약
    - 예: "월간 가용성 99.5% 미달 시 환불"

**에러 예산(Error Budget)**:

- 100% - SLO = 허용되는 실패량
- 예산 소진 시: 새 기능보다 안정화에 집중
- 예산 여유 있을 때: 더 빠른 실험/배포 가능

이 개념이 없으면 "0% 다운타임"이라는 비현실적 목표를 추구하다 번아웃됩니다.

### 4. 알림 체계 (Alerting)

알림은 "사람이 행동해야 할 때만" 와야 합니다.

**알림 설계 원칙**:

- **증상 기반 알림**: 원인이 아니라 사용자에게 보이는 문제로
    - ❌ "CPU 90% 초과" → ✅ "p95 응답 시간 SLO 초과"
- **명확한 액션**: 알림 받은 사람이 무엇을 해야 하는지 분명
- **심각도 분리**: critical / warning / info
- **알림 채널 분리**:
    - Critical: PagerDuty/OpsGenie + SMS/전화
    - Warning: Slack 전용 채널
    - Info: 대시보드만
- **알림 피로도(Alert Fatigue) 경계**: 무시되는 알림은 알림이 아닙니다
- **억제(Suppression) 규칙**: 점검 시간, 알려진 이슈는 자동 억제
- **에스컬레이션**: N분 응답 없으면 다음 사람에게

**좋은 알림의 조건**:

- 실제 문제를 나타내는가
- 자동으로 해결되지 않는가
- 사람의 즉시 조치가 필요한가
- 충분한 컨텍스트(링크, 대시보드, 런북)가 함께 오는가

### 5. 대시보드 (Dashboards)

상시 모니터링과 사후 분석을 위한 시각화입니다.

**대시보드 종류**:

- **개요(Overview)**: 시스템 전체 건강 상태, 한 화면
- **서비스별 상세**: 각 서비스의 상세 메트릭
- **비즈니스 대시보드**: 비기술 인원도 볼 수 있는 KPI
- **인시던트 대시보드**: 장애 대응 시 필요한 정보 집중

**좋은 대시보드 원칙**:

- 한 화면에 너무 많이 넣지 않기
- 가장 중요한 것을 위에/크게
- 일관된 시간 범위, 일관된 색상 의미
- "정상"이 한눈에 보이게
- 클릭으로 드릴다운 가능

### 6. 인시던트 대응 (Incident Response)

문제가 발생했을 때의 체계가 곧 신뢰성입니다.

**인시던트 라이프사이클**:

1. **감지(Detect)**: 자동 알림 또는 사용자 신고
2. **분류(Triage)**: 심각도, 영향 범위 판단
3. **선언(Declare)**: 인시던트 채널 개설, 담당자 지정
4. **완화(Mitigate)**: 영향 최소화 (롤백, 트래픽 차단 등) — **근본 해결 전**
5. **해결(Resolve)**: 근본 원인 수정
6. **회고(Postmortem)**: 학습 및 재발 방지

**역할 분담** (큰 인시던트):

- **Incident Commander**: 전체 지휘, 의사결정
- **Tech Lead**: 기술적 해결 주도
- **Communications**: 내부/외부 커뮤니케이션
- **Scribe**: 타임라인 기록

**도구**:

- 인시던트 관리: PagerDuty, Incident.io, FireHydrant, Rootly
- 협업: Slack, Zoom, Google Docs
- 상태 페이지: Statuspage, Instatus, Better Stack

### 7. 런북(Runbook) & 플레이북(Playbook) 작성

알려진 문제에 대한 대응 절차를 문서화합니다.

**런북에 들어갈 내용**:

- 증상
- 원인 추정
- 확인 명령어/대시보드
- 대응 절차 (단계별)
- 에스컬레이션 기준
- 관련 링크

**플레이북**: 더 큰 범위의 시나리오별 가이드 (예: "DB 장애 시", "DDoS 공격 시")

알림에 런북 링크를 함께 넣어두면, 새벽에 호출된 엔지니어도 빠르게 대응할 수 있습니다.

### 8. 로그 관리

- **구조화된 로깅**: JSON 형식 권장
    
    ```json
    {"level":"error","msg":"payment failed","user_id":"u123","order_id":"o456","trace_id":"abc"}
    ```
    
- **상관 관계 ID**: 한 요청을 여러 서비스에서 추적 가능
- **로그 레벨 관리**: 프로덕션은 info 이상, debug는 임시
- **민감 정보 필터링**: 비밀번호, 토큰, 개인정보 절대 로그에 X
- **보관 정책**: 비용 균형 (예: 7일 핫, 30일 콜드, 1년 아카이브)
- **검색 최적화**: 자주 쓰는 필드 인덱싱

### 9. 성능 모니터링 (Performance Monitoring)

- **APM(Application Performance Monitoring)**: 요청 단위 성능 추적
- **느린 쿼리(Slow Query) 추적**: DB 병목
- **N+1 쿼리 감지**
- **외부 API 응답 시간**
- **프론트엔드 성능**: Core Web Vitals (LCP, FID, CLS)
- **번들 사이즈 추적**: 시간에 따른 변화

**도구**: Datadog APM, New Relic, Sentry Performance, Lighthouse CI

### 10. 사용자 경험 모니터링 (RUM / Synthetic)

- **RUM(Real User Monitoring)**: 실제 사용자 환경에서의 성능
    - 페이지 로드 시간
    - JS 에러
    - 사용자 환경별 차이 (브라우저, 디바이스, 지역)
- **합성 모니터링(Synthetic Monitoring)**: 가짜 사용자가 주기적으로 테스트
    - 핵심 사용자 여정 자동 실행
    - 다운타임 즉시 감지

**도구**: Datadog RUM, Sentry, Checkly, Pingdom

### 11. 보안 모니터링 (Security Monitoring)

- **인증/인가 실패율 모니터링**
- **비정상 트래픽 패턴**: 갑작스러운 요청 증가, 봇
- **시크릿 노출 감지**: 로그, 응답에 시크릿이 흘러나가는지
- **의존성 취약점 알림**: Snyk, Dependabot
- **WAF/DDoS 알림**: Cloudflare, AWS WAF
- **감사 로그(Audit Log)**: 누가 무엇을 했는지

### 12. 비용 모니터링 (Cost Monitoring)

- **일일/월간 비용 추적**
- **예상 초과 시 알림**
- **서비스별 비용 분해**
- **사용량 이상치 감지** (예: 갑자기 S3 트래픽 폭증)
- **태깅(Tagging)**: 팀/프로젝트별 비용 분리
- **사용하지 않는 리소스 정리**

**도구**: AWS Cost Explorer, GCP Billing, Vantage, Infracost

### 13. 데이터 백업 & 재해 복구 (DR)

- **백업 정책**:
    - 빈도 (예: 일 1회 + 트랜잭션 로그 5분마다)
    - 보관 기간
    - 다른 리전/계정에 복제
- **백업 검증**: 정기적으로 복원 테스트 (백업이 없는 것보다, 못 쓰는 백업이 더 위험)
- **RTO(Recovery Time Objective)**: 얼마나 빨리 복구해야 하는가
- **RPO(Recovery Point Objective)**: 데이터를 얼마나 잃어도 되는가
- **DR 훈련(Game Day)**: 정기적으로 재해 시나리오 연습

### 14. 용량 계획 (Capacity Planning)

- **트렌드 분석**: 트래픽이 어떻게 증가하는가
- **포화점 예측**: 언제 자원이 부족해질 것인가
- **사전 확장**: 임계점 도달 전 확장
- **자동 스케일링**: 가능한 곳은 자동화
- **부하 테스트**: 정기적으로 한계 확인

### 15. 사용자 피드백 수집

기술 메트릭만으로는 부족합니다. 사용자의 실제 경험을 들어야 합니다.

- **인앱 피드백**: 별점, 신고 기능
- **고객 지원 티켓 분석**: 어떤 문제가 자주 오는가
- **NPS/CSAT 조사**
- **사용자 인터뷰**
- **세션 리플레이**: FullStory, LogRocket, Hotjar
- **사용자 행동 분석**: PostHog, Mixpanel, Amplitude

### 16. 데이터 기반 학습 & 환원

운영의 진짜 가치는 **다음 사이클로의 학습**입니다.

- **주간/월간 리뷰**: 메트릭 트렌드, 인시던트 요약
- **포스트모템 라이브러리**: 학습 사항 축적
- **개선 백로그**: 운영에서 발견한 이슈를 기획/개발로 환원
- **A/B 테스트 결과 분석**
- **회고(Retrospective)**: 프로세스 자체 개선

### 17. On-Call & 운영 부담 관리

사람이 무한정 일할 수 없습니다.

- **온콜 로테이션**: 공평하게 분배
- **온콜 보상**: 시간, 금전, 또는 휴가
- **온콜 부담 측정**: 페이지 수, 야간 호출 빈도
- **부담 줄이기**: 가짜 알림 제거, 자동화 확대
- **번아웃 방지**: 인시던트 후 회복 시간

### 18. 컴플라이언스 & 감사

산업/지역에 따라 추가 요구사항:

- **GDPR/개인정보보호법**: 데이터 처리 로그, 삭제 요청 처리
- **PCI-DSS** (결제): 카드 정보 처리 감사
- **HIPAA** (의료): 의료 정보 접근 로그
- **SOC 2 / ISO 27001**: 보안 감사

## 서브에이전트 활용 방안

운영·모니터링 단계는 서브에이전트 활용 가치가 가장 큰 영역 중 하나입니다. **24/7 감시**, **반복적 분석**, **빠른 1차 트리아지(triage)** 가 필요한데, 사람의 시간으로는 한계가 있기 때문입니다.

### 패턴 1: 메트릭 이상 탐지 분석가 (Metric Anomaly Analyst)

**역할**: "주기적으로 메트릭을 분석하고 이상치 보고"

입력:

- 최근 N시간 메트릭 데이터
- 기준선(baseline) 데이터
- SLO 정의

출력:

- 정상에서 벗어난 메트릭 목록
- 각 이상치의 심각도
- 가능한 원인 후보
- 추가 확인할 메트릭 추천

**효과**: 사람이 대시보드를 계속 쳐다보지 않아도 이상 징후를 놓치지 않습니다.

### 패턴 2: 로그 분석가 (Log Analyzer)

**역할**: "대량 로그에서 패턴/이상 식별"

입력:

- 시간 범위 로그
- 특정 사용자/요청 ID (선택)

출력:

- 새로 등장한 에러 메시지
- 에러 빈도 증가 패턴
- 의심스러운 트래픽 패턴
- 가장 자주 발생한 에러 Top 10

**효과**: 로그 수백만 줄을 사람이 다 볼 수 없습니다. AI가 요약해서 사람의 주의를 어디로 돌려야 할지 알려줍니다.

### 패턴 3: 인시던트 트리아지 보조자 (Incident Triage Assistant)

**역할**: "알림 발생 시 1차 분석 및 컨텍스트 수집"

자동 트리거: 알림 발생 시 입력:

- 알림 내용
- 최근 배포 이력
- 관련 메트릭/로그
- 유사 과거 인시던트

출력:

- 가능성 높은 원인 후보 Top 3 (확신도 함께)
- 영향 범위 추정
- 권장 즉시 조치 (런북 링크 포함)
- 비슷한 과거 인시던트 링크
- 깨우셔야 할 사람 추천

**효과**: 새벽 3시에 깨어난 엔지니어가 5분 안에 상황 파악. 골든 타임을 확보합니다.

### 패턴 4: 런북 추천자 (Runbook Recommender)

**역할**: "현재 상황에 맞는 런북 찾기"

알림과 컨텍스트를 받아 가장 적합한 런북을 찾아 제시. 없으면 비슷한 인시던트를 참조하라고 안내.

### 패턴 5: 인시던트 타임라인 작성자 (Incident Timeline Writer)

**역할**: "인시던트 진행 중 자동으로 타임라인 기록"

채널 메시지, 배포 이벤트, 알림을 모아 시간순 타임라인을 생성. 포스트모템 작성 시 이 자료를 그대로 활용 가능.

### 패턴 6: 포스트모템 보조자 (Postmortem Assistant)

**역할**: "인시던트 후 포스트모템 초안 작성"

입력:

- 인시던트 타임라인
- 영향 메트릭
- 채팅 로그
- 관련 변경/배포

출력:

- 표준 템플릿에 맞춘 초안
    - 요약
    - 타임라인
    - 근본 원인 (5 Whys 적용)
    - 영향 분석
    - 잘된 점 / 개선할 점
    - 액션 아이템

**원칙**: 블레임리스 톤 강제, 사람 탓 표현 자동 필터링.

### 패턴 7: 보안 모니터링 분석가 (Security Monitoring Analyst)

**역할**: "보안 관련 이상 징후 감시"

체크:

- 비정상 로그인 패턴 (지리/시간/빈도)
- 권한 상승 시도
- 의심스러운 API 호출
- 새로 공개된 취약점이 우리 의존성에 영향 있는지
- 시크릿 누출 의심

출력: 위협 등급 + 권장 조치

### 패턴 8: 비용 최적화 분석가 (Cost Optimization Analyst)

**역할**: "주기적으로 비용 분석 및 절감 기회 식별"

입력:

- 최근 N개월 비용 데이터
- 리소스 사용량
- 트래픽 패턴

출력:

- 비용 증가 원인 분석
- 사용하지 않는 리소스 목록
- 다운사이징 가능한 리소스
- 예약 인스턴스/약정 할인 추천
- 예상 절감액

### 패턴 9: 성능 회귀 탐지자 (Performance Regression Detector)

**역할**: "배포 전후 성능 비교, 회귀 탐지"

배포 이벤트 후 자동 실행:

- 핵심 엔드포인트의 응답 시간 비교
- 에러율 비교
- 자원 사용량 비교
- 통계적으로 유의미한 변화 식별

출력: 회귀 발견 시 알림 + 의심 PR 추정

### 패턴 10: 사용자 피드백 분류자 (User Feedback Classifier)

**역할**: "유입되는 피드백/티켓을 분류·요약"

입력:

- 최근 고객 지원 티켓
- 인앱 피드백
- 앱스토어 리뷰
- 소셜 미디어 언급

출력:

- 카테고리별 분류 (버그/기능 요청/사용성 문제)
- 빈도순 정렬
- 신규 발견 이슈 vs 알려진 이슈
- 우선순위 추천 (영향도 × 빈도)

**효과**: 매주 수백 건의 피드백을 사람이 다 읽을 수 없습니다. AI가 요약해서 핵심을 보여줍니다.

### 패턴 11: 용량 예측가 (Capacity Forecaster)

**역할**: "트래픽 추세 기반으로 확장 시점 예측"

입력:

- 최근 트래픽/자원 사용 추세
- 계절성 패턴
- 예정된 마케팅 이벤트

출력:

- N주 후 예상 자원 사용량
- 임계점 도달 예상 시점
- 사전 확장 추천

### 패턴 12: 주간 운영 리포트 작성자 (Weekly Ops Report Writer)

**역할**: "한 주의 운영 데이터를 종합한 리포트 작성"

자동 매주 실행:

- 가용성, SLO 달성률
- 인시던트 요약
- 성능 트렌드
- 비용 트렌드
- 주요 사용자 피드백
- 다음 주 주의 사항

출력: 팀/경영진용 리포트

**효과**: 매주 리포트 작성 시간 절약 + 일관된 형식.

### 패턴 13: 의존성 건강 감시자 (Dependency Health Monitor)

**역할**: "외부 서비스/라이브러리 상태 추적"

- 외부 API의 가동 상태 및 응답 시간
- 사용 중인 라이브러리의 새 버전/취약점
- 라이선스 변경
- EOL(End of Life) 다가오는 의존성

### 패턴 14: 백업 검증자 (Backup Verifier)

**역할**: "백업이 실제로 복원 가능한지 정기 검증"

- 백업 파일 존재 확인
- 복원 가능성 테스트 (테스트 환경에)
- 백업 크기 추세 분석
- 누락 시 즉시 알림

```
[상시 백그라운드 실행]
├─ Metric Anomaly Analyst (5분마다)
├─ Log Analyzer (15분마다)
├─ Security Monitoring Analyst (실시간)
├─ Performance Regression Detector (배포 후)
└─ Backup Verifier (일 1회)

[알림 발생 시]

   → Slack 채널에 1차 분석 게시
2. Runbook Recommender가 관련 런북 첨부
3. 사람이 인시던트 선언
4. Incident Timeline Writer가 자동 기록 시작
5. 사람들이 대응 (AI는 보조)
6. 인시던트 해결
7. Postmortem Assistant가 초안 작성
8. 사람이 검토/완성

[주기적 분석]
├─ User Feedback Classifier (주 1회)
├─ Cost Optimization Analyst (월 1회)
├─ Capacity Forecaster (주 1회)
├─ Dependency Health Monitor (일 1회)
└─ Weekly Ops Report Writer (주 1회)
```

### 서브에이전트 운영 팁 (운영 단계 특화)

1. **`.claude/agents/ops/` 디렉토리 구조**:
    
    ```
    .claude/agents/ops/
      metric-anomaly-analyst.md
      log-analyzer.md
      incident-triage-assistant.md
      runbook-recommender.md
      incident-timeline-writer.md
      postmortem-assistant.md
      security-monitoring-analyst.md
      cost-optimization-analyst.md
      performance-regression-detector.md
      user-feedback-classifier.md
      capacity-forecaster.md
      weekly-ops-report-writer.md
      dependency-health-monitor.md
      backup-verifier.md
    ```
    
2. **AI는 분석·추천, 결정·실행은 사람**:
    
    - 자동 롤백 같은 자동화는 명확한 규칙으로만 (AI 판단 X)
    - 인시던트 의사결정은 반드시 사람
    - 고객 커뮤니케이션은 사람
3. **컨텍스트로 줄 자료**:
    
    - SLO/SLA 정의
    - 정상 메트릭 기준선
    - 과거 인시던트 데이터베이스
    - 런북 라이브러리
    - 회사 가치 / 커뮤니케이션 가이드
4. **거짓 양성(false positive) 관리**:
    
    - AI가 너무 많이 알리면 결국 무시당함
    - 신뢰도 점수 함께 출력
    - 사람 피드백으로 학습 (어떤 알림이 가짜였는지)
5. **출력은 행동 가능하게**:
    
    - ❌ "에러율이 올라갔다"
    - ✅ "에러율 5분간 3.2% 증가, 주된 원인은 /api/payments의 timeout, 권장 조치: ① 결제 게이트웨이 상태 확인 (대시보드 링크) ② 이전 30분 배포 확인 ③ 영향 받는 사용자 약 1,200명 추정"
6. **사람 검토 필수 영역**:
    
    - 외부에 나가는 모든 커뮤니케이션 (상태 페이지, 사용자 공지)
    - 포스트모템 최종본
    - 인시던트 심각도 판정
    - 비즈니스 의사결정
7. **AI의 한계 인식**:
    
    - 처음 보는 장애 패턴 약함
    - 비즈니스 영향 무게 판단 어려움
    - 정치적/조직적 맥락 모름
    - 새로운 위협/공격 패턴 못 잡을 수 있음

## 한 가지 조언

운영·모니터링 단계에서 가장 중요한 마인드셋은 **"실패는 피할 수 없다, 빨리 발견하고 빨리 회복하는 것이 진짜 신뢰성"** 입니다.

흔한 함정:

- **완벽주의**: "다운타임 0%"를 목표로 하면 아무것도 못 합니다. SLO를 현실적으로.
- **사후 대응**: 문제 터지고 나서 모니터링 추가는 늦습니다. 출시 전에 셋업.
- **알림 과다**: 알림이 너무 많으면 진짜를 놓칩니다. 정기적으로 정리.
- **모니터링만 보고 사용자 안 보기**: 메트릭이 정상인데 사용자는 불만일 수 있습니다.
- **사람 탓 문화**: 블레임리스가 아니면 사람들이 실수를 숨기게 됩니다.

Claude Code 환경에서 특히 강조하고 싶은 점:

1. **배포 빈도 ↑ = 모니터링 부담 ↑**: AI로 코드 빠르게 만들면 운영 부담도 비례해서 늘어납니다. 자동화 안 하면 사람이 버티지 못합니다.
    
2. **AI 1차 감시자의 가치**: 사람이 24시간 대시보드를 볼 수 없지만, AI 서브에이전트는 가능합니다. 다만 결정은 사람이.
    
3. **학습 사이클이 닫혀야 함**: 운영에서 배운 것이 다음 기획으로 들어가야 합니다. 그렇지 않으면 같은 문제가 반복됩니다.
    
4. **인시던트는 자산**: 잘 분석된 인시던트는 시스템을 더 강하게 만듭니다. 포스트모템을 진지하게.
    

운영은 **개발의 마지막이 아니라, 다음 사이클의 시작**입니다. 사용자에게 도달한 코드에서 얻는 데이터, 메트릭, 피드백, 인시던트가 다음 기획·설계·개발의 입력이 됩니다. 이 루프가 잘 돌면 제품과 팀이 함께 성장하고, 안 돌면 같은 자리를 계속 맴돕니다.

진행 중인 프로젝트의 인프라(클라우드, 서비스 종류, 트래픽 규모)와 현재 모니터링 도구를 알려주시면, 그에 맞는 구체적인 SLO 정의 예시, 알림 설정, 서브에이전트 정의 파일까지 작성해드릴 수 있습니다.
