# 7. 배포 단계 상세 가이드

Claude Code를 활용한 앱 개발 — 배포 단계에서 해야 할 작업을 파트별로 정리합니다.

---

## 파트 1. 배포 전략 수립

### 배포 환경 구성 `필수`

프로덕션 배포 전에 반드시 세 환경을 분리해서 운영합니다.

```
개발(Development)
   ↓ 기능 완성 후
스테이징(Staging)     ← 프로덕션과 동일한 환경에서 최종 검증
   ↓ 검증 완료 후
프로덕션(Production)  ← 실제 서비스
```

```bash
claude -p "
개발/스테이징/프로덕션 환경별로
환경변수, DB, 외부 서비스를 분리하는 설정 구조를 잡아줘.
각 환경별 .env 파일 템플릿도 함께 작성해줘
"
```

### 배포 방식 결정 `필수`

서비스 규모와 팀 상황에 맞는 배포 방식을 선택합니다.

|방식|설명|적합한 경우|
|---|---|---|
|Rolling 배포|인스턴스를 순차적으로 교체|일반적인 웹 서비스|
|Blue/Green 배포|구버전·신버전 동시 운영 후 트래픽 전환|다운타임 허용 불가|
|Canary 배포|일부 트래픽만 신버전으로 점진적 전환|대규모 서비스, 리스크 최소화|
|Recreate 배포|구버전 종료 후 신버전 시작|소규모, 다운타임 허용 가능|

```bash
claude -p "
우리 서비스 규모와 인프라 구성을 고려해서
적합한 배포 방식을 추천하고 설정 방법을 알려줘
"
```

### 롤백 계획 수립 `필수`

배포 실패 시 즉시 이전 버전으로 되돌릴 수 있는 계획을 미리 준비합니다.

```bash
claude -p "
배포 실패 시 5분 이내 롤백할 수 있는 절차와
자동 롤백 스크립트를 작성해줘.
DB 마이그레이션 롤백 방법도 포함해줘
"
```

## 파트 2. CI/CD 파이프라인 구성

### 전체 파이프라인 흐름 `필수`

```
코드 푸시 / PR 머지
      ↓
CI 단계 (자동)
  ├── 린트 검사
  ├── 단위 테스트
  ├── 통합 테스트
  ├── 빌드
  └── 보안 스캔
      ↓
CD 단계 (자동 또는 수동 승인)
  ├── 스테이징 배포
  ├── 스테이징 E2E 테스트
  ├── 배포 승인 (수동)
  └── 프로덕션 배포
```

### GitHub Actions 파이프라인 구성

```bash
claude -p "
다음 조건의 GitHub Actions 워크플로우 파일을 작성해줘.

트리거:
- PR 생성/업데이트 시 CI 실행
- main 브랜치 머지 시 스테이징 자동 배포
- 수동 승인 후 프로덕션 배포

CI 단계:
- Node.js 20 환경
- 의존성 캐싱 적용
- 린트 → 테스트 → 빌드 순서로 실행
- 실패 시 Slack 알림

CD 단계:
- Docker 이미지 빌드 및 레지스트리 푸시
- 스테이징 서버 배포
- 헬스체크 통과 시 프로덕션 배포 승인 요청
"
```

### 환경별 시크릿 관리 `필수`

```bash
# GitHub Secrets 등록 목록 정리
claude -p "
이 프로젝트의 CI/CD에 필요한 GitHub Secrets 목록을 정리해줘.
각 시크릿의 용도, 값 형식, 등록 방법을 포함해줘.

환경: AWS, PostgreSQL, Slack 웹훅 사용
"
```

## 파트 5. DB 마이그레이션

### 마이그레이션 배포 순서 `필수`

DB 마이그레이션은 반드시 아래 순서를 지킵니다.

```
1. 마이그레이션 파일 사전 검토
2. 프로덕션 DB 백업
3. 마이그레이션 실행 (다운타임 최소화)
4. 앱 서버 배포
5. 마이그레이션 결과 검증
```

```bash
claude -p "
다음 마이그레이션 파일을 검토해줘.

확인 항목:
- 되돌릴 수 없는 변경이 있는가 (컬럼 삭제, 타입 변경)
- 대용량 테이블 변경으로 락이 발생할 수 있는가
- 인덱스 생성으로 인한 성능 저하 구간이 있는가
- 롤백 스크립트가 준비되어 있는가

[마이그레이션 파일 내용 붙여넣기]
"
```

### 무중단 마이그레이션 전략

```bash
claude -p "
다음 DB 변경을 무중단으로 배포하는 방법을 알려줘.

변경 내용: users 테이블에 phone_number 컬럼 추가 (NOT NULL)

단계별 배포 계획을 작성해줘.

"
```

### 배포 직후 모니터링 `필수`

배포 완료 후 최소 30분은 집중적으로 모니터링합니다.

```bash
claude -p "
배포 직후 모니터링해야 할 핵심 지표와
각 지표의 이상 기준을 정리해줘.

모니터링 도구: CloudWatch, Datadog
서비스: NestJS API 서버, PostgreSQL, Redis
"
```

주요 모니터링 지표는 다음과 같습니다.

```
- API 에러율          → 1% 초과 시 즉시 롤백
- 평균 응답 시간      → 배포 전 대비 20% 초과 시 확인
- DB 연결 수          → 최대치 80% 초과 시 확인
- 메모리 사용량       → 85% 초과 시 확인
- CPU 사용량          → 80% 지속 시 확인
- 5xx 에러 로그       → 발생 즉시 확인
```

## 파트 7. 배포 자동화 스크립트 모음

### 전체 배포 파이프라인 스크립트

```bash
# scripts/deploy.sh
#!/bin/bash

set -e  # 오류 발생 시 즉시 중단

ENVIRONMENT=$1        # staging 또는 production
VERSION=$(git rev-parse --short HEAD)
TIMESTAMP=$(date +%Y%m%d-%H%M%S)

echo "=== 배포 시작: $ENVIRONMENT / $VERSION ==="

# 1. 배포 공지
claude -p "
Slack에 배포 시작을 알리는 메시지를 작성해줘.
환경: $ENVIRONMENT
버전: $VERSION
시작 시간: $TIMESTAMP
담당자: $(git config user.name)
"

# 2. 사전 검증
if [ "$ENVIRONMENT" = "production" ]; then
  echo "프로덕션 사전 검증 중..."
  ./scripts/pre-deploy-check.sh
fi

# 3. Docker 이미지 빌드 및 푸시
docker build -t myapp:$VERSION .
docker push registry/myapp:$VERSION

# 4. DB 마이그레이션
echo "DB 마이그레이션 실행 중..."
npx prisma migrate deploy

# 5. 앱 배포
echo "앱 서버 배포 중..."
./scripts/update-ecs-service.sh $ENVIRONMENT $VERSION

# 6. 헬스체크
echo "헬스체크 확인 중..."
./scripts/health-check.sh $ENVIRONMENT

echo "=== 배포 완료: $ENVIRONMENT / $VERSION ==="
```

### 롤백 스크립트

```bash
# scripts/rollback.sh
#!/bin/bash

ENVIRONMENT=$1
PREVIOUS_VERSION=$2

echo "=== 롤백 시작: $ENVIRONMENT → $PREVIOUS_VERSION ==="

claude -p "
롤백 Slack 알림 메시지를 작성해줘.
환경: $ENVIRONMENT
롤백 버전: $PREVIOUS_VERSION
사유: 배포 후 이상 감지
"

# 이전 버전으로 ECS 서비스 롤백
./scripts/update-ecs-service.sh $ENVIRONMENT $PREVIOUS_VERSION

# DB 마이그레이션 롤백 (필요 시)
# npx prisma migrate resolve --rolled-back

echo "=== 롤백 완료 ==="
```

## 파트 8. 서브에이전트로 배포 검증 병렬화

배포 후 검증 작업을 서브에이전트로 병렬 실행합니다.

```bash
# scripts/post-deploy-validation.sh
#!/bin/bash

ENVIRONMENT=$1

echo "=== 배포 후 검증 병렬 실행 ==="

# API 검증 에이전트
claude -p "
역할: API 검증 엔지니어
작업: $ENVIRONMENT 환경의 모든 핵심 API 엔드포인트 응답 확인
기준: 응답 코드 200, 응답 시간 200ms 이하
결과: logs/api-validation.md에 저장
" > logs/api-agent.log 2>&1 &

# 성능 검증 에이전트
claude -p "
역할: 성능 검증 엔지니어
작업: $ENVIRONMENT 환경 부하 테스트 실행
기준: 동시 100명 기준 에러율 1% 이하, 평균 응답 200ms 이하
결과: logs/performance-validation.md에 저장
" > logs/perf-agent.log 2>&1 &

# 로그 분석 에이전트
claude -p "
역할: 로그 분석 엔지니어
작업: 배포 후 10분간 에러 로그 수집 및 분석
기준: 신규 에러 패턴 없음
결과: logs/log-validation.md에 저장
" > logs/log-agent.log 2>&1 &

wait

echo "=== 검증 완료 ==="

# 결과 종합
claude -p "
logs/api-validation.md
logs/performance-validation.md
logs/log-validation.md
를 읽고 배포 성공 여부를 판단해줘.
이상이 있으면 롤백 권고 여부도 포함해줘
"
```

---

> **핵심 포인트**: 배포는 "올리는 것"이 아니라 "안전하게 전환하는 것"입니다. 스테이징 검증, 자동 롤백, 배포 직후 모니터링 세 가지가 갖춰져야 프로덕션 배포를 신뢰할 수 있습니다. Claude Code는 스크립트 작성과 검증 자동화를 도와주지만, 배포 승인과 롤백 결정은 반드시 사람이 내려야 합니다.
