PR(Pull Request) 생성부터 최종 승인 및 병합까지의 전체 과정을 단계별로 상세히 설명해 드리겠습니다.

### 1단계: 작업 브랜치 생성 및 푸시 (준비 단계)
가장 먼저 본인의 로컬 환경에서 새로운 브랜치를 만들고 작업을 완료한 뒤 GitHub 서버로 올립니다.
*   `git checkout -b feature/board-fix` (브랜치 생성)
*   `git add .` / `git commit -m "내용 수정"` (커밋)
*   `git push origin feature/board-fix` (서버로 전송)

### 2단계: PR 생성 (요청 단계)
GitHub 웹사이트에서 `feature` 브랜치의 내용을 `main`에 합쳐달라고 요청서를 작성합니다.
1.  GitHub 저장소 상단의 **[Pull requests]** -> **[New pull request]** 클릭. 이때 PR이 생성된다.(push시가 아님)
2.  어떤 브랜치를 어디로 합칠지 선택(base: `main` <- compare: `feature/board-fix`).
3.  변경 사항의 제목과 내용을 작성하고 **[Create pull request]** 클릭.

### 3단계: 자동화 테스트(CI) 실행 (검증 단계)
우리가 설정한 **GitHub Actions**가 이때 빛을 발합니다.
*   PR이 생성되자마자 GitHub Actions가 자동으로 실행됩니다.
*   코드 빌드, 라이브러리 설치, 테스트 코드가 정상인지 확인합니다.
*   **체크 표시(✅)**가 뜨면 코드상 결함이 없다는 뜻이며, 리뷰어가 안심하고 리뷰를 시작할 수 있습니다.

### 4단계: 코드 리뷰 및 피드백 (검토 단계)
다른 팀원(리뷰어)이 작성된 코드를 확인합니다.
*   **[Files changed]** 탭에서 코드 줄마다 댓글을 달아 수정 제안을 할 수 있습니다.
*   수정이 필요하면 개발자가 다시 코드를 수정해서 푸시합니다. (이때 PR은 자동으로 업데이트됩니다.)
``
### 5단계: 승인 (Approval - 승인 단계)
리뷰어가 모든 코드가 적절하다고 판단하면 승인 절차를 밟습니다.
1.  오른쪽 상단의 **[Review changes]** 버튼 클릭.
2.  **Approve**를 선택하고 "확인했습니다. 병합하세요!" 같은 메시지를 남깁니다.
3.  **[Submit review]**를 누르면 공식적으로 승인 상태가 됩니다.

### 6단계: 병합 (Merge - 완료 단계)
승인이 완료되고 CI 테스트도 통과했다면, 이제 코드를 합칩니다.
1.  PR 하단의 초록색 **[Merge pull request]** 버튼 클릭.
2.  **[Confirm merge]** 클릭.
3.  이제 `feature/board-fix` 브랜치의 내용이 최종적으로 `main` 브랜치에 반영됩니다.

### 7단계: 브랜치 삭제 (정리 단계)
병합이 끝난 브랜치는 더 이상 필요 없으므로 **[Delete branch]** 버튼을 눌러 깔끔하게 정리합니다.

### 요약
개발자는 **"작업 - 푸시 - PR 생성"**을 하고, 관리자/리뷰어는 **"CI 결과 확인 - 코드 리뷰 - 승인"**을 한 뒤, 최종적으로 **"병합"**을 함으로써 안전하게 소스 코드를 통합하게 됩니다._

🎯  PR의 **[Review changes]** 버튼 내에 **Approve(승인)** 옵션이 보이지 않는 데에는 몇 가지 대표적인 이유가 있습니다.

### 1. 본인이 만든 PR인 경우 (가장 흔한 이유)
GitHub에서는 기본적으로 **자신이 생성한 PR을 스스로 승인할 수 없습니다.** 본인이 만든 PR의 경우 [Files changed] 탭에서 `Review changes` 버튼을 눌러도 `Comment` 옵션만 나타나고 `Approve`나 `Request changes`는 활성화되지 않습니다.
*   **해결 방법**: 다른 계정(동료)으로 로그인하여 확인하거나, 본인 프로젝트라면 승인 과정 없이 바로 하단의 `Merge pull request` 버튼을 눌러 병합하면 됩니다.

### 2. 저장소 권한 문제
해당 레포지토리에 대한 **Write(쓰기) 권한**이 없는 경우 리뷰 승인을 할 수 없습니다.
*   **해결 방법**: 레포지토리 관리자가 [Settings] -> [Collaborators]에서 해당 사용자를 초대하거나 권한을 부여해야 합니다.

### 3. 브랜치 보호 규칙(Branch Protection Rules) 미설정
아무런 규칙이 설정되어 있지 않은 개인 레포지토리에서는 굳이 '승인' 절차를 거치지 않아도 바로 병합이 가능하기 때문에, UI상에서 승인 옵션이 덜 강조되거나 생략되어 보일 수 있습니다.
*   **공식적인 '승인' 단계를 강제하고 싶다면**:
    1.  레포지토리의 **[Settings]** 탭으로 이동합니다.
    2.  왼쪽 메뉴에서 **[Code and automation] -> [Branches]**를 클릭합니다.
    3.  `main` 브랜치에 대해 **[Add branch protection rule]**을 클릭합니다.
    4.  **"Require a pull request before merging"**을 체크하고, 그 아래 **"Require approvals"**를 체크합니다.
    5.  이렇게 설정하면 이제 반드시 승인이 있어야만 병합이 가능해지며 승인 메뉴가 활성화됩니다.

### 요약
현재 혼자 테스트 중이시라면 **본인이 만든 PR이라서 승인 버튼이 안 보이는 것**일 확률이 99%입니다. 이 경우 승인 단계 없이 바로 **Merge**를 진행해 보셔도 무방합니다!

설정된 조건(`on:`)에 따라 구체적인 실행 시점이 조금씩 다릅니다. 현재 작성된 `.github/workflows/ci.yml` 코드를 기준으로 설명해 드릴게요.

### 1. `push` (main 브랜치 대상)
*   **실행됨**: `main` 브랜치로 직접 코드를 푸시할 때 실행됩니다.
*   **참고**: 만약 `feature/abc` 같은 다른 브랜치에 푸시한다면, 현재 설정(`branches: [ "main" ]`)상 실행되지 않습니다.

### 2. `Create pull request` (PR 생성)
*   **실행됨**: 다른 브랜치에서 `main` 브랜치로 합쳐달라는 **PR을 생성하는 순간** 바로 실행됩니다.
*   **목적**: 이 코드를 `main`에 합치기 전에, "미리 빌드해보고 테스트해서 안전한지" 검증하기 위함입니다.
*   **업데이트**: PR이 열려 있는 상태에서 해당 브랜치에 추가로 코드를 푸시해도 계속 다시 실행되어 최신 상태를 검증합니다.

### 3. `Merge pull request` (병합 완료)
*   **실행됨**: PR이 승인되어 **Merge(병합) 버튼을 누르는 순간** 다시 한번 실행됩니다.
*   **왜 또 실행되나요?**: GitHub 입장에서는 Merge가 완료되는 것이 결국 `main` 브랜치에 새로운 코드가 **`push`** 된 것과 동일한 이벤트로 간주하기 때문입니다. 최종적으로 합쳐진 `main` 브랜치가 여전히 정상인지 마지막으로 확인하는 과정입니다.

### 요약하자면:
작성하신 워크플로우 설정 덕분에 코드가 이동하는 **모든 주요 길목(푸시, 요청, 합병)**에서 자동으로 검사가 이루어지고 있는 것입니다. 아주 바람직한 CI 설정입니다!_

결론부터 말씀드리면 **PR 요청 시**와 **병합 시** 실행되는 트리거는 서로 다릅니다.

### 1. PR 요청 시 (PR 생성 및 코드 추가 푸시)
*   트리거: **`pull_request:`**
*   작동: `main` 브랜치로 합쳐달라는 요청이 왔을 때, 합쳐지기 전의 상태를 미리 테스트합니다.

### 2. 병합 시 (Merge 완료 시)
*   트리거: **`push:`**
*   작동: PR이 승인되어 `Merge` 버튼을 누르면, 결과적으로 `main` 브랜치에 새로운 코드가 들어오게 됩니다. 이것은 GitHub 입장에서 `main` 브랜치에 대한 **`push` 이벤트**로 간주됩니다.

### 만약 코드에서 하나를 지운다면?

현재 코드에는 두 가지가 모두 적혀 있습니다:
```yaml
on:
  push:           # <- (A) 병합 완료 시 실행되게 함
    branches: [ "main" ]
  pull_request:    # <- (B) PR 요청 시 실행되게 함
    branches: [ "main" ]
```

*   **(B) `pull_request`만 있다면?**: PR을 올렸을 때는 테스트가 돌지만, 정작 **Merge 버튼을 눌러서 합쳐진 후**에는 테스트가 돌지 않습니다.
*   **(A) `push`만 있다면?**: PR을 올렸을 때는 아무 반응이 없다가, **Merge가 완료되어 `main`에 반영된 후**에야 뒤늦게 테스트가 돕니다. (이미 합쳐진 뒤라 만약 에러가 난다면 수습이 늦어지겠죠?)

### 결론
따라서 **PR 요청 시 검증(pull_request)**하고, **최종적으로 합쳐진 결과도 다시 한번 확인(push)**하기 위해 지금처럼 두 가지 트리거를 모두 써주는 것이 가장 안전한 표준 설정입니다!_
