GitHub의 이슈 등록부터 PR 승인까지 전체 워크플로우입니다. 단계별로 정리하면 다음과 같습니다.

**이슈 단계** 이슈를 등록할 때는 제목, 설명, 라벨(bug/feature/enhancement 등), 담당자(Assignee)를 설정합니다. 팀 내에서 우선순위를 협의하고 담당자를 확정하면 개발로 넘어갑니다.

**브랜치 단계** 이슈 번호를 브랜치명에 포함시키는 것이 핵심입니다. 예: `feature/#42-user-login`, `fix/#55-null-pointer`. 이렇게 하면 브랜치와 이슈가 자동으로 연결됩니다.

**PR 생성 단계** PR 본문에 `Closes #42` 또는 `Fixes #42`를 명시하면 머지 시 이슈가 자동으로 닫힙니다. Reviewer는 최소 1명 이상 지정하고, Draft PR로 먼저 올려 피드백을 받는 방식도 많이 사용합니다.

**CI/자동화 단계** GitHub Actions 등으로 빌드, 테스트, 린트가 자동 실행됩니다. 실패하면 수정 후 다시 push — CI가 통과할 때까지 반복합니다.

**리뷰 & 승인 단계** Reviewer가 코드를 검토하고 Comment(의견), Request Changes(수정 요청), Approve(승인) 중 하나를 선택합니다. 변경 요청이 오면 수정 후 재요청, 승인이 완료되면 머지로 진행합니다.

**머지 단계** 머지 방법은 세 가지 중 선택합니다.

- **Merge commit**: 커밋 히스토리를 그대로 보존
- **Squash and merge**: PR의 모든 커밋을 하나로 합쳐 깔끔한 히스토리 유지
- **Rebase and merge**: 선형 히스토리 유지

머지 후 브랜치를 삭제하고, `Closes` 키워드 덕분에 이슈는 자동으로 닫힙니다.
