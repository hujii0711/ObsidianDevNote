
### 1. 개발 단계의 구체적 작업
① 기능을 원자 단위(Atomic Task)로 쪼개어 지시하기
② 명확한 컨텍스트(Reference) 지정 및 첫 프롬프트 던지기
③ AI의 실행 과정 모니터링 및 실시간 개입 (Human-in-the-Loop)
④ 빌드/린트 에러 피드백 및 자가 치유 루프 (Error Iteration)
⑤ 점진적 깃(Git) 커밋 및 세이브포인트 구축

### 2. 브랜치 생성 & 작업 시작

- **이슈 단위 브랜치**: `feature/user-signup`, `fix/login-error`
- **명명 규칙 준수**: 환경 셋업에서 정한 컨벤션
- **베이스 브랜치 최신화**: `git pull origin main` 먼저
- **컨텍스트 정리**: 관련 문서/이슈 다시 읽기

### 3. 브랜치 단위 개발

기능 하나 = 브랜치 하나 = PR 하나 원칙을 지킵니다.

```bash
# 기능 브랜치 생성
git checkout -b feature/user-auth

# 개발 완료 후 커밋
git add .
git commit -m "feat: 유저 로그인 API 구현"

# PR 생성 (MCP 연결 시 Claude Code로 직접 생성 가능)
claude -p "지금 변경사항으로 PR 작성해줘"
```

## 서브에이전트(Sub-agent) 활용 방안

Claude Code의 강력한 기능 중 하나가 서브에이전트입니다. 메인 에이전트가 작업을 진행하면서, **격리된 컨텍스트를 가진 보조 에이전트에게 특정 작업을 위임**할 수 있습니다.

### 1. 왜 서브에이전트를 써야 하는가

- **컨텍스트 분리**: 메인 세션이 무거운 탐색/조사로 컨텍스트 창을 낭비하지 않게 됨
- **전문화**: 역할별로 시스템 프롬프트를 다르게 줘서 특화된 응답을 얻음
- **병렬성**: 독립적인 작업들을 동시에 처리
- **재사용성**: 자주 쓰는 역할을 정의해두고 반복 호출

### 2. 개발 단계에서 유용한 서브에이전트 패턴

#### 1: 코드 탐색 전용 에이전트 (Code Explorer)
**역할**: "이 기능과 관련된 기존 코드를 찾아서 요약 보고"

큰 코드베이스에서 메인 에이전트가 일일이 파일을 열어보면 컨텍스트가 금세 가득 찹니다. 탐색 전용 서브에이전트에게 "결제 로직과 관련된 모든 파일과 핵심 함수를 정리해줘"라고 위임하면, 결과 요약만 메인으로 돌아옵니다.

**예시 시나리오**:
> 메인 에이전트: "주문 환불 기능을 추가해야 해. 먼저 환불 관련 기존 코드를 조사해야 하는데..." → Code Explorer 서브에이전트 호출 → 서브: 결제/주문/환불 관련 파일 목록 + 핵심 함수 시그니처 + 데이터 흐름 요약 반환 → 메인: 요약본만 받아서 깨끗한 컨텍스트로 구현 시작

#### 2: 테스트 작성 전용 에이전트 (Test Writer)
**역할**: "주어진 함수/모듈에 대한 테스트 케이스 작성"

메인이 구현에 집중하고, 테스트 작성은 별도 에이전트에 위임합니다. 시스템 프롬프트에 다음을 박아둡니다:

- 사용 프레임워크 (Vitest/Jest 등)
- 테스트 컨벤션 (AAA 패턴, 명명 규칙)
- 커버해야 할 케이스 종류 (정상/엣지/에러)

#### 3: 코드 리뷰어 에이전트 (Code Reviewer)
**역할**: "이 diff를 시니어 엔지니어 관점에서 비판"

매우 효과적인 패턴입니다. 구현 직후 변경된 코드를 리뷰어 서브에이전트에 넘기면, 생성한 세션과 다른 시각에서 문제점을 찾아냅니다.

시스템 프롬프트 예시:
> "당신은 까다로운 시니어 엔지니어다. 다음 관점에서 비판적으로 리뷰하라: 버그 가능성, 보안 이슈, 성능 문제, 가독성, 컨벤션 일치, 테스트 누락. 칭찬은 생략하고 개선점만 지적하라."

#### 4: 디버거 에이전트 (Debugger)
**역할**: "에러 메시지/스택 트레이스/재현 단계를 받고 원인 분석"
버그 추적은 컨텍스트가 폭발하기 쉬운 작업입니다. 디버거 에이전트에 격리시키면 메인이 깔끔하게 유지됩니다.

위임할 때 함께 넘길 정보:
- 에러 메시지/스택 트레이스
- 재현 단계
- 관련 코드 경로
- 최근 변경 사항 (`git log`)
#### 6: 마이그레이션/리팩토링 에이전트
**역할**: "특정 패턴을 일괄 변경"

예: "프로젝트 전체에서 `var`를 `const`로 바꾸기", "모든 API 호출에 에러 처리 추가". 반복적이지만 컨텍스트가 많이 필요한 작업에 적합합니다.

### 3. 서브에이전트 활용 원칙

1. **명확한 단일 책임**: 한 에이전트에 너무 많은 역할을 주지 말 것. "테스트 작성+실행+수정"보다 "테스트 작성"만.
    
2. **입력과 출력 형식을 정의**: 위임 시 무엇을 주고 무엇을 받을지 정해두면 결과를 메인에서 활용하기 쉽습니다.
    
3. **`.claude/agents/` 폴더에 정의 저장**: Claude Code는 프로젝트별 서브에이전트 정의를 지원합니다. 팀 전체가 같은 에이전트 셋을 공유할 수 있습니다.

> 예시 구조:
```
    .claude/
      agents/
        code-explorer.md
        test-writer.md
        code-reviewer.md
        debugger.md
        security-auditor.md
```
4. **시스템 프롬프트는 구체적으로**: "테스트를 작성해줘"보다 "Vitest로 AAA 패턴, 파일명 `*.test.ts`, 정상/엣지/에러 케이스 각 1개 이상"이 훨씬 좋습니다.
    
5. **메인 에이전트의 컨텍스트 관리**: 서브에이전트에게 위임할 작업은 **결과 요약만** 메인이 받습니다. 메인이 모든 중간 과정을 추적할 필요 없습니다.
    
6. **병렬 실행 활용**: 독립적인 조사/작업은 여러 서브에이전트에 동시 위임 가능합니다. "프론트 패턴 조사"와 "백엔드 패턴 조사"를 동시에.

### 4. 실전 워크플로 예시: "결제 환불 기능 추가"

```
1. 메인 에이전트가 작업 시작
2. → Code Explorer 서브에이전트: "결제/환불 관련 기존 코드 조사"
   → 요약 보고 받음
3. → 메인이 구현 계획 수립, 인터페이스 설계
4. → Test Writer 서브에이전트: "환불 함수의 테스트 케이스 작성"
   → 테스트 파일 받음
5. → 메인이 실제 구현 (테스트 통과 목표)
6. → Code Reviewer 서브에이전트: "이 diff를 리뷰"
   → 지적 사항 받음
7. → 메인이 수정
8. → Security Auditor 서브에이전트: "결제 관련이라 보안 점검"
   → 취약점 보고 받음
9. → 메인이 최종 마무리, 커밋, PR
```

메인 에이전트의 컨텍스트는 거의 "구현"에만 집중되어, 깨끗하게 유지됩니다.

### 5. 개발 단계 체크리스트

- [ ] 작업이 1~4시간 단위로 분해되었는가
- [ ] 이슈 트래커에 등록되었는가
- [ ] 작업 시작 전 관련 문서/코드를 다시 읽었는가
- [ ] 테스트를 먼저 또는 동시에 작성했는가
- [ ] 작게, 자주 커밋했는가
- [ ] 점진적으로 실행/검증했는가
- [ ] 셀프 리뷰를 거쳤는가
- [ ] 디버그 코드/console.log를 제거했는가
- [ ] 커밋 메시지가 컨벤션을 따르는가
- [ ] PR 설명이 충실한가
- [ ] 비자명한 결정을 기록했는가
- [ ] (선택) 서브에이전트로 리뷰/보안/테스트 한 번 더 확인했는가
