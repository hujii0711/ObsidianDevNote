

### 1. 기획 (Planning)

- 무엇을, 왜, 누구를 위해 만드는지 정의
- 성공 지표(KPI), 범위(Scope), 비범위(Out-of-scope) 명확화
- _추가 권장_: 사용자 스토리 또는 유스케이스 형태로 정리해두면 Claude에게 그대로 컨텍스트로 줄 수 있어 효율적입니다.
### 2. 설계 (Design / Architecture)

- 시스템 아키텍처, 데이터 모델, API 스펙, UI 와이어프레임
- 기술 스택 결정과 그 근거
- _추가 권장_: `CLAUDE.md` 또는 `ARCHITECTURE.md`로 문서화. Claude Code가 매 세션마다 컨텍스트를 잃기 때문에, 설계 문서를 프로젝트 루트에 두면 일관성이 크게 올라갑니다.

**➕ 2.5 환경 셋업 (Environment Setup) — 신규 추가 권장**

- 레포 초기화, 디렉토리 구조, 린터/포매터, 컨벤션 규칙
- 의존성 관리, `.env` 템플릿, Git hooks
- _왜 필요한가_: Claude Code는 기존 컨벤션을 잘 따르지만, 초기에 규칙이 없으면 파일마다 스타일이 흔들립니다. 첫 단추를 잘 끼우는 단계입니다.

### 3. 개발 (Development)

- 기능별로 작게 쪼개서 구현
- _Claude Code 특화 팁_:
    - 작은 단위(기능 하나 → 커밋 하나)로 작업 지시
    - 큰 모듈은 "먼저 인터페이스만, 다음 구현" 식으로 단계 분리
    - 변경 후 항상 `git diff`를 사람이 직접 검토

**➕ 3.5 셀프 검증 (Self-Verification) — 신규 추가 권장**

- 개발 직후, 테스트로 넘기기 전에 짧게:
    - 빌드가 깨지지 않는지
    - 타입 체크/린트 통과하는지
    - 변경된 부분을 실제로 실행해봤는지
- _왜 필요한가_: Claude가 "구현 완료"라고 보고했지만 실제로는 import 누락이나 미사용 변수 같은 문제가 남아있는 경우가 흔합니다. 이 단계가 테스트 단계의 부담을 크게 줄여줍니다.

### 4. 테스트 (Testing)

- 단위 / 통합 / E2E 테스트
- _추가 권장_: 가능하면 **테스트를 먼저 작성하거나 동시에 작성** (TDD에 가깝게). Claude는 명세가 테스트 코드로 주어질 때 훨씬 정확하게 구현합니다.

### 5. 코드 리뷰 (Code Review)

- AI 리뷰 + 사람 리뷰의 이중 구조 권장
- _Claude Code 특화_: "이 PR을 시니어 엔지니어 관점에서 비판적으로 리뷰해줘"라고 별도 세션에서 검토시키면, 생성한 세션과 다른 시각이 나옵니다.

**➕ 5.5 보안 & 품질 점검 (Security / Quality Gate) — 신규 추가 권장**

- 시크릿/API 키 노출 검사 (`gitleaks` 등)
- 의존성 취약점 점검 (`npm audit`, `pip-audit`)
- 정적 분석 (SAST), 라이선스 확인
- _왜 필요한가_: AI가 생성한 코드는 종종 더미 API 키, 하드코딩된 경로, 오래된 라이브러리 버전을 포함하기 쉽습니다.

**➕ 5.7 스테이징 / UAT — 신규 추가 권장**

- 실제 환경과 유사한 곳에서 배포 전 최종 검증
- 사용자 수용 테스트(UAT)
- 프로덕션 배포의 안전망 역할

### 6. 배포 (Deployment)

- CI/CD 파이프라인을 통한 자동 배포
- _추가 권장_: 카나리 / 블루-그린 / 피처 플래그로 점진적 롤아웃

### 7. 운영 & 모니터링 (Operations / Observability)

- 로그, 메트릭, 알림(Alerting), 에러 트래킹(Sentry 등)
- 성능 모니터링, 사용자 행동 분석

### 8. 회고 & 개선 (Retrospective / Iteration)

- 배포 후 KPI 확인, 사용자 피드백 수집
- 다음 사이클의 기획으로 연결 → 전체가 **루프**가 됩니다.

## 정리하면

```
기획 → 설계 → [환경 셋업] → 개발 → [셀프 검증] → 테스트
  → 리뷰 → [보안/품질 점검] → [스테이징/UAT] → 배포
  → [운영/모니터링] → [회고] → (다시 기획)
```

## 한 가지 강조하고 싶은 점

Claude Code로 작업할 때 가장 중요한 보강은 **"환경 셋업"과 "셀프 검증"** 두 단계입니다. 이유는:

- 환경 셋업: AI가 따라야 할 규칙을 코드/문서로 못 박아두면 일관성이 비약적으로 향상됨
- 셀프 검증: "구현했다"와 "정상 동작한다" 사이의 갭이 사람이 짠 코드보다 크기 때문

나머지(보안 점검, 모니터링, 회고)는 전통적인 모범 사례라 규모가 큰 프로젝트일수록 가치가 커집니다. 작은 사이드 프로젝트면 처음에는 생략해도 됩니다.

혹시 만들려는 애플리케이션의 규모나 종류(웹/모바일/CLI 등)를 알려주시면, 거기에 맞춰 더 구체적으로 어느 단계에 힘을 줘야 할지 짚어드릴 수 있습니다.

**개발 단계별 역할 분리**

`플래너` → 요구사항 분석, 구현 순서 설계, 의존성 파악. 코딩 시작 전 청사진을 그립니다.

`코드 작성자` → 실제 기능 구현에만 집중합니다. 리뷰나 테스트 걱정 없이 순수 코딩에 특화합니다.

`코드 리뷰어` → 작성된 코드의 품질, 버그, 컨벤션을 독립적인 시각으로 검토합니다.

`테스터` → 유닛·통합 테스트 작성 및 엣지 케이스를 커버합니다. 코드 작성자와 분리해야 놓치는 케이스가 줄어듭니다.

`디버거` → 에러 로그 분석, 재현 경로 추적, 수정 패치 제안에 특화합니다.

`문서 작성자` → README, API 문서, 인라인 주석을 코드 완성 후 별도로 담당합니다.

`보안 감사자` → OWASP 체크리스트, 인증/인가 패턴, 취약점 스캔을 전담합니다.

`DevOps 에이전트` → CI/CD 파이프라인, Dockerfile, IaC 설정 등 인프라 코드를 담당합니다.

`리서처` → 라이브러리 선택, 기술 비교, 아키텍처 패턴 조사를 담당합니다.

---

**실전 운용 원칙**

역할을 나눌 때 가장 중요한 건 **컨텍스트 격리**입니다. 각 에이전트에게 해당 역할에만 필요한 정보와 도구 접근권을 주는 것이 효율적입니다. 독립적인 태스크는 병렬로 실행하고 (예: 테스터 + 문서 작성자 동시 실행), 결과는 오케스트레이터가 통합합니다.

프로젝트 규모가 작으면 `플래너 + 코드 작성자 + 리뷰어` 3역할로도 충분하고, 대규모 팀 프로젝트일수록 보안 감사자·DevOps 에이전트까지 세분화하는 것이 효과적입니다.
