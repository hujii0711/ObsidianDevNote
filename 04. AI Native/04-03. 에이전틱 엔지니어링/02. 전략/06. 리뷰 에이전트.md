### 자동화된 검증 통과 (Automated Checks)
사람이 리뷰하기 전에 **CI가 먼저 검증**합니다.

> 리뷰 에이전트 역할 분담
- 시니어 엔지니어 리뷰어
	역할: "PR diff를 시니어 엔지니어 관점에서 비판적으로 리뷰"
- 코드 컨벤션:  린터가 못 잡는 "코드 외 규칙"을 자동 검증하는 효과 있다.
	- 명명 규칙
	- 폴더/파일 구조
	- 절대 하지 말 것 목록 위반
	- 패턴 불일치 (다른 곳은 A인데 여기만 B)
- 성능 병목 체크
- 리소스 누수 체크
- 빌드 성공
- 린트 통과
- 타입 체크 통과
- 테스트 통과 (단위/통합/E2E)
- 커버리지 임계값 충족
- 보안 스캔 통과 (Snyk, gitleaks 등)

이게 빨갛게 떠있는데 리뷰 요청하는 건 예의 위반입니다. **녹색 빌드 후 리뷰 요청**이 원칙입니다.

### 승인 & 머지 기준

언제 머지할 수 있는가에 대한 명확한 규칙이 필요합니다.

- **필수 승인 수**: 최소 1명, 중요 코드는 2명
- **블로킹 코멘트 모두 해결**
- **모든 CI 체크 통과**
- **최신 main 브랜치와 머지/리베이스 완료**
- **머지 전략**: Squash / Merge commit / Rebase 중 팀 컨벤션 따르기
- **머지 후 브랜치 삭제**

### 서브에이전트 활용 방안

리뷰 단계는 서브에이전트가 가장 빛나는 단계입니다. 사람 리뷰어의 시간은 비싸고 한정적이지만, AI 리뷰어는 **모든 PR에 1차 검토**를 제공할 수 있습니다. 핵심은 **"사람 리뷰를 대체"가 아니라 "사람 리뷰의 부담을 줄이고 품질을 높이는 1차 필터"** 로 쓰는 것입니다.

### 실전 워크플로: PR 리뷰 파이프라인

```
1. 개발자가 PR 생성
2. CI 자동 실행 (빌드, 린트, 타입, 테스트)
   └─ 실패 시: 개발자가 수정 후 다시
3. AI 1차 리뷰 (병렬 실행):
   ├─ Senior Reviewer    (전반 품질)
   ├─ Security Reviewer  (보안)
   ├─ Performance Reviewer (성능)
   ├─ Convention Checker (컨벤션)
   ├─ Test Auditor       (테스트)
   └─ Doc Auditor        (문서)
   → 통합 리포트 PR 코멘트로 자동 게시
4. 개발자가 AI 지적 사항 반영
5. AI 재검토 (이번엔 새 diff만)
6. 사람 리뷰어에게 할당
   → 사람은 AI가 못 잡는 영역에 집중:
      - 비즈니스 로직 정합성
      - 장기 유지보수 관점
      - 팀/제품 컨텍스트
      - 사용자 영향
7. 사람 리뷰 통과 → 머지
```

**핵심**: AI 리뷰는 "사람 리뷰 전 단계의 자동 필터"입니다. 이 단계가 잘 돌면, 사람 리뷰는 빠르고 가치 있는 일에만 집중하게 됩니다.

### 서브에이전트 운영 팁 (리뷰 단계 특화)

##### 1. **`.claude/agents/reviewers/` 디렉토리로 분리**:

 ```
.claude/agents/reviewers/
	senior.md
	security.md
	performance.md
	convention.md
	test.md
	architecture.md
	docs.md
	ux.md
	regression-impact.md
 ```
 
##### 2. **GitHub Actions 와 통합**: PR 생성 시 자동으로 AI 리뷰가 코멘트로 달리게 설정

##### 3. **출력 형식 표준화**: 각 리뷰어가 같은 형식으로 출력하면 통합 리포트 생성이 쉬움
```
    ## [에이전트 이름]
    ### Blocking
    - ...
    ### Suggestions
    - ...
    ### Nitpicks
    - ...
```
   
### 리뷰 단계 체크리스트

**작성자(Author) 측**:
- [ ] 셀프 리뷰 완료
- [ ] PR이 작고 단일 목적인가
- [ ] PR 제목/설명 충실
- [ ] 모든 CI 체크 녹색
- [ ] AI 1차 리뷰 지적 사항 반영
- [ ] 재리뷰 요청 명시

**리뷰어(Reviewer) 측**:
- [ ] 정확성 검토 (엣지 케이스, 에러 처리)
- [ ] 설계 적정성
- [ ] 가독성/명명
- [ ] 테스트 충분성
- [ ] 보안 점검
- [ ] 성능 영향
- [ ] 컨벤션 일치
- [ ] 문서 업데이트
- [ ] 코멘트가 건설적/구체적인가

**머지 전**:
- [ ] 필수 승인 수 충족
- [ ] 블로킹 코멘트 모두 해결
- [ ] CI 통과
- [ ] 최신 base 브랜치 반영
- [ ] AI 재검토 통과

### 한 가지 조언

리뷰 단계에서 흔한 실수는 두 가지입니다.

**첫째, 너무 빡빡한 리뷰**: "이게 다 통과해야 머지"라는 기준이 비현실적으로 높으면, PR이 쌓이고 개발 속도가 죽습니다. 완벽이 아니라 **"지금보다 나아지는가"** 가 기준이어야 합니다.

**둘째, 너무 느슨한 리뷰**: "LGTM 👍" 한 줄 승인이 반복되면, 리뷰가 형식이 되고 품질 문제가 누적됩니다.

균형점은 **"심각도에 따라 차등 대응"** 입니다.

- `blocking`: 머지 전 반드시 해결
- `suggestion`: 가능하면 반영, 안 되면 이유 적기
- `nitpick`: 무시해도 됨, 작성자 재량

그리고 Claude Code 환경에서 가장 큰 변화는, **AI 1차 리뷰가 표준이 되면 사람 리뷰는 "정말 사람이 봐야 할 것"에만 집중**할 수 있다는 점입니다. AI가 못 잡는 영역(비즈니스 정합성, 장기 설계 영향, 팀 컨텍스트)에 사람의 시간을 쓰는 것이 새로운 리뷰의 표준입니다.

진행 중인 프로젝트의 리뷰 프로세스와 팀 규모를 알려주시면, 그에 맞는 서브에이전트 셋과 GitHub Actions 워크플로 예시까지 구체적으로 작성해드릴 수 있습니다.
