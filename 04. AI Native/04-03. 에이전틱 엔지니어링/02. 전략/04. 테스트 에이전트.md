### PART 1. 테스트 전략 수립

- 테스트 도구 선정(필수)
	기술 스택에 맞는 테스트 도구를 확정합니다.

| 계층      | JavaScript/TypeScript | Python         |
| ------- | --------------------- | -------------- |
| 단위 테스트  | Jest, Vitest          | pytest         |
| 통합 테스트  | Supertest, Jest       | pytest + httpx |
| E2E 테스트 | Playwright, Cypress   | Playwright     |
| 커버리지    | Istanbul (Jest 내장)    | pytest-cov     |

### PART 2. 단위 테스트 (Unit Test)

가장 작은 단위(함수, 클래스, 컴포넌트)가 단독으로 올바르게 동작하는지 검증합니다.
- 백엔드 단위 테스트 (필수)
- 프론트엔드 단위 테스트 (필수)
- 커버리지 측정 및 기준 설정 (필수)


### PART 3. 통합 테스트 (Integration Test)

여러 모듈이 함께 동작할 때 올바르게 연동되는지 검증합니다.
- API 통합 테스트 (필수)
	실제 DB와 연결해서 API 엔드포인트 전체 흐름을 테스트합니다.
-  테스트 DB 격리 설정 (필수)
- 서비스 간 연동 테스트 (권장)
	외부 API, 메시지 큐, 캐시 등 외부 서비스와의 연동을 검증합니다.


### PART 4. E2E 테스트 (End-to-End Test)

실제 브라우저에서 유저 시나리오 전체를 검증합니다.
-  Playwright 설정 (필수)
- 핵심 유저 시나리오 E2E 테스트 (필수)
	MVP의 핵심 기능을 유저 관점에서 처음부터 끝까지 테스트합니다.
- 시각적 회귀 테스트 (권장)
	UI 변경 시 의도치 않은 시각적 변화를 감지합니다.


### PART 5. 특수 테스트
- 성능 테스트 `권장`
	API 응답 시간과 동시 접속 처리 능력을 검증합니다.
-  보안 테스트 `권장`
	일반적인 보안 취약점을 자동으로 검사합니다.
- 접근성 테스트 `권장`
	웹 접근성 기준(WCAG) 준수 여부를 검사합니다.


### 8. 테스트 실행 자동화

**로컬 실행**:

- watch 모드 (`vitest --watch`)로 파일 저장 시 자동 실행
- pre-commit 훅에서 변경된 파일 관련 테스트만 실행
- pre-push 훅에서 전체 단위 테스트 실행

**CI 실행**:

- PR마다 모든 단위/통합 테스트 실행
- main 브랜치에 E2E 테스트 추가 실행
- 야간에 부하/보안 테스트
- 병렬 실행으로 시간 단축
- 캐싱 (의존성, 빌드 결과)
### 9. 커버리지 측정 & 보고

- **도구**: Istanbul/c8 (JS), coverage.py (Python)
- **메트릭**: 라인/브랜치/함수 커버리지
- **임계값 설정**: 일정 수치 이하면 CI 실패
- **변경된 코드의 커버리지** 우선 (전체보다 의미 있음)
- **시각화**: Codecov, Coveralls에 업로드

**주의**: 커버리지 100%가 품질을 보장하지 않습니다. 의미 없는 테스트로 숫자만 채울 수 있으니, **무엇을** 테스트하는지가 더 중요합니다.

### 10. 회귀 테스트 (Regression Tests)

버그가 발견되면:

1. **버그를 재현하는 테스트를 먼저 작성** (실패해야 함)
2. 그 버그를 수정
3. 테스트가 통과하면 수정 완료
4. 이 테스트는 영구히 회귀 방지 역할

이 방식이 "고쳤다고 했는데 또 같은 버그 터지는" 사고를 막아줍니다.

### 12. 테스트 리뷰 & 유지보수

테스트도 코드입니다. 같이 리뷰하고 리팩토링합니다.

- **테스트 자체에 대한 코드 리뷰**: 명확한 이름, 적절한 추상화
- **중복 제거**: 헬퍼 함수, 공통 셋업 추출
- **사양 변경 시 테스트 업데이트**
- **죽은 테스트 제거**: 사용하지 않는 기능의 테스트


## 서브에이전트 활용 방안
### 패턴 1: 테스트 케이스 설계자 (Test Designer)
**역할**: "주어진 함수/기능에 대해 어떤 테스트 케이스가 필요한지 나열"
코드를 받고 **테스트 케이스의 목록만** 반환합니다. 실제 코드는 아직 안 짭니다.

### 패턴 2: 단위 테스트 작성자 (Unit Test Writer)
**역할**: "케이스 목록과 대상 함수를 받아 실제 테스트 코드 작성"

### 패턴 3: 통합 테스트 작성자 (Integration Test Writer)
**역할**: "API 엔드포인트나 DB 트랜잭션에 대한 통합 테스트 작성
별도 에이전트로 분리하는 이유: 단위 테스트와 다른 패턴(테스트 DB 셋업, 시드 데이터, 클린업)이 필요하기 때문.

### 패턴 4: E2E 시나리오 작성자 (E2E Scenario Writer)
**역할**: "사용자 스토리를 받아 Playwright/Cypress 테스트로 변환"

### 패턴 5: 모킹 설계자 (Mock Designer)
**역할**: "외부 의존성을 식별하고 모킹 코드 작성"

### 패턴 6: 테스트 리뷰어 (Test Reviewer)
**역할**: "작성된 테스트가 의미 있는지, 안티패턴이 없는지 검토"

### 패턴 7: 회귀 테스트 생성기 (Regression Test Generator)
**역할**: "버그 리포트나 픽스 PR을 받아 회귀 테스트 작성"

### 패턴 8: 커버리지 분석가 (Coverage Analyzer)
**역할**: "커버리지 리포트를 분석하고 우선 보강할 곳 추천"

### 패턴 9: 플레이키 테스트 헌터 (Flaky Test Hunter)
**역할**: "테스트 실행 로그를 받아 플레이키 테스트 식별 및 원인 분석"

### 패턴 10: 보안 테스트 에이전트 (Security Test Agent)
**역할**: "OWASP Top 10 등 보안 관점의 테스트 케이스 생성"


**Claude Code 환경에서는 "테스트 먼저"가 훨씬 유리한 경우가 많습니다**. 그 이유를 단계적으로 설명드리겠습니다.

## 전통적인 두 입장

### "테스트 먼저" (TDD: Test-Driven Development)

Kent Beck이 정립한 방식으로, 다음 사이클을 반복합니다.

1. **Red**: 실패하는 테스트 작성
2. **Green**: 테스트를 통과하는 최소 코드 작성
3. **Refactor**: 코드 개선 (테스트는 계속 통과)

**장점**:
- 사양이 명확해진다 (테스트가 곧 사양)
- 과도한 구현 방지 (필요한 것만 만들게 됨)
- 리팩토링 안전망 즉시 확보
- 자연스럽게 테스트 가능한 설계가 됨
- 디버깅 시간 감소

**단점**:
- 초기 속도가 느리게 느껴짐
- 사양이 자주 바뀌면 테스트도 자주 깨짐
- 탐색적 작업(prototyping, 리서치)에는 부적합
- 학습 곡선이 있음

### "개발 먼저" (Test-After 또는 No-Test)

먼저 동작하는 코드를 만들고, 그 다음 테스트를 작성하거나 아예 안 작성하는 방식.

**장점**:
- 초기 속도가 빠르게 느껴짐
- 탐색적/실험적 작업에 자유로움
- 사양이 명확하지 않을 때 유연함
- 진입 장벽이 낮음

**단점**:
- 테스트를 미루다 안 짜게 됨 ("나중에"가 영원히)
- 테스트하기 어려운 설계로 코드가 만들어짐
- 회귀 버그 자주 발생
- 리팩토링이 두려워짐 → 코드 부패
- 디버깅에 더 많은 시간이 든다는 연구들이 있음

## 사실, 답은 "사이"에 있다

극단적인 TDD도, 테스트 없는 개발도 현실에선 드뭅니다. 실제 현장에서 가장 흔하고 효과적인 방식은:

**"테스트와 개발을 거의 동시에 진행"** (Test-Adjacent Development)

- 함수 시그니처 설계 → 핵심 테스트 케이스 2~3개 작성 → 구현 → 추가 테스트로 보강 → 리팩토링

엄격한 TDD의 "테스트 한 줄 → 코드 한 줄"까지 가지 않더라도, **"기능 단위로 테스트를 먼저 또는 동시에"** 라는 원칙은 거의 모든 경우에 유효합니다.

## 상황별 가이드

### 테스트를 먼저 작성하는 게 좋은 경우

1. **사양이 명확한 경우**: 입력/출력이 분명한 비즈니스 로직, 알고리즘, API 엔드포인트
2. **버그 수정**: 먼저 버그를 재현하는 테스트 작성 → 수정 → 재발 방지
3. **레거시 코드 수정**: 변경 전에 현재 동작을 테스트로 고정(characterization test)
4. **여러 엣지 케이스가 있는 로직**: 가격 계산, 권한 검증, 상태 머신
5. **공유/공용 라이브러리**: 다양한 사용자가 의존할 코드
6. **결제, 인증 같은 치명적 영역**: 실수 비용이 큰 곳
7. **AI(Claude Code)와 협업할 때**: 테스트가 명세 역할을 함

### 테스트를 나중에 또는 가볍게 해도 되는 경우

1. **프로토타입/스파이크(spike)**: 가능성 검증용 코드, 어차피 버릴 것
2. **사양이 매우 유동적인 초기 탐색**: 매번 테스트 갈아엎으면 비용 큼
3. **UI 디테일/스타일링**: 시각적 확인이 더 효율적
4. **일회성 스크립트**: 한 번 쓰고 안 쓸 도구
5. **단순 CRUD의 자동 생성 코드**: 프레임워크가 검증해주는 경우
6. **사용자 피드백 받기 위한 MVP의 비핵심 부분**: 핵심만 테스트하고 빠르게 출시

### 어떤 경우에도 테스트 없이는 안 되는 영역

- 결제/금전 거래
- 인증/인가
- 데이터 무결성에 관한 부분
- 외부로 노출되는 공개 API
- 보안 관련 로직
- 컴플라이언스 요구가 있는 영역 (의료, 금융 등)

## Claude Code 환경에서의 특별한 권장 사항

이 부분이 핵심입니다. **AI와 협업하는 개발에서는 "테스트 먼저"가 단순한 모범 사례가 아니라 효율의 핵심**이 됩니다.

### 왜 AI와의 협업에서 테스트 먼저가 유리한가

1. **테스트가 곧 명세, AI는 명세에 강하다**
   - "이 함수 만들어줘"보다 "이 테스트들이 통과하는 함수 만들어줘"가 훨씬 정확합니다
   - 자연어 명세는 해석의 여지가 있지만, 테스트 코드는 명확합니다
   - AI가 만든 결과를 즉시 자동 검증할 수 있습니다

2. **AI는 그럴듯하지만 틀린 코드를 만들 수 있다**
   - 사람이 매번 코드를 꼼꼼히 읽기 어려움
   - 테스트가 1차 검증자 역할
   - "구현했다"와 "정상 동작한다" 사이의 갭을 메워줌

3. **반복 작업 비용이 거의 0**
   - 사람이 테스트 먼저 짜는 부담의 큰 이유는 "귀찮음"
   - AI에게 테스트 케이스 생성을 위임할 수 있음
   - "이 함수의 테스트 케이스를 정상/엣지/에러로 분류해 나열해줘" → AI가 빠르게 처리

4. **리팩토링/재구현이 자주 일어남**
   - AI가 한 번에 잘 못 만들었을 때, 테스트가 있으면 "다시 짜줘"가 안전함
   - 테스트가 없으면 매번 사람이 검증해야 함

### Claude Code에서의 실전 사이클 (권장)

```
1. 기능 요구사항 정리
   → 입력, 출력, 엣지 케이스 명시
   
2. 서브에이전트로 테스트 케이스 발굴
   "이 기능에 필요한 테스트 케이스를 정상/경계/에러로 나열"
   
3. 사람이 케이스 목록 검토/보강
   (AI가 빠뜨린 도메인 특화 케이스 추가)
   
4. 서브에이전트로 테스트 코드 작성
   "이 케이스 목록을 Vitest로, AAA 패턴으로"
   
5. 사람이 테스트 검토
   (단언이 의도와 맞는지, 너무 약하지 않은지)
   
6. 테스트 실행 → 실패 확인 (Red)
   
7. AI에게 구현 요청
   "이 테스트들이 통과하도록 구현해줘"
   
8. 테스트 실행 → 통과 확인 (Green)
   
9. AI에게 리팩토링 요청
   "테스트는 그대로 두고 코드 개선"
   
10. 테스트 재실행 → 여전히 통과
```

이 사이클이 돌면, 한 번도 코드를 자세히 안 읽고도 신뢰할 수 있는 결과물이 나옵니다.

### 단, 주의할 점

- **테스트 자체도 AI가 만들면 검증해야 함**: AI가 만든 테스트가 잘못된 사양을 표현할 수 있음. 사람이 한 번은 봐야 함.
- **테스트와 구현을 같은 AI 세션에서 하지 말 것**: 같은 맥락에서 만든 테스트와 구현은 같은 오해를 공유할 수 있음. 가능하면 다른 서브에이전트가 작성.
- **명세가 진짜 모호한 초기 탐색에서는 무리하지 말 것**: TDD가 모든 경우 정답은 아님.

## 그래서 결론은?

**원칙적인 답**:

> "테스트와 구현을 분리해서 누가 먼저냐를 따지는 사고 자체에서 벗어나야 합니다. 둘은 같은 작업의 두 면입니다. 사양을 정하는 작업(테스트)과 사양을 만족시키는 작업(구현)은 서로를 정의합니다."

**실용적인 답**:

1. **기본 모드는 "테스트 우선 또는 동시 작성"**: 엄격한 TDD가 부담스러우면 최소한 같은 PR 안에 테스트와 구현이 함께 들어가게.

2. **테스트 없이 시작해도 되는 영역을 명확히 구분**: 프로토타입, UI 탐색 같은 곳은 자유롭게.

3. **Claude Code 환경이면 "테스트 먼저"의 가치가 2배**: AI에게 명세를 주는 가장 정확한 방식이 테스트. 시간 비용도 AI가 분담해주므로 부담이 적음.

4. **"개발 먼저"를 선택했다면 반드시 같은 작업 단위 안에 테스트 추가**: "나중에 짜겠다"는 99% 실패합니다.

5. **버그 픽스는 무조건 테스트 먼저**: 이건 예외 없는 규칙으로 권장.

## 가장 흔한 오해 정리

- ❌ "TDD는 시간이 더 걸린다"
  → 단기적으론 그럴 수 있으나, 디버깅 시간을 합하면 같거나 빠릅니다. 여러 연구에서 일관된 결과.

- ❌ "프로토타입에선 테스트 쓸모없다"
  → 핵심 로직은 프로토타입에서도 테스트 가치가 있습니다. UI/스타일링은 예외.

- ❌ "테스트 100% 커버리지가 목표"
  → 의미 없는 테스트로 숫자만 채울 수 있음. 무엇을 테스트하는지가 더 중요.

- ❌ "테스트는 QA의 일"
  → 단위/통합 테스트는 개발자의 책임. QA는 더 상위 레벨.

- ❌ "AI가 짠 코드는 어차피 검증해야 하니 테스트 의미 없다"
  → 정반대. AI가 짠 코드일수록 자동 검증 수단이 필수.

## 한 줄 결론

**"테스트와 구현 중 무엇이 먼저냐"는 잘못된 질문입니다. 옳은 질문은 "이 작업의 사양을 어떻게 명시적으로 표현할 것인가, 그리고 그 표현을 어떻게 검증 가능하게 만들 것인가"이며, 그 답이 대개 "테스트를 먼저 또는 동시에 작성한다"가 됩니다. 특히 Claude Code 환경에서는 이 원칙이 효율성의 핵심 도구가 됩니다.**

진행 중인 프로젝트의 성격(프로토타입/MVP/프로덕션 서비스)이나 팀 상황을 알려주시면, 거기에 맞는 구체적인 테스트 전략과 적용 비율(예: "핵심 도메인은 TDD, UI는 사후 테스트")을 더 구체적으로 제안해드릴 수 있습니다.
