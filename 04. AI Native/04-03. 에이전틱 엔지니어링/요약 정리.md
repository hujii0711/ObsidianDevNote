
- ### rules/ 폴더 — 모듈형 규칙 관리
    `CLAUDE.md`가 커지면 `.claude/rules/`로 분리
    - `CLAUDE.md`가 커질 경우 `.claude/rules/` 폴더로 분리해 관리
    - 각 규칙 파일은 **주제별로 분리**되어 유지보수가 용이
        - 예: `code-style.md`, `testing.md`, `api-conventions.md`, `security.md`
    - YAML 프런트매터의 `paths` 필드를 사용하면 **특정 경로에만 적용되는 규칙** 지정 가능
        - 예: `src/api/**/*.ts` 경로에만 API 규칙 적용
    - 경로 지정이 없는 규칙은 모든 세션에 항상 로드됨
- **규칙이 적다면** → `paths` 없이 토픽별 분리만 해도 충분
- **규모가 커질수록** → `paths`로 스코프를 좁혀서 컨텍스트 효율화

결국 `rules/`의 핵심은 **CLAUDE.md 분리 + 선택적 로드** 두 가지이고, `paths`는 후자를 위한 옵션입니다.
규모가 작을 땐 CLAUDE.md 하나로 충분하고, **팀이 커지거나 규칙이 20줄을 넘어가기 시작할 때** `rules/`로 분리하는 것이 자연스러운 시점입니다.

## `.claude/rules/` 폴더의 동작 방식

각 규칙 파일(`.md`)은 frontmatter에 `paths:` 필드가 있는지 여부로 로딩 시점이 갈립니다.

**1. `paths:` 없는 규칙 → 세션 시작 시 항상 로드**

```markdown
# 이 파일은 세션마다 무조건 읽힘
- 커밋 메시지는 conventional commit 형식 사용
- ...
```

**2. `paths:` 있는 규칙 → 매칭되는 파일이 컨텍스트에 들어올 때만 로드**

```markdown
---
paths:
  - "src/api/**/*.ts"
---

이 규칙은 src/api/ 아래 파일을 Claude가 읽을 때만 로드됨
```

즉, `paths` glob 패턴을 지정해두면 해당 경로의 파일을 Claude가 실제로 다룰 때만 그 규칙 파일이 컨텍스트에 로드되고, 관련 없는 세션에서는 전혀 읽히지 않습니다.

- ### CLAUDE.md에 직접 넣지 않는 이유

CLAUDE.md는 **매 세션 항상** 컨텍스트에 로드됩니다. 길고 상세한 레퍼런스 문서를 직접 넣으면 토큰 낭비입니다.

`.claude/docs/`에 두고 skill이 필요할 때만 `@` import로 끌어오면 **필요한 순간에만** 컨텍스트에 올라옵니다.

Claude가 코드베이스를 한 번 훑고 나서 스스로 파악할 수 있는 내용(예: 특정 테스트 유틸 위치)은 파일에 안 적어도 됩니다. `/memory`(auto memory)가 자동으로 기록하니 중복 낭비.

### 훅(Hooks)과 안전장치

- **배경**: 아마존 2026년 3월 사고 - AI가 작성한 코드를 검토 없이 배포하여 6시간 다운타임 발생
- **훅의 정의**: AI가 특정 행동을 하기 직전/직후에 자동 실행되는 스크립트
- **4가지 실용적인 훅**:  
    1. **린트/테스트/빌드 훅**: 커밋 전 자동 실행  
    2. **PR 리뷰 훅**: 서브 에이전트를 통한 확증 편향 방지  
    3. **TDD 훅**: 테스트 미작성 시 파일 수정 차단  
    4. **서비스 장애 패턴 검증 훅**: 과거 장애 패턴을 스크립트화하여 자동 검증 
- 사람이 아닌 시스템에 의존하는 것이 핵심

- 스킬 설정 파일
스킬 설정 파일은 특정 프롬프트와 프로그램 스크립트로 이뤄져 있다. 쉽게 말해, 에이전트가 따라야 할 절차를 안내하는 메뉴얼과 이 때 실행할 프로그램을 함께 제공하는 것이다.

스킬의 경우 평소에는 한줄 설명만 올라가고 전체 내용은 쓸 때만 불러온다.  
같은 기능이라면 MCP 보다 스킬이 훨씬 가볍다.  
그래서 간단한 작업이라면 MCP 대신 로컬 스크립트를 스킬로 감싸주는 것을 추천한다.
```
.claude/skills/
└── ppt-generator/            ← 스킬 폴더
    ├── SKILL.md               ← 핵심 파일 (필수)
    ├── template.md            ← Claude가 채울 템플릿 (선택)
    ├── examples/              ← 예제 출력 (선택)
	    ├── sample.md
    └── scripts/               ← 실행 가능한 스크립트 (선택)
	    ├── generator.py
```

## 한 줄 정리

```
내부 피드백 → "Claude가 실수하지 않도록" 작업 중 교정
외부 피드백 → "팀 전체 기준을 통과했는지" 제출 후 검증

내부는 속도와 컨텍스트,
```

## 함께 쓸 때 가장 강력한 시나리오

```
[Claude 작업 중 - 내부 피드백]
PreToolUse Hook
  → 위험 명령어 사전 차단
  → 보안 파일 접근 제어

PostToolUse Hook
  → 수정 즉시 유닛 테스트
  → 실패 시 같은 세션에서 즉시 재시도

멀티에이전트
  → 생성 에이전트가 코드 작성
  → 평가 에이전트가 품질 채점
  → 기준 미달 시 재생성

        ↓ 내부 검증 통과 후 커밋/푸시

[코드 제출 후 - 외부 피드백]
GitHub Actions
  → 팀 전체 통합 테스트
  → 실제 인프라 E2E 테스트
  → 커버리지 게이트
  → 프로덕션 배포
  → 감사 로그 기록
```

### 개발 단계별 역할 분리

▪︎ 플래너 → 요구사항 분석, 구현 순서 설계, 의존성 파악. 코딩 시작 전 청사진을 그립니다.
▪︎ 코드 작성자 → 실제 기능 구현에만 집중합니다. 리뷰나 테스트 걱정 없이 순수 코딩에 특화합니다.
▪︎ 코드 리뷰어 → 작성된 코드의 품질, 버그, 컨벤션을 독립적인 시각으로 검토합니다.
▪︎ 테스터 → 유닛·통합 테스트 작성 및 엣지 케이스를 커버합니다. 코드 작성자와 분리해야 놓치는 케이스가 줄어듭니다.
▪︎ 디버거 → 에러 로그 분석, 재현 경로 추적, 수정 패치 제안에 특화합니다.
▪︎ 문서 작성자 → README, API 문서, 인라인 주석을 코드 완성 후 별도로 담당합니다.
▪︎ 보안 감사자 → OWASP 체크리스트, 인증/인가 패턴, 취약점 스캔을 전담합니다.
▪︎ DevOps 에이전트 → CI/CD 파이프라인, Dockerfile, IaC 설정 등 인프라 코드를 담당합니다.
▪︎ 리서처 → 라이브러리 선택, 기술 비교, 아키텍처 패턴 조사를 담당합니다.
