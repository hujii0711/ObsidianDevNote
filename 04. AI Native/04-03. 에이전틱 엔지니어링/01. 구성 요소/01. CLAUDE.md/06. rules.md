
가장 큰 목적은 **CLAUDE.md 분리**입니다.

공식 문서도 이렇게 설명합니다:

> "For larger projects, you can organize instructions into multiple files using the `.claude/rules/` directory. This keeps instructions modular and easier for teams to maintain."

---

### 기능 차이로 보면

||CLAUDE.md|`.claude/rules/`|
|---|---|---|
|핵심 목적|항상 필요한 핵심 규칙|CLAUDE.md 분리 + 선택적 로드|
|path 스코프|❌|✅ (선택사항)|
|토픽별 분리|하나의 파일|여러 파일로 분산 가능|

`paths` 지정은 **부가 기능**이고, 단순 분리만 해도 충분히 가치 있습니다.

---

### 실제로는 이 순서로 도입하게 됨

1. 처음엔 `CLAUDE.md` 하나로 시작
2. 내용이 늘어나면 → `rules/`로 토픽별 분리
3. 규모가 더 커지면 → `paths`로 스코프 제한까지 추가

결국 `rules/`는 **CLAUDE.md의 확장 공간**이라고 보면 가장 정확합니다.

## `.claude/rules/` 활용 가이드

### CLAUDE.md vs rules/ 차이부터 이해

||`CLAUDE.md`|`.claude/rules/`|
|---|---|---|
|로드 시점|세션 시작 시 **항상**|시작 시 전체 로드 OR 해당 파일 열 때만|
|용도|항상 필요한 핵심 규칙|상황별/파일별 선택적 규칙|
|크기|200줄 이하 권장|토픽별로 분리 가능|

핵심은 <font color="#ff0000">"항상 필요한가, 아니면 특정 상황에서만 필요한가"</font>로 구분하면 됩니다.

---

### 유용한 활용 패턴

**1. 언어/파일 타입별 규칙** (path-scoped)

```yaml
# .claude/rules/typescript.md
---
paths:
  - "**/*.ts"
  - "**/*.tsx"
---
- strict mode 필수
- any 타입 사용 금지
- interface보다 type 선호
```

**2. 레이어별 규칙** (path-scoped)

```yaml
# .claude/rules/api.md
---
paths:
  - "src/api/**/*.ts"
---
- 모든 엔드포인트 입력값 검증 필수
- 표준 에러 응답 포맷 사용
- OpenAPI 주석 포함
```

```yaml
# .claude/rules/components.md
---
paths:
  - "src/components/**/*.tsx"
---
- props에 반드시 타입 명시
- 스타일은 CSS module만 사용
- 컴포넌트당 파일 하나
```

**3. 테스트 규칙**

```yaml
# .claude/rules/testing.md
---
paths:
  - "**/*.test.ts"
  - "**/*.spec.ts"
---
- describe/it 구조 필수
- mock은 파일 상단에 선언
- 각 테스트는 독립적으로 실행 가능해야 함
```

**4. 보안 규칙** (path 없이 항상 적용)

```
# .claude/rules/security.md
- 환경변수 직접 하드코딩 절대 금지
- SQL은 반드시 parameterized query 사용
- 사용자 입력값은 항상 sanitize
- 시크릿 관련 코드 변경 시 보안팀 리뷰 필요 명시
```

**5. 마이그레이션/레거시 주의사항**

```yaml
# .claude/rules/legacy.md
---
paths:
  - "src/legacy/**"
---
- 이 디렉토리는 리팩토링 금지
- 새 기능 추가 시 반드시 신규 모듈에 작성
- 여기서 import 추가할 때 팀장 승인 필요
```

### 판단 기준 요약

- **CLAUDE.md에 넣을 것** → 빌드 명령어, 프로젝트 전체 구조, 네이밍 컨벤션 등 항상 필요한 것
- **rules/에 넣을 것** → 특정 파일 타입이나 디렉토리에서만 의미 있는 규칙, 내용이 길어서 분리하고 싶은 것
- **skills에 넣을 것** → 특정 태스크를 수행할 때만 필요한 절차적 지침 (배포 절차, PR 작성법 등)

---

<font color="#ff0000">`paths` 없이도 충분히 유용합니다. 핵심은 "CLAUDE.md가 너무 길어질 때 분리" 입니다.</font>

---

### paths 없는 rules/ — 단순 분리 목적

```
.claude/rules/
├── security.md      # 항상 적용, 보안 규칙만 모아둠
├── git-workflow.md  # 항상 적용, 커밋/PR 규칙
└── testing.md       # 항상 적용, 테스트 규칙
```

CLAUDE.md 하나에 200줄 넘게 우겨넣는 것보다, 토픽별로 파일을 나누는 것만으로도 **유지보수가 훨씬 편해집니다.** 팀에서 "보안 규칙 바꾸자"고 하면 `security.md`만 열면 되니까요.

---

### paths 지정 — 컨텍스트 절약 목적

<font color="#ff0000">`paths`의 진짜 가치는 불필요한 규칙을 컨텍스트에서 제외</font>하는 것입니다.

예를 들어 레거시 디렉토리 주의사항을 `paths: ["src/legacy/**"]`로 걸어두면, 레거시 파일을 건드릴 때만 로드됩니다. 평소엔 컨텍스트를 차지하지 않습니다.

규칙이 많아질수록 이 차이가 커집니다.

---

### 정리

- **규칙이 적다면** → `paths` 없이 토픽별 분리만 해도 충분
- **규모가 커질수록** → `paths`로 스코프를 좁혀서 컨텍스트 효율화

결국 `rules/`의 핵심은 **CLAUDE.md 분리 + 선택적 로드** 두 가지이고, `paths`는 후자를 위한 옵션입니다.

## `.claude/rules/` 폴더의 동작 방식

각 규칙 파일(`.md`)은 frontmatter에 `paths:` 필드가 있는지 여부로 로딩 시점이 갈립니다.

**1. `paths:` 없는 규칙 → 세션 시작 시 항상 로드**

```markdown
# 이 파일은 세션마다 무조건 읽힘
- 커밋 메시지는 conventional commit 형식 사용
- ...
```

**2. `paths:` 있는 규칙 → <font color="#ff0000">매칭되는 파일이 컨텍스트에 들어올 때만 로드</font>**

```markdown
---
paths:
  - "src/api/**/*.ts"
---

이 규칙은 src/api/ 아래 파일을 Claude가 읽을 때만 로드됨
```

즉, `paths` glob 패턴을 지정해두면 해당 경로의 파일을 <font color="#ff0000">Claude가 실제로 다룰 때만 그 규칙 파일이 컨텍스트에 로드</font>되고, 관련 없는 세션에서는 전혀 읽히지 않습니다.

## 요약

|상황|동작|
|---|---|
|`paths:` 없는 rule|CLAUDE.md처럼 세션 시작 시 항상 로드|
|`paths:` 있는 rule|매칭 파일 등장 시에만 온디맨드 로드|

그래서 CLAUDE.md가 커질 때 rules 폴더로 분리하는 게 유효한 전략입니다 — 전역적으로 필요한 규칙은 `paths` 없이, 특정 영역(예: 테스트, API 설계 등)에만 필요한 규칙은 `paths`로 스코프를 걸어두면 컨텍스트 낭비 없이 필요한 순간에만 로드됩니다. 서브디렉토리도 자동으로 탐색되므로 `.claude/rules/frontend/react.md`처럼 폴더로 정리해도 됩니다.

# `.claude/rules/` 사용 전략

## 1. 기본 원칙: "전역 vs 조건부"로 나누기

CLAUDE.md가 200줄을 넘어가기 시작하면, 먼저 각 규칙에 대해 이 질문을 던지세요:

> **"이 규칙이 매 세션, 모든 작업에 필요한가? 아니면 특정 파일/폴더를 건드릴 때만 필요한가?"**

- 항상 필요 → CLAUDE.md에 남기거나 `paths` 없는 rule로
- 특정 영역에서만 필요 → `paths`로 스코프된 rule로 분리

## 2. 폴더 구조 예시

```
.claude/
  CLAUDE.md              # 정말 핵심적인 것만 (빌드/테스트 명령어, 전체 아키텍처 개요)
  rules/
    testing.md            # paths: **/*.test.ts
    api-design.md          # paths: src/api/**/*.ts
    frontend/
      react.md             # paths: src/components/**/*.tsx
      styling.md            # paths: **/*.css, **/*.scss
    database.md            # paths: src/db/**/*.ts, **/*migration*.ts
    security.md            # paths 없음 → 항상 로드 (보안은 전역 규칙)
```

서브디렉토리로 나눠도 자동 탐색되니, 도메인별로 묶는 게 관리하기 편합니다.

## 3. 실전 전략

**① 도메인/역할별로 파일 쪼개기**

- `testing.md`, `api-design.md`, `db-migration.md`처럼 하나의 파일 = 하나의 관심사
- 팀에서 "API 컨벤션은 A가, 테스트 규칙은 B가" 식으로 소유권을 나누기 쉬움

**② `paths` glob은 최대한 구체적으로**

```yaml
---
paths:
  - "src/api/**/*.ts"
  - "!src/api/**/*.test.ts"   # 테스트 파일은 제외 (지원 여부는 버전별 확인)
---
```

너무 넓게 잡으면(`**/*.ts`) 사실상 전역 로드와 다를 게 없어져서 분리 의미가 없어집니다.

**③ 정말 전역적인 것만 CLAUDE.md/paths rule에 남기기**

- 빌드·테스트 명령어
- 프로젝트 전체에 적용되는 네이밍/구조 컨벤션
- 보안, 절대 하면 안 되는 것들 (예: "절대 .env 커밋 금지")

**④ "학습 후 알게 되는 것"은 애초에 넣지 않기**

- Claude가 코드베이스를 한 번 훑고 나서 스스로 파악할 수 있는 내용(예: 특정 테스트 유틸 위치)은 파일에 안 적어도 됩니다. `/memory`(auto memory)가 자동으로 기록하니 중복 낭비.

## 4. 디버깅 팁

규칙이 안 먹히는 것 같으면 십중팔구 원인은 둘 중 하나입니다.

1) 규칙이 로드됐는지 확인
세션 중 /memory 또는 /context 계열 명령으로 현재 로드된 CLAUDE.md와 rule 파일 목록을 확인하세요. paths가 지정된 rule은 매칭되는 파일을 아직 열지 않았다면 로드되지 않은 상태입니다.

2) paths glob 패턴 재검토
의도한 파일 경로와 실제 glob 패턴이 정확히 매칭되는지 확인하세요. 예를 들어 `src/api/**/*.ts`인데 실제 파일이 `apps/api/...` 아래 있다면 매칭되지 않습니다.

3) 명시적으로 파일을 언급해 트리거
규칙이 필요한 상황이면 해당 폴더로 이동하거나 관련 파일을 직접 언급해서 Claude가 그 파일을 읽게 만들면, 연결된 rule도 함께 로드됩니다.

4) 정말 전역이어야 하면 paths 제거
매 세션 초반부터 반드시 적용돼야 하는 규칙이라면 애초에 paths 필드를 빼고 세션 시작 시 항상 로드되도록 바꾸는 게 맞습니다.

## 5. 요약 가이드라인

| 상황                 | 어디에                          |
| ------------------ | ---------------------------- |
| 프로젝트 전체 빌드/테스트 명령어 | CLAUDE.md                    |
| 절대 원칙 (보안, 금지사항)   | CLAUDE.md 또는 paths 없는 rule   |
| 특정 언어/프레임워크 컨벤션    | paths로 스코프된 rule             |
| 테스트 작성 규칙          | `paths: **/*.test.ts` rule   |
| API/DB 설계 규칙       | 해당 디렉토리 paths rule           |
| 한 번 알면 되는 코드베이스 정보 | 아예 안 씀 (auto memory가 알아서 기록) |

핵심은 **CLAUDE.md를 얇게 유지하고, 나머지는 "언제 필요한가"를 기준으로 rules에 조건부로 흩뿌리는 것**입니다. 이렇게 하면 컨텍스트 낭비 없이 필요한 순간에만 정확한 규칙이 로드됩니다.
