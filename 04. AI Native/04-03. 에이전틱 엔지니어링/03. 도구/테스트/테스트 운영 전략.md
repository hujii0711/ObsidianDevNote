### 1. TDD 기반 스마트 코딩

> **핵심 루프**: 작은 변경 → 테스트 → 린트 → 커밋 → 반복
1. 기능 하나 추가
2. 테스트 돌려서 확인
3. 린트/포맷 체크
4. 문제 없으면 커밋
5. 다음 기능으로 넘어가기

---

💡이렇게 하면 문제가 생겨도 **마지막 커밋**으로 돌아가면 되니까, 디버깅이 훨씬 쉬워집니다.
테스트 자동화는 단순히 "테스트를 돌린다"는 행위를 넘어, 소프트웨어의 품질을 일정하게 유지하기 위한 **시스템**으로 운영됩니다. 실무에서 보통 운영하는 방식은 크게 4가지 단계로 나뉩니다.

### 1. 테스트의 단계별 운영 (Test Pyramid)
모든 것을 자동화할 수 없으므로, 효율적으로 계층을 나눕니다.
*   **단위 테스트 (Unit Test)**: 함수나 클래스 하나하나를 테스트합니다. 매우 빠르고 많습니다. (현재 우리 코드의 `npm test`가 속할 위치)
*   **통합 테스트 (Integration Test)**: DB 연결이나 API 간의 상호작용을 테스트합니다.
*   **E2E 테스트 (End-to-End Test)**: 브라우저를 직접 띄워 사용자가 실제 버튼을 누르는 것처럼 테스트합니다. (Cypress, Playwright 등 사용)

### 2. CI(지속적 통합) 파이프라인 연동
개발자가 코드를 수정할 때마다 자동으로 실행되게 합니다.
*   **커밋/푸시 시**: 아주 가벼운 단위 테스트만 실행 (빠른 피드백).
*   **PR 생성 시**: 전체 단위 테스트 + 린트(코드 스타일) 체크 + 가벼운 통합 테스트 실행. **이 단계가 통과되어야만 리뷰가 시작됩니다.**
*   **병합(Merge) 전**: 모든 테스트가 100% 통과해야 함을 강제합니다.

### 3. 테스트 결과 리포팅 및 가시성
테스트가 실패했을 때 즉시 알 수 있게 합니다.
*   **알림 자동화**: Slack, Discord 등으로 테스트 실패 로그와 담당자를 태그해서 알림을 보냅니다.
*   **테스트 커버리지(Coverage)**: 우리 코드의 몇 %가 테스트되었는지 측정하고, 이 수치가 떨어지면(예: 80% 미만) PR을 반려하기도 합니다.

### 4. 정기적 및 배포 전 실행
*   **Nightly Build**: 매일 밤마다 전체 시스템에 대해 아주 무거운 테스트(E2E 테스트 등)를 돌려봅니다.
*   **Staging 배포 후**: 실제 서비스와 똑같은 환경(Staging)에 배포한 후, 자동화된 시나리오 테스트를 통과해야만 최종 운영 환경(Production)으로 넘어갑니다.

---

### 실무에서의 핵심 원칙 (Fail Fast)
*   **"빨리 실패하게 하라"**: 에러가 있다면 배포 후에 발견되는 것이 아니라, 개발자의 컴퓨터나 PR 단계에서 **가장 먼저** 발견되게 하는 것이 목표입니다.
*   **"테스트는 자산이다"**: 버그를 하나 잡을 때마다 그 버그가 다시는 발생하지 않도록 해당 케이스를 자동화 테스트로 추가합니다.

### 우리 프로젝트에 적용해본다면?
지금 설정하신 GitHub Actions는 이 중 **"2번 CI 파이프라인 연동"**의 가장 핵심적인 기초를 완성하신 것입니다. 앞으로 기능을 추가할 때마다 `src/test/` 폴더를 만들고 테스트 코드를 하나씩 채워 넣으시면 완벽한 자동화 운영이 가능해집니다!_


---

일반적인 운영 방식은 **"개발자가 직접 작성한 테스트 케이스 코드를 대상으로, 방금 푸시한 기능을 검증하는 것"**입니다.

### 1. 테스트의 대상 (무엇이 무엇을 검사하나?)
*   **기능 코드**: 개발자가 방금 푸시한 실제 게시판 로직 (예: `server.js`)
*   **테스트 코드**: 이 기능이 잘 작동하는지 확인하기 위해 개발자가 별도로 작성한 코드 (예: `server.test.js`)

**CI 서버(GitHub Actions)**는 방금 푸시된 소스 코드를 내려받은 뒤, 그 안에 포함된 **테스트 코드**를 실행시켜서 **기능 코드**가 예상대로 작동하는지 확인합니다.

### 2. 일반적인 작업 흐름
개발자는 보통 기능을 만들 때 테스트 코드도 함께 작성해서 푸시합니다.
1.  `server.js`에 "게시글 삭제" 기능을 만듭니다.
2.  `server.test.js`에 "임의의 글을 삭제했을 때 정말 데이터베이스에서 사라지는지 확인하는 코드"를 작성합니다.
3.  이 두 파일을 **동시에 푸시**합니다.
4.  **GitHub Actions**가 `npm test`를 실행하면, `server.test.js`가 돌아가면서 방금 푸시된 `server.js`의 삭제 기능을 실제로 호출해보고 결과를 체크합니다.

### 3. 왜 이렇게 하나요? (코드가 코드를 검사하는 이유)
*   **자동화**: 사람이 일일이 브라우저를 띄워 버튼을 눌러보지 않아도 되기 때문입니다.
*   **회귀 테스트 (Regression Test)**: 새로운 기능을 추가했을 때, **기존에 잘 되던 기능들이 망가지지 않았는지** 수백 개의 테스트 코드가 단 몇 초 만에 대신 확인해 줍니다.

### 4. 예외: 코드 자체를 검사하는 경우 (Linting/Static Analysis)
테스트 코드를 실행하지 않고, 코드의 **형태**만 보고 문제를 찾는 경우도 있습니다.
*   "세미콜론을 빠뜨렸나?"
*   "사용하지 않는 변수가 있나?"
*   "보안상 위험한 함수를 썼나?"
이런 것은 테스트 케이스 없이도 도구(ESLint 등)가 코드 자체를 훑어서 찾아낼 수 있으며, 이 역시 CI 파이프라인의 중요한 일부입니다.

### 요약하자면:
일반적으로는 **"방금 푸시한 소중한 기능(기능 코드)이 고장 나지 않았음을 증명하기 위해, 내가 작성한 검증용 코드(테스트 케이스)를 실행시키는 방식"**으로 운영됩니다
