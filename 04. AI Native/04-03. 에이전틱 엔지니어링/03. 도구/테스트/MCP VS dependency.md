
> MCP 서버를 통한 실행 vs 프로젝트에 의존성으로 설치하여 실행

### 1. 개요

Playwright는 두 가지 방식으로 활용할 수 있다.

- **MCP 방식**: AI 에이전트(Claude 등)가 MCP 프로토콜로 Playwright MCP 서버를 호출, 자연어 지시에 따라 즉석으로 브라우저를 조작.
- **프로젝트 의존성 방식**: `@playwright/test`를 devDependency로 설치하고, 테스트 코드(`*.spec.js`)를 작성해 러너로 실행. (현재 Test02 프로젝트가 채택한 방식)

이 문서는 둘의 본질적 차이, 적합한 시나리오, 그리고 **토큰 사용량 측면**의 차이를 정리한다.

### 2. 본질적 차이 — "누가, 언제, 왜 실행하는가"

| 축 | **MCP 방식** | **프로젝트 의존성 방식** |
|---|---|---|
| 실행 주체 | AI 에이전트(Claude)가 대화 중 즉석에서 브라우저 조작 | 테스트 러너가 `tests/*.spec.js`를 일괄 실행 |
| 트리거 | 자연어 지시 ("로그인 페이지 열어서 버튼 눌러봐") | `npx playwright test`, CI 파이프라인, git hook |
| 산출물 | 대화 컨텍스트의 결과(스크린샷·DOM·콘솔) | HTML 리포트, trace, 스크린샷, exit code |
| 코드 자산화 | **남지 않음** (한 번 쓰고 휘발) | `*.spec.js`로 **레포에 영구 저장** → 회귀 테스트 |
| 결정성 | LLM 해석이 끼어 결과가 흔들릴 수 있음 | `expect()` 기반 결정적 어서션 |

### 3. 잘 맞는 시나리오

### MCP가 유리 — 일회성·탐색적 상황
- "이 화면 깨졌는지 직접 눈으로 확인해 봐"
- 명세 작성 전 UX를 한 번 만져보기
- 버그 재현 단계를 사람이 모를 때 에이전트에게 시키기
- 새 기능 손풀기·프로토타이핑

### 프로젝트 의존성이 유리 — 반복·검증 상황
- 회귀 테스트 (이 프로젝트의 핵심 용도)
- CI/PR 게이트
- 스펙 → 테스트 → 구현 워크플로우
- 결정적 어서션 (`expect(locator).toHaveText(...)`)

## 4. 기술 스택 차이

### MCP 방식
Claude가 MCP 프로토콜로 Playwright MCP 서버에 호출 → 서버가 브라우저를 띄워 액션 실행 → 접근성 트리(accessibility snapshot)와 스크린샷을 반환. **테스트 코드는 작성하지 않고**, 도구 호출만으로 흐름을 진행한다.

### 프로젝트 의존성 방식
`@playwright/test`가 Node 프로세스 안에서 `chromium`/`webkit`/`firefox` 바이너리를 직접 구동. 테스트 코드(`page.goto`, `expect`, `test()`)가 그대로 실행 단위가 된다. `playwright.config.js`의 `webServer` 옵션으로 서버 자동 기동 가능.

## 5. 토큰 사용량 차이

이 부분이 두 방식의 **가장 실질적인 비용 차이**다.

### 5-1. 누가 토큰을 소비하는가

| 단계 | **MCP 방식** | **의존성 방식** |
|---|---|---|
| 테스트 작성 | (없음 — 매번 즉석 실행) | 최초 1회: 수백~1k 토큰 (LLM이 spec 작성) |
| 실행 1회 | **매 단계마다** 입력+출력 토큰 누적 | **0** (Node 프로세스 안에서 실행, 결과만 exit code) |
| 100번 재실행 | 100배로 누적 | **0** (CI가 돌리면 끝) |
| 실패 분석 | 이미 컨텍스트에 다 있음 | 실패 trace를 Claude에 보여줄 때만 토큰 소비 |

**핵심**: MCP는 "실행=토큰", 의존성은 "작성만 토큰".

### 5-2. MCP 한 액션당 무게 — accessibility snapshot이 비용의 대부분

| 페이지 종류 | 스냅샷 크기 (대략) |
|---|---|
| 로그인 폼 같은 단순 페이지 | 1k ~ 3k 토큰 |
| 게시판 목록 (글 20개) | 3k ~ 6k 토큰 |
| 댓글·페이지네이션 포함 상세 페이지 | 5k ~ 10k 토큰 |

**누적성**이 더해진다. 5단계 시나리오(로그인 → 목록 → 글쓰기 → 저장 → 확인)면 스냅샷이 매 단계 컨텍스트에 쌓여 **10k ~ 25k 토큰** + 추론 토큰. 같은 시나리오를 spec.js로 짜면 코드 자체는 ~500토큰, 실행은 0.

### 5-3. 프롬프트 캐시 관점

- **MCP**: 매 액션 결과가 컨텍스트 끝에 추가되며 직전 캐시는 유효하지만, 대화 중간에 다른 도구·파일 읽기가 끼면 캐시 무력화가 잦음. 5분 TTL도 압박.
- **의존성**: 테스트 작성 한 번이면 끝. 이후 실행은 Claude를 거치지 않으니 캐시 이슈 자체가 없음.

### 5-4. 도구 정의(schema) 자체의 비용

- Playwright MCP 서버를 등록하면 ~20개 액션 도구의 schema가 컨텍스트에 로드됨 (수백~1k 토큰).
- 단, Claude Code의 deferred tools 메커니즘이 적용되면 `ToolSearch`로 필요한 것만 끌어오므로 상시 비용은 줄어듦.

### 5-5. 100회 회귀 누적 비용 시나리오

게시판에 "댓글 기능"을 추가하고 회귀 검증을 100번 돌린다고 가정.

| 항목 | MCP 방식 | 의존성 방식 |
|---|---|---|
| 최초 검증 (1회) | ~15k 토큰 | spec.js 작성 ~1k 토큰 |
| 회귀 99회 (CI/로컬) | ~15k × 99 ≈ **1.5M 토큰** | **0 토큰** |
| 합계 | ≈ 1.5M 토큰 | ≈ 1k 토큰 |

회귀가 반복될수록 격차는 기하급수.

## 6. 결론

> **둘은 경쟁 관계가 아니라 보완 관계.**
>
> - **탐색·일회성 검증** → MCP. 적은 횟수면 토큰 비용도 감내 가능.
> - **회귀·CI 게이트** → 의존성. 토큰 비용이 사실상 0이고, 100번 돌리든 1000번 돌리든 동일.

이 프로젝트(Test02)의 `tester` 서브에이전트가 **반복 회귀 검증** 역할이라는 점에서, 토큰 효율 측면에서도 의존성 방식이 압도적으로 유리하다. MCP Playwright는 필요 시 **탐색·디버깅용 손도구**로 추가 등록하는 옵션 정도로 두는 것이 적절.
