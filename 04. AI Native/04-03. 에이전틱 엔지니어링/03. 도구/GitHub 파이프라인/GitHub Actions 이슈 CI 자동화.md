
CI 파이프라인에서 문제가 발견되었을 때의 처리 흐름과 자동화 방법에 대해 설명해 드릴게요.

### 1. 테스트 실패 시 PR은 어떻게 되나요?
PR 요청 중 CI(테스트)가 실패하면 다음과 같이 진행됩니다:

*   **상태 표시**: PR 페이지 하단에 빨간색 **X** 표시와 함께 "All checks have failed"라는 메시지가 뜹니다.
*   **병합 차단**: 만약 레포지토리 설정(Branch Protection Rule)에서 "Require status checks to pass before merging"을 켜두었다면, **Merge 버튼이 비활성화**되어 아예 합칠 수 없게 됩니다. (가장 권장되는 설정입니다.)
*   **수정 과정**: 개발자는 로그를 확인해 문제를 파악하고, 본인의 브랜치에서 코드를 수정하여 다시 `push` 합니다. 그러면 CI가 자동으로 다시 돌고, 성공하면 그때서야 초록색 체크와 함께 Merge 버튼이 활성화됩니다.

---

### 2. 이슈(Issue) 등록이 가능한가요?
네, 가능합니다! GitHub Actions에는 **"이전 단계가 실패했을 때만 실행되는 단계"**를 만들 수 있는 기능이 있습니다.

워크플로우 파일(`ci.yml`)에 다음과 같은 단계를 추가하면 테스트 실패 시 자동으로 이슈를 생성할 수 있습니다.

```yaml
    - name: Create Issue on Failure
      if: failure()  # 앞선 단계(테스트 등)가 실패했을 때만 실행
      uses: actions/github-script@v7
      with:
        script: |
          github.rest.issues.create({
            owner: context.repo.owner,
            repo: context.repo.repo,
            title: `❌ CI 실패 리포트: ${context.payload.pull_request.title}`,
            body: `PR #${context.issue.number} 에서 테스트가 실패했습니다. 로그를 확인해 주세요!`
          })
```

### 3. 실무에서는 어떻게 하나요?
보통 PR 단계에서의 실패는 **이슈를 따로 등록하기보다는 PR 안에서 해결**하는 것이 일반적입니다. PR 자체가 이미 "검토 중인 공간"이기 때문입니다.

대신 다음과 같은 방식을 많이 사용합니다:
*   **Slack/Discord 알림**: 테스트 실패 시 개발팀 채팅방으로 즉시 알림을 보냅니다.
*   **댓글 자동 작성**: 이슈를 새로 만들기보다, 해당 PR에 "테스트가 실패했습니다"라는 댓글을 자동으로 달아줍니다.
*   **이슈 등록은 언제?**: PR이 아니라 `main` 브랜치(이미 합쳐진 코드)에서 정기적으로 실행되는 테스트가 실패했을 때는, 즉시 해결해야 하는 버그이므로 이슈를 자동으로 등록하도록 설정하는 경우가 많습니다.

### 요약
1.  CI 실패 시 PR은 **병합이 차단**되도록 설정하는 것이 표준입니다.
2.  `if: failure()` 옵션을 통해 **자동 이슈 등록이 가능**합니다.
3.  다만 PR 단계에서는 이슈 등록보다는 **PR 내 댓글 알림**이나 **채팅 알림**을 더 선호합니다.
