
# 린터/코드 검사 배치 결정 원칙

## Context

사용자가 "린터 수행은 hooks와 skill 중 어디가 적절한가?"를 질문. 특정 도구나 구현 작업이 아닌 **일반 원칙 정리**가 목적. Claude Code의 두 확장 메커니즘(hooks, skills)은 트리거 방식·결정론성·강제력이 달라 같은 작업이라도 어디에 두느냐에 따라 신뢰성과 유지비용이 크게 달라진다. 이 문서는 향후 린터·포매터·테스트·검증 작업을 어디에 배치할지 판단할 수 있도록 결정 기준을 정리한다.

---

## 핵심 결론

|작업 성격|적절한 위치|
|---|---|
|도구 기반 결정론적 검사 (eslint, prettier, ruff, tsc)|**Hooks**|
|Claude의 판단이 필요한 코드 리뷰|**Skill**|
|둘 다 필요한 경우|**둘 다** (역할 분리)|

**기본 원칙**: 매번 똑같이 실행되어야 하는 일은 hooks, 상황에 따라 판단이 필요한 일은 skill.

---

## 결정 기준

### Hooks가 적절한 경우

다음 중 **하나라도** 해당하면 hooks:

1. **결정론적**: 입력이 같으면 출력도 같다 (linter, formatter, type checker, test runner)
2. **매번 실행되어야 함**: Claude가 잊으면 안 되는 작업 — 하네스가 강제 실행
3. **빠르고 자동화 가능**: shell 명령 한 줄로 끝남
4. **편집 직후/턴 종료 직전에 묶이는 작업**: `PostToolUse` (Edit/Write 후), `Stop` (턴 종료 시)
5. **실패 시 Claude에게 즉시 피드백**: 종료 코드와 stderr를 컨텍스트로 주입해 같은 턴에서 수정 유도

**예시**:

- `PostToolUse` on Edit/Write → 변경된 파일에 `eslint --fix` 실행
- `Stop` → 전체 프로젝트 `tsc --noEmit` 또는 테스트 실행해 통과 못하면 차단
- `PreToolUse` on Bash → 위험 명령 차단

### Skill이 적절한 경우

다음 중 **하나라도** 해당하면 skill:

1. **판단이 필요함**: 어떤 파일을 검사할지, 어느 정도까지 엄격할지 Claude가 결정
2. **여러 단계 절차**: 단순 명령이 아닌 다단계 워크플로우 (리뷰 → 분류 → 우선순위화 → 제안)
3. **설명·교육 목적**: 왜 문제인지, 어떻게 고쳐야 하는지 자연어로 안내
4. **선택적/명시 호출**: 사용자가 원할 때만 실행 (`/review` 같은 슬래시 커맨드)
5. **도구가 없는 영역**: 네이밍, 일관성, 가독성, 아키텍처 — 자동화 도구로 표현 어려운 규범

**예시**:

- `/review` — 변경된 코드 전체를 보고 가독성·일관성·잠재 버그 리뷰
- `/security-review` — 보안 관점에서 변경분 점검
- `/simplify` — 중복·복잡도 검토 후 리팩토링 제안

### 헷갈릴 때 빠른 판별 질문

- "shell 명령으로 정확한 종료 코드가 나오는가?" → **Hooks**
- "사람이 보고 판단해야 하는 영역인가?" → **Skill**
- "Claude가 깜빡하면 사고가 나는가?" → **Hooks** (강제력 필요)
- "매번 돌리면 비용/소음이 큰가?" → **Skill** (선택적 호출)

---

## 안티패턴

- **Skill에 린터를 둠**: Claude가 호출을 잊으면 검증 누락. 결정론적 작업은 강제 실행이 핵심.
- **Hook에서 자연어 리뷰**: Hook은 짧고 빠르고 결정론적이어야 함. 판단 작업은 컨텍스트와 토큰이 필요해 hook에서 돌리면 출력이 지저분해지고 매 편집마다 비용 발생.
- **Hook에서 자동 commit/push**: 결정론적이지만 사용자 승인 없이 일어나면 안 되는 작업. 손쉬운 작업이라도 부작용이 큰 일은 명시 호출(skill 또는 명령)로.
- **Hook 출력을 무시**: PostToolUse hook이 실패해도 Claude가 무시하도록 두면 hook의 의미가 없음. 실패 시 stderr를 컨텍스트로 주입해 Claude가 보도록 설계.

## 실무 배치 패턴 (참고)

전형적 구성:

1. **Hooks (자동, 강제)**
    - `PostToolUse` on Edit/Write: 해당 언어 포매터 + 린터 `--fix`
    - `Stop`: 타입 체크 또는 빠른 테스트 — 실패 시 턴 차단
2. **Skill (수동, 판단)**
    - `/review`: 다단계 리뷰 (구조·네이밍·테스트 커버리지·문서)
    - `/security-review`: 보안 관점 검토

이렇게 분리하면 **기계적 정합성은 hooks가 보장**, **품질·맥락 판단은 skill이 담당**하여 역할 충돌이 없다.
