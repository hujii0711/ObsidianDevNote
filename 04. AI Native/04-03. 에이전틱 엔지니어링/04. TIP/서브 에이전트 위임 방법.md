

서브에이전트는 언제 사용하냐면
메인 컨텍스트가 작업을 하는데 컨텍스트가 모자랄 것 같을 때 서브에이전트를 생성하는 것이 좋다.
예를 들어 어떤 큰 리팩토링 작업을 해야 된다. 그런 것을 작업을 7단계로 쪼개서 진행하다보면 컨텍스트가 꽉 차게된다. 그때부터 퀄리티가 떨어진다.

---

## Claude Code에서 전문 서브에이전트에게 작업을 위임하는 방법

### 1. 서브에이전트 파일 구조

서브에이전트는 YAML frontmatter가 있는 마크다운 파일로 정의합니다. 기본 형식은 다음과 같습니다:

```markdown
---
name: code-reviewer
description: 코드 변경 후 즉시 사용. 버그, 보안, 코드 품질을 검토하는 전문가.
tools: Read, Grep, Glob
model: sonnet
permissionMode: default
---

You are a senior code reviewer. When invoked, check for:
- Security vulnerabilities
- Performance issues
- Code style violations
Return findings as a prioritized list with file/line references.
```

`description` 필드가 핵심입니다. Claude는 각 서브에이전트의 `description`을 읽고 어떤 작업을 위임할지 결정하므로, 언제 사용해야 하는지 명확하게 작성해야 합니다.

---

### 2. 파일 저장 위치 (스코프)

|위치|스코프|우선순위|
|---|---|---|
|`--agents` CLI 플래그|현재 세션만|높음|
|`.claude/agents/`|현재 프로젝트|중간|
|`~/.claude/agents/`|모든 프로젝트|낮음|

프로젝트 서브에이전트(`.claude/agents/`)는 버전 컨트롤에 커밋해서 팀 전체가 공유하는 방식이 권장됩니다.

---

### 3. 위임 방식 3가지

위임 방식은 크게 네 가지입니다:

**① 자동 위임 (권장)** — Claude가 `description`을 보고 알아서 라우팅

```
# 사용자가 그냥 요청하면 Claude가 알아서 적절한 서브에이전트를 선택
"auth 모듈에서 보안 취약점 확인해줘"
→ Claude가 security-reviewer 서브에이전트로 자동 위임
```

**② 이름으로 명시적 지시**

```
"test-runner 서브에이전트로 실패한 테스트 고쳐줘"
```

**③ @-멘션**

```
"@code-reviewer로 이 PR 검토해줘"
```

---

### 4. 내장 서브에이전트 (빌트인)

Claude Code는 기본 내장 서브에이전트를 포함합니다:

- **Explore**: Haiku 모델, 읽기 전용 코드베이스 탐색 전용 (빠르고 저렴)
- **Plan**: 플랜 모드에서 컨텍스트 수집용, 읽기 전용
- **General-purpose**: 탐색 + 수정이 모두 필요한 복잡한 작업용

---

### 5. 실전 전문가 팀 구성 예시

복잡한 프로젝트에서는 실제 애자일 팀 구조를 반영하는 것이 효과적입니다. 일반적인 역할 구성은: Architect/Planner(Opus), Builder/Developer(Sonnet), Validator/Tester(Sonnet) 입니다.

```
.claude/agents/
├── architect.md      # 설계·계획 (Opus, 읽기 전용)
├── developer.md      # 구현 (Sonnet, 전체 툴)
├── test-runner.md    # 테스트 실행·수정 (Sonnet, Bash 포함)
├── security.md       # 보안 분석 (Sonnet, 읽기 전용)
└── docs-writer.md    # 문서 작성 (Haiku, Write 포함)
```

---

### 6. 주의사항

자동 라우팅의 신뢰도는 아직 완벽하지 않습니다. Claude가 명시적으로 관련된 서브에이전트가 있어도 메인 세션에서 직접 처리하는 경우가 있으며, 가장 확실한 트리거는 명시적 호출입니다. 또한 Claude Opus 4.6은 불필요하게 서브에이전트를 과도하게 생성하는 경향이 있습니다.

따라서 실용적인 접근법은:

- `description`에 **"Use proactively when..."** 같은 행동 지향적 문구를 포함
- 복잡한 워크플로우는 CLAUDE.md에 위임 규칙을 명시적으로 작성
- 자동 라우팅이 불안정하면 `@-mention`이나 이름 지시로 명시적 호출

### (보충) 자동위임 동작 원리

Claude는 태스크 설명과 컨텍스트를 기반으로 자동 라우팅합니다. `description` 필드를 읽고 현재 요청과 매칭되면 해당 서브에이전트로 위임합니다.

즉, 이론적인 흐름은:

```
사용자: "auth.py 코드 리뷰해줘"
         ↓
Claude: .claude/agents/ 스캔
         ↓
code-reviewer.md의 description 확인
         ↓
매칭 → Agent 툴로 자동 위임
         ↓
서브에이전트가 독립 컨텍스트에서 실행 후 결과 반환
```

---

### 현실적인 주의점

자동 선택은 아직 신뢰도가 떨어집니다. 에이전트가 명시적으로 관련되어 있고 description이 태스크와 일치해도, Claude가 메인 세션에서 직접 처리하는 경우가 자주 있습니다. 이것은 알려진 버그이며 GitHub에 오픈 이슈가 있습니다.

그래서 `description`을 잘 작성하는 것이 핵심입니다. 자동 라우팅을 높이는 작성 패턴:

```yaml
# 나쁜 예 — 너무 모호함
description: Code reviewer

# 좋은 예 — 언제 사용할지 행동 지향적으로 명시
description: >
  Use proactively after any code changes or when asked to review code.
  Checks for bugs, security issues, and code quality problems.
```

`"Use proactively when..."`, `"Use after..."`, `"Use whenever..."` 같은 표현이 자동 라우팅 트리거에 효과적입니다.

---

### 확실한 방법

자동 위임이 불안정할 때는 명시적으로 호출하는 것이 가장 확실합니다:

```
# 이름으로 지시
"code-reviewer 서브에이전트로 auth.py 리뷰해줘"

# @-멘션
"@code-reviewer auth.py 리뷰해줘"
```

결론적으로, 자동 위임은 되긴 하지만 100% 신뢰하기엔 아직 불안정하므로 중요한 워크플로우라면 명시적 호출을 병행하는 것이 현실적입니다.

### 사전 준비: 서브에이전트 파일

모든 전략이 공통으로 사용하는 에이전트 파일입니다.

```
.claude/agents/code-reviewer.md
```

```yaml
---
name: code-reviewer
description: >
  Use proactively after any code changes or when asked to review code.
  Checks for bugs, security issues, code quality, and test coverage.
tools: Read, Grep, Glob, Bash
model: sonnet
permissionMode: default
---

You are a senior code reviewer.

When invoked:
1. Run `git diff HEAD` to see recent changes
2. Focus on modified files only
3. Review for: readability, error handling, security, test coverage

Return findings organized by priority:
- Critical (must fix before merge)
- Warnings (should fix)
- Suggestions (nice to have)
```

### 전략 1. Hooks — 100% 결정론적 자동 실행

훅의 `agent` 타입은 `Read`, `Grep`, `Glob` 같은 툴 접근이 가능한 서브에이전트를 직접 스폰합니다. `command` 타입보다 느리지만 코드베이스를 실제로 탐색할 수 있습니다.

파일 편집 후 자동으로 코드 리뷰 에이전트를 트리거하는 방법:

```json
// .claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit|MultiEdit",
        "hooks": [
          {
            "type": "agent",
            "prompt": "Run the code-reviewer agent on the file that was just modified: $CLAUDE_TOOL_INPUT_FILE_PATH",
            "timeout": 120
          }
        ]
      }
    ]
  }
}
```

> **동작**: `Write`, `Edit`, `MultiEdit` 툴 실행 직후 → 조건 없이 코드 리뷰 에이전트 자동 실행. 사용자가 아무것도 하지 않아도 됩니다.

특정 조건일 때만 트리거하는 고급 패턴 (bash 스크립트 연동):

```bash
# .claude/hooks/review-on-change.sh
#!/bin/bash
INPUT=$(cat)
FILE=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

# .ts, .py 파일 변경 시에만 트리거
if echo "$FILE" | grep -qE '\.(ts|py)$'; then
  echo '{"additionalContext": "Trigger code-reviewer agent for this file change."}'
fi
exit 0
```

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": ".claude/hooks/review-on-change.sh"
          }
        ]
      }
    ]
  }
}
```

### 전략 2. Skill (Slash Command) — `/review-pr`로 위임

skill의 frontmatter에 `agent` 필드를 지정하면 `/slash-command` 호출이 해당 서브에이전트로 위임됩니다. `/security-scan`을 입력하면 security 에이전트가 스폰되는 식입니다.

```
.claude/skills/review-pr/SKILL.md
```

```yaml
---
name: review-pr
description: PR 코드 리뷰 실행. 변경된 파일 전체를 code-reviewer 에이전트로 검토.
agent: code-reviewer
invocation: user
disable-model-invocation: true
---

# PR 코드 리뷰

다음 순서로 실행하세요:

1. `git diff main...HEAD --name-only`로 변경 파일 목록 확인
2. 변경된 모든 파일을 code-reviewer 에이전트에 전달
3. 결과를 Critical / Warnings / Suggestions로 구분해 보고

대상 파일: $ARGUMENTS (미지정 시 전체 변경 파일)
```

사용:

```
/review-pr src/auth/
```

> **동작**: `/review-pr` 입력 → skill이 `code-reviewer` 에이전트를 직접 스폰 → 독립 컨텍스트에서 실행 후 결과 반환. `disable-model-invocation: true`로 설정하면 Claude가 자동으로 트리거하지 않고 오직 사용자가 명시적으로 `/review-pr`을 입력할 때만 실행됩니다.

### 전략 3. @-mention / 이름 지시 — 가장 직접적인 호출

```
# @-멘션 방식
@code-reviewer auth.py의 JWT 처리 로직 검토해줘

# 이름 지시 방식
code-reviewer 에이전트로 src/payment/ 디렉토리 전체 리뷰해줘

# 명시적 위임 요청
최근 커밋의 변경사항을 code-reviewer 에이전트에게 위임해서 리뷰해줘
```

> **동작**: 에이전트 이름을 명시하면 Claude가 `.claude/agents/`에서 해당 파일을 찾아 Agent 툴로 직접 위임합니다. 자동 라우팅 불안정 문제를 완전히 우회합니다.

### 전략 4. CLAUDE.md 위임 규칙 — 오케스트레이터 지시

```markdown
# CLAUDE.md

## 에이전트 위임 규칙

### 코드 변경 시 (필수)
- 3개 이상의 파일을 수정했다면 반드시 `code-reviewer` 에이전트로 검토를 위임하라.
- auth/, security/, payment/ 경로의 파일을 수정했다면 **즉시** `code-reviewer`를 실행하라.
- 수정 직후 메인 세션에서 직접 리뷰하지 말고, 항상 에이전트에 위임하라.

### PR 생성 전 (필수)
Before creating any PR, ALWAYS delegate to the `code-reviewer` agent first.
Do NOT create a PR until code-reviewer has completed and returned findings.

### 테스트 작성 시
- 새 테스트 파일 작성 후 `test-runner` 에이전트로 실행 및 검증을 위임하라.
```

> **동작**: Claude가 CLAUDE.md를 읽고 조건 충족 시 명시된 에이전트로 스스로 위임합니다. CLAUDE.md 지시는 약 80% 신뢰도로 따르므로 중요한 규칙은 "ALWAYS", "MUST", "Do NOT ... until" 같은 강제 표현을 사용하는 것이 효과적입니다.

### 전략 5. Dynamic Workflows — JS 코드로 실행 순서 고정

Workflows는 제어 흐름 자체를 결정론적으로 고정합니다. 오케스트레이션 로직은 코드로 작성되고, 각 `agent()` 호출 내부의 작업만 모델이 처리합니다.

프롬프트에 `workflow` 단어를 포함시키면 Claude가 JS 오케스트레이션 스크립트를 자동 작성합니다:

```
PR 머지 전 workflow를 실행해줘:
1. code-reviewer 에이전트로 코드 품질 검토
2. security-reviewer 에이전트로 보안 취약점 스캔
3. test-runner 에이전트로 테스트 커버리지 확인
세 에이전트는 병렬로 실행하고 결과를 통합해서 보고해줘
```

Claude가 내부적으로 생성하는 오케스트레이션 스크립트 (개념):

```javascript
// Claude가 자동 생성하는 workflow script
const [reviewResult, securityResult, testResult] = await Promise.all([
  agent("code-reviewer", { task: "Review all changed files in this PR" }),
  agent("security-reviewer", { task: "Scan for OWASP vulnerabilities" }),
  agent("test-runner", { task: "Run test suite and report coverage" })
]);

return synthesize([reviewResult, securityResult, testResult]);
```

저장해서 재사용 가능한 `/pr-gate` 커스텀 workflow로 만들기:

```yaml
# .claude/skills/pr-gate/SKILL.md
---
name: pr-gate
description: PR 머지 전 3-에이전트 병렬 검증 workflow
invocation: user
disable-model-invocation: true
---

다음 workflow를 실행하세요:

병렬로 아래 세 에이전트를 동시에 실행:
1. `code-reviewer` — 코드 품질 및 가독성 검토
2. `security-reviewer` — 보안 취약점 스캔
3. `test-runner` — 테스트 실행 및 커버리지 확인

모든 에이전트 완료 후 결과를 통합하여 PASS / FAIL 판정을 내려라.
FAIL 조건: Critical 이슈 1개 이상 OR 보안 취약점 발견 OR 테스트 실패
```

사용:

```
/pr-gate
```

### 전략 선택 가이드

| 상황              | 권장 전략                                    |
| --------------- | ---------------------------------------- |
| 파일 수정 후 항상 리뷰   | Hooks (PostToolUse)                      |

| 프로젝트 전반의 암묵적 규칙 | CLAUDE.md 위임 규칙                          |
| 여러 에이전트 병렬 실행   | Dynamic Workflows                        |
