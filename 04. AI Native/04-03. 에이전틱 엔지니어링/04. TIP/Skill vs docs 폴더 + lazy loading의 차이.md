
사실 **이 프로젝트는 이미 두 방식을 동시에 쓰고 있다** — `.claude/skills/`는 스킬 방식, `_workspace/*.md`는 정확히 "docs + lazy read" 방식이다. 그래서 둘의 차이를 이 프로젝트에 빗대 설명하면 명확하다.

## 본질적 차이는 "트리거"에 있다

||**Skill**|**docs/ + lazy read**|
|---|---|---|
|발견 방식|description이 항상 노출되어 **모델이 스스로 "지금 이걸 써야겠다" 판단**|누군가 **경로와 시점을 미리 알고** 읽어줘야 함|
|"언제 쓰는가"의 위치|스킬 frontmatter의 description (하네스가 효율적으로 관리)|호출하는 프롬프트/CLAUDE.md 안에 박혀 있어야 함 (항상 로드됨)|
|로딩|2단계 — 평소 description만, 호출 시 본문|1단계 — 읽으면 통째로 (직접 부분 읽기 가능)|
|실행 의미|Skill 도구로 **호출**(invoke). 로깅·`allowed-tools` 권한 스코프 가능|그냥 텍스트를 컨텍스트에 주입. 실행/권한 개념 없음|
|접근 권한|에이전트 `tools`에 **Skill 도구**가 있어야 함|**Read만** 있으면 누구나|
|표준·이식성|표준 포맷, `/` 메뉴 노출, 플러그인·마켓 공유|프로젝트 로컬 관습. 툴이 인식 못 함|

## 가장 큰 실질 차이: 자동 발견 vs 명시적 읽기

**Skill의 핵심 가치는 "모델이 스스로 발견해서 호출한다"이다.**

- 사용자가 "쇼핑몰 만들어줘"라고만 해도, 메인 Claude는 `shopping-mall-builder`의 description을 보고 _스스로_ "이 요청엔 이 스킬이다" 판단해 로드한다. 아무도 경로를 알려주지 않았다.
- 이걸 docs로 하면? `docs/shopping-mall-builder.md`가 있어도, **누군가 "쇼핑몰 요청이면 이 파일을 읽어라"는 지시를 어딘가에 박아둬야** 한다. 그 지시(인덱스)는 결국 [CLAUDE.md](http://claude.md/) 같은 **항상 로드되는 곳**에 살아야 하고, 문서가 50개면 인덱스 50줄이 영구히 컨텍스트를 차지한다.

스킬은 이 "인덱스 비용"을 하네스가 description 레지스트리로 대신 관리해 주는 셈이다.

## 반대로 docs + lazy read가 정답인 경우

**"실행할 절차"가 아니라 "읽을 데이터"이고, 읽을 시점·경로가 명확할 때.**

이 프로젝트의 `_workspace/` 산출물이 정확히 그렇다:

- `02_data_schema.prisma`, `03_be_api_spec.md` 등은 **자동 발견이 필요 없다.** 파이프라인 순서상 "ux는 확정 스키마를 읽는다", "frontend는 API 스펙을 읽는다"가 이미 정해져 있고, 그 경로가 스폰 프롬프트에 하드코딩돼 있다.
- 이걸 스킬로 만들면 오히려 과하다 — 자동 트리거도 필요 없고, 매번 새로 생성되는 산출물이라 표준 포맷도 무의미하다.

즉 **`_workspace/`를 docs+lazy read로 둔 건 올바른 설계**이고, **절차(`write-prd`, `shopping-mall-builder`)를 스킬로 둔 것도 올바른 설계**다.

## 만약 스킬을 전부 docs로 옮긴다면

잃는 것:

1. **자동 발견** — 메인 Claude가 "쇼핑몰 요청 → builder 로드"를 스스로 못 하고, CLAUDE.md에 "쇼핑몰이면 docs/builder.md 읽어라"를 영구 명시해야 함.
2. **2단계 progressive disclosure** — description만 노출하는 효율을 직접 인덱스로 재구현해야 함.
3. **`/` 메뉴 호출·권한 스코프·이식성** — 전부 사라짐.

얻는 것:

- **결정성** — 모델의 자율 판단 없이 "정확히 이 시점에 이 파일"만 읽음. 자동 트리거가 오히려 방해될 때 유리.
- **접근성** — Read만 있으면 됨(Skill 도구 불필요). 단, 이 프로젝트 에이전트들은 이미 Skill 도구를 가짐.

## 결론

둘은 "어느 쪽이 우월"이 아니라 **트리거 모델이 다르다.**

- **모델이 스스로 "써야 할 때"를 판단해야 하는 절차** → Skill (예: 오케스트레이션 진입, 역할별 작업 절차)
- **읽을 시점·경로가 이미 결정돼 있는 참조 데이터** → docs + lazy read (예: `_workspace/` 산출물)

이 프로젝트는 우연이 아니라 의도적으로 둘을 적재적소에 나눠 쓰고 있고, 그게 맞는 선택이다. "전부 docs로 통일"하면 자동 발견이라는 스킬의 유일하고 핵심적인 가치를 버리고 그 자리를 영구 인덱스 비용으로 메우게 된다.
