리뷰 단계는 "이 코드를 본격적으로 세상에 내보내기 전에, 다른 시각으로 한 번 더 검증하는" 단계입니다. 단순히 "코드가 돌아가는가"를 넘어, **장기적으로 유지보수할 가치가 있는가, 팀의 자산이 될 수 있는가**를 판단합니다.

Claude Code 환경에서는 리뷰의 의미가 더 커집니다. AI가 만든 코드는 "통과는 하지만 미묘하게 어색하거나, 그럴듯하지만 틀린" 경우가 많아서, **사람의 비판적 시선과 다른 AI의 다른 시각**이 모두 필요합니다. 리뷰는 AI 코드의 품질을 보장하는 마지막 안전망입니다.

## 리뷰 단계의 구체적 작업

### 1. 셀프 리뷰 (Self-Review)

리뷰의 시작은 **본인이 먼저 자기 코드를 객관적으로 보는 것**입니다.

- **PR을 올리기 직전에 `git diff` 전체 훑기**: 작성할 때와 다른 시각이 생깁니다
- **"내가 리뷰어라면 뭐라고 할까?"** 시점 전환
- **체크할 것**:
    - 디버그 코드, console.log, 주석 처리된 코드
    - 하드코딩된 값 (URL, 매직 넘버, 시크릿)
    - TODO/FIXME가 남아있는데 PR에 포함되어도 되는지
    - 변수/함수 이름이 최선인지
    - 누락된 에러 처리
    - 누락된 테스트
    - 불필요한 변경 (포맷팅만 바꾼 파일 등)

이 단계를 거르고 PR을 올리면, 리뷰어가 "본인이 발견할 수 있었던 것"을 지적하게 되어 시간 낭비입니다.

### 2. PR(Pull Request) 작성

리뷰가 잘 되려면 **리뷰어가 맥락을 빠르게 파악**할 수 있어야 합니다.

**좋은 PR의 조건**:

- **작다**: 변경 라인 수 400 이하가 이상적, 1000 넘으면 분리 고려
- **단일 목적**: 한 PR = 한 가지 변경. "리팩토링 + 새 기능"은 분리
- **제목**: 무엇을 했는지 한 문장 (Conventional Commits 스타일)
- **설명에 들어가야 할 것**:
    - **왜** 변경했는가 (배경, 문제)
    - **무엇을** 변경했는가 (핵심 변경 사항 요약)
    - **어떻게** 검증했는가 (테스트 방법, 스크린샷)
    - **리뷰 포인트** (특히 봐줬으면 하는 부분)
    - **트레이드오프 / 미해결 사항**
    - **관련 이슈 링크**
- **PR 템플릿 활용**: 빈 PR 설명은 게으름의 표시

### 3. 자동화된 검증 통과 (Automated Checks)

사람이 리뷰하기 전에 **CI가 먼저 검증**합니다.

- **빌드 성공**
- **린트 통과**
- **타입 체크 통과**
- **테스트 통과** (단위/통합/E2E)
- **커버리지 임계값 충족**
- **보안 스캔 통과** (Snyk, gitleaks 등)
- **번들 사이즈 체크** (프론트엔드)

이게 빨갛게 떠있는데 리뷰 요청하는 건 예의 위반입니다. **녹색 빌드 후 리뷰 요청**이 원칙입니다.

### 4. 코드 리뷰 (Peer Review)

이제 사람이 리뷰합니다. **무엇을 봐야 하는지**가 가장 중요합니다.

#### 4-1. 정확성 (Correctness)

- 의도한 동작을 하는가?
- 엣지 케이스를 처리하는가? (null, 빈 배열, 음수, 동시성)
- 에러 처리가 적절한가?
- 비즈니스 로직이 사양과 일치하는가?

#### 4-2. 설계 (Design)

- 기존 아키텍처와 일관되는가?
- 책임 분리(SRP)가 적절한가?
- 추상화 레벨이 맞는가? (너무 일찍/과하게 추상화하지 않았나)
- 새 의존성 도입이 정당한가?
- 다른 모듈에 미치는 영향을 고려했는가?

#### 4-3. 가독성 (Readability)

- 이름이 의도를 드러내는가?
- 함수가 짧고 한 가지 일만 하는가?
- 주석이 "왜"를 설명하는가? (코드가 못 말하는 것을)
- 새로 합류한 사람이 이해할 수 있는가?

#### 4-4. 테스트 (Testing)

- 변경된 동작에 대한 테스트가 있는가?
- 테스트가 의미 있는가? (단언이 약하지 않은가)
- 회귀 테스트가 필요한 버그 픽스인가?

#### 4-5. 보안 (Security)

- 사용자 입력을 검증하는가?
- 인증/인가 체크가 빠지지 않았는가?
- 시크릿이 코드에 들어가지 않았는가?
- SQL 인젝션, XSS 같은 일반 취약점은 없는가?
- 로그에 민감 정보가 남지 않는가?

#### 4-6. 성능 (Performance)

- N+1 쿼리 같은 명백한 문제는 없는가?
- 큰 데이터 처리에 메모리 문제 없는가?
- 불필요한 렌더링/연산은 없는가?
- 외부 API 호출이 적절한가? (캐싱, 배치)

#### 4-7. 컨벤션 (Conventions)

- 프로젝트 코드 스타일 일치
- 명명 규칙 일치
- 파일/폴더 구조 규칙 일치
- 커밋 메시지 컨벤션 일치

#### 4-8. 문서화 (Documentation)

- 공개 API에 주석이 있는가?
- README, 설계 문서가 업데이트되었는가?
- 변경 로그(CHANGELOG)가 갱신되었는가?

### 5. 리뷰 코멘트 작성 원칙

리뷰는 코드를 보는 것만큼이나 **어떻게 말하느냐**가 중요합니다.

- **코드를 비판하되 사람을 비판하지 않기**: "이 함수는 ~"이지 "당신은 왜 ~"가 아님
- **명령보다 질문**: "~로 바꾸세요"보다 "~로 하면 어떨까요? 이유는 ~"
- **이유 설명**: 의견의 근거를 항상 제시
- **심각도 표시**: `[blocking]`, `[suggestion]`, `[nitpick]`, `[question]`, `[praise]` 같은 라벨
- **좋은 부분 칭찬도**: 잘된 부분도 명시적으로
- **대안 제시**: 문제만 지적하지 말고 가능하면 해결책도
- **링크와 근거**: 패턴 문서, 공식 가이드 링크

예시:

> `[suggestion]` 이 로직은 `src/shared/utils/validation.ts`의 패턴과 비슷한데, 거기 헬퍼를 재사용하면 어떨까요? 컨벤션과도 맞을 것 같습니다.

### 6. 리뷰 응답 (Author 입장)

리뷰를 받는 쪽의 매너도 중요합니다.

- **모든 코멘트에 응답**: 수정했거나, 동의 안 하는 이유를 적거나
- **반박은 합리적으로**: 감정이 아니라 근거로
- **합의가 안 되면 에스컬레이션**: 시니어/팀 리드에게
- **수정 후 force-push 대신 새 커밋**: 리뷰어가 변경분을 보기 쉽도록 (PR 머지 직전 squash는 OK)
- **재리뷰 요청 명시**: "수정 완료, 재확인 부탁드립니다"

### 7. 승인 & 머지 기준

언제 머지할 수 있는가에 대한 명확한 규칙이 필요합니다.

- **필수 승인 수**: 최소 1명, 중요 코드는 2명
- **블로킹 코멘트 모두 해결**
- **모든 CI 체크 통과**
- **최신 main 브랜치와 머지/리베이스 완료**
- **머지 전략**: Squash / Merge commit / Rebase 중 팀 컨벤션 따르기
- **머지 후 브랜치 삭제**

### 8. 리뷰 외 추가 검토

코드 리뷰 외에 PR 단계에서 함께 확인할 것:

- **디자인 리뷰**: UI 변경이면 디자이너가 확인
- **PM 리뷰**: 기능 변경이면 사양 일치 여부
- **DBA/SRE 리뷰**: 스키마 변경, 인프라 변경
- **법무/보안팀 리뷰**: 개인정보, 결제, 외부 데이터 노출 시
- **번역/i18n**: 다국어 지원이면 번역 파일 검토

### 9. 리뷰 메트릭 추적

조직 차원에서 리뷰 프로세스를 개선하려면 측정해야 합니다.

- **리뷰 응답 시간** (PR 생성 → 첫 리뷰)
- **머지까지 걸리는 시간**
- **PR 크기 분포**
- **리뷰당 코멘트 수**
- **리뷰 후 발견된 버그 비율**

이 지표들이 나빠지면 프로세스 자체를 점검합니다.

### 10. 리뷰 문화 정착

도구만으로는 안 됩니다.

- **리뷰는 학습 기회**: 신입에게도 시니어 코드 리뷰하게 하기
- **PR 작은 단위 유지**: 리뷰 부담 낮추기
- **24시간 룰**: PR이 하루 이상 방치되지 않게
- **페어 프로그래밍**: 복잡한 코드는 리뷰 대신 페어로
- **회고에서 리뷰 프로세스 점검**

## 서브에이전트 활용 방안

리뷰 단계는 서브에이전트가 가장 빛나는 단계입니다. 사람 리뷰어의 시간은 비싸고 한정적이지만, AI 리뷰어는 **모든 PR에 1차 검토**를 제공할 수 있습니다. 핵심은 **"사람 리뷰를 대체"가 아니라 "사람 리뷰의 부담을 줄이고 품질을 높이는 1차 필터"** 로 쓰는 것입니다.

### 패턴 1: 시니어 엔지니어 리뷰어 (Senior Reviewer)

**역할**: "PR diff를 시니어 엔지니어 관점에서 비판적으로 리뷰"

시스템 프롬프트 예시:

> "당신은 10년 경력의 까다로운 시니어 엔지니어다. 다음 관점에서 비판적으로 리뷰하라: 정확성, 설계, 가독성, 테스트, 보안, 성능. 칭찬은 생략하고 개선점만 지적하라. 각 지적은 `[blocking]`, `[suggestion]`, `[nitpick]` 중 하나로 분류하고, 이유와 가능한 해결책을 함께 제시하라."

**효과**: 사람 리뷰어가 보기 전에 사소한 지적은 모두 해결됨. 사람은 진짜 중요한 결정에만 집중.

### 패턴 2: 보안 리뷰어 (Security Reviewer)

**역할**: "보안 취약점만 집중 검토"

시스템 프롬프트에 박아둘 것:

- OWASP Top 10
- CWE 일반 패턴
- 회사 보안 정책
- 절대 금지 사항 (시크릿 하드코딩, 검증 없는 SQL 등)

검토 항목:

- 입력 검증 누락
- 인증/인가 우회 가능성
- 시크릿/민감 정보 노출
- 인젝션 취약점 (SQL, XSS, 커맨드)
- 안전하지 않은 역직렬화
- CORS, CSP 설정
- 의존성 취약점

**왜 별도인가**: 일반 리뷰어는 보안을 종종 놓칩니다. 전용 에이전트는 보안만 본다는 사명으로 집요하게 찾아냅니다.

### 패턴 3: 성능 리뷰어 (Performance Reviewer)

**역할**: "성능 영향 식별"

검토 항목:

- N+1 쿼리
- 큰 데이터 메모리 적재
- 불필요한 리렌더링 (React)
- 누락된 인덱스
- 동기 처리로 인한 블로킹
- 무거운 외부 API 호출
- 캐싱 누락
- 번들 사이즈 증가

출력: 영향도 추정 + 측정 방법 + 개선 방안

### 패턴 4: 컨벤션 검사관 (Convention Checker)

**역할**: "프로젝트 컨벤션 위반 식별"

시스템 프롬프트에 프로젝트 컨벤션 문서(`CLAUDE.md`, `CONTRIBUTING.md`) 전체를 넣어둡니다.

검토 항목:

- 명명 규칙
- 폴더/파일 구조
- 절대 하지 말 것 목록 위반
- 패턴 불일치 (다른 곳은 A인데 여기만 B)

**효과**: 린터가 못 잡는 "코드 외 규칙"을 자동 검증.

### 패턴 5: 테스트 검수자 (Test Auditor)

**역할**: "PR의 테스트가 충분하고 의미 있는지 검토"

검토 항목:

- 변경된 코드에 테스트가 있는가
- 테스트가 핵심 동작을 검증하는가 (단언이 약하지 않은가)
- 엣지 케이스가 빠지지 않았는가
- 모킹이 과하지 않은가 (내부 구현 모킹)
- 플레이키할 가능성이 있는가
- 회귀 테스트가 필요한 버그 픽스라면 회귀 테스트가 있는가

### 패턴 6: 아키텍처 리뷰어 (Architecture Reviewer)

**역할**: "큰 그림에서 설계 정합성 검토"

설계 문서(`docs/architecture.md`, ADR 등)를 컨텍스트로 받아:

- 이 변경이 아키텍처 원칙을 위반하지 않는가
- 의존성 방향이 맞는가 (레이어 위반 없음)
- 책임이 적절한 모듈에 있는가
- 더 좋은 위치/방법이 있지 않은가

**언제 호출**: 큰 변경, 새 모듈 추가, 의존성 추가 시.

### 패턴 7: 문서화 검수자 (Doc Auditor)

**역할**: "문서가 코드 변경에 맞춰 업데이트되었는지 확인"

검토 항목:

- README의 설치/실행 방법이 여전히 유효한가
- API 스펙 문서가 갱신되었는가
- 공개 함수에 주석이 있는가
- CHANGELOG가 업데이트되었는가
- 새 환경 변수가 `.env.example`에 추가되었는가
- 마이그레이션 가이드가 필요한 변경인가

### 패턴 8: 사용자 경험 리뷰어 (UX Reviewer)

**역할**: "코드 변경이 사용자 경험에 미치는 영향 분석"

검토 항목:

- 로딩 상태 처리
- 에러 메시지 사용자 친화성
- 접근성(a11i): aria 속성, 키보드 네비게이션, 명도 대비
- 반응형 처리
- i18n(다국어) 누락
- 빈 상태(empty state) 처리

### 패턴 9: PR 설명 검수자 (PR Description Auditor)

**역할**: "PR 설명이 리뷰하기 충분한지 검토"

체크:

- 변경 이유가 적혀있는가
- 핵심 변경 사항 요약이 있는가
- 테스트 방법이 명시되었는가
- 스크린샷이 필요한 변경에 첨부되었는가
- 관련 이슈 링크가 있는가

부족하면 무엇을 추가해야 하는지 제안.

### 패턴 10: 회귀 영향 분석가 (Regression Impact Analyzer)

**역할**: "이 변경이 영향을 줄 수 있는 다른 코드 식별"

PR diff를 받아:

- 수정된 함수를 호출하는 곳 목록
- 변경된 데이터 모델을 사용하는 곳
- 영향 받을 가능성이 높은 테스트
- 추가 테스트가 필요한 영역

이게 있으면 "이 변경이 다른 데 영향 줄까?"라는 막연한 불안을 구체화할 수 있습니다.

---

### 실전 워크플로: PR 리뷰 파이프라인

```
1. 개발자가 PR 생성
2. CI 자동 실행 (빌드, 린트, 타입, 테스트)
   └─ 실패 시: 개발자가 수정 후 다시
3. AI 1차 리뷰 (병렬 실행):
   ├─ Senior Reviewer    (전반 품질)
   ├─ Security Reviewer  (보안)
   ├─ Performance Reviewer (성능)
   ├─ Convention Checker (컨벤션)
   ├─ Test Auditor       (테스트)
   └─ Doc Auditor        (문서)
   → 통합 리포트 PR 코멘트로 자동 게시
4. 개발자가 AI 지적 사항 반영
5. AI 재검토 (이번엔 새 diff만)
6. 사람 리뷰어에게 할당
   → 사람은 AI가 못 잡는 영역에 집중:
      - 비즈니스 로직 정합성
      - 장기 유지보수 관점
      - 팀/제품 컨텍스트
      - 사용자 영향
7. 사람 리뷰 통과 → 머지
```

**핵심**: AI 리뷰는 "사람 리뷰 전 단계의 자동 필터"입니다. 이 단계가 잘 돌면, 사람 리뷰는 빠르고 가치 있는 일에만 집중하게 됩니다.

### 서브에이전트 운영 팁 (리뷰 단계 특화)

1. **`.claude/agents/reviewers/` 디렉토리로 분리**:
    
    ```
    .claude/agents/reviewers/
      senior.md
      security.md
      performance.md
      convention.md
      test.md
      architecture.md
      docs.md
      ux.md
      regression-impact.md
    ```
    
2. **GitHub Actions 또는 GitLab CI와 통합**: PR 생성 시 자동으로 AI 리뷰가 코멘트로 달리게 설정
    
3. **출력 형식 표준화**: 각 리뷰어가 같은 형식으로 출력하면 통합 리포트 생성이 쉬움
    
    ```
    ## [에이전트 이름]
    ### Blocking
    - ...
    ### Suggestions
    - ...
    ### Nitpicks
    - ...
    ```
    
4. **중복 지적 제거**: 여러 에이전트가 같은 걸 지적하면 통합 단계에서 정리
    
5. **컨텍스트 주의**: AI 리뷰어에게 필요한 컨텍스트를 함께 전달
    
    - 프로젝트 컨벤션 문서
    - 관련 ADR
    - 변경된 파일의 기존 버전
    - 관련 이슈/PR 링크
6. **점수가 아니라 행동**: "이 PR은 7/10"보다 "이 5가지를 고쳐라"가 유용
    
7. **AI 리뷰의 한계 인정**:
    
    - 비즈니스 도메인 이해 부족
    - 팀의 암묵적 합의 모름
    - 거시적 아키텍처 직관 부족
    - 사용자/제품 컨텍스트 부족 → 이런 영역은 **반드시 사람 리뷰**가 필요

## 리뷰 단계 체크리스트

**작성자(Author) 측**:

- [ ] 셀프 리뷰 완료
- [ ] PR이 작고 단일 목적인가
- [ ] PR 제목/설명 충실
- [ ] 모든 CI 체크 녹색
- [ ] AI 1차 리뷰 지적 사항 반영
- [ ] 재리뷰 요청 명시

**리뷰어(Reviewer) 측**:

- [ ] 정확성 검토 (엣지 케이스, 에러 처리)
- [ ] 설계 적정성
- [ ] 가독성/명명
- [ ] 테스트 충분성
- [ ] 보안 점검
- [ ] 성능 영향
- [ ] 컨벤션 일치
- [ ] 문서 업데이트
- [ ] 코멘트가 건설적/구체적인가

**머지 전**:

- [ ] 필수 승인 수 충족
- [ ] 블로킹 코멘트 모두 해결
- [ ] CI 통과
- [ ] 최신 base 브랜치 반영
- [ ] AI 재검토 통과

## 한 가지 조언

리뷰 단계에서 흔한 실수는 두 가지입니다.

**첫째, 너무 빡빡한 리뷰**: "이게 다 통과해야 머지"라는 기준이 비현실적으로 높으면, PR이 쌓이고 개발 속도가 죽습니다. 완벽이 아니라 **"지금보다 나아지는가"** 가 기준이어야 합니다.

**둘째, 너무 느슨한 리뷰**: "LGTM 👍" 한 줄 승인이 반복되면, 리뷰가 형식이 되고 품질 문제가 누적됩니다.

균형점은 **"심각도에 따라 차등 대응"** 입니다.

- `blocking`: 머지 전 반드시 해결
- `suggestion`: 가능하면 반영, 안 되면 이유 적기
- `nitpick`: 무시해도 됨, 작성자 재량

그리고 Claude Code 환경에서 가장 큰 변화는, **AI 1차 리뷰가 표준이 되면 사람 리뷰는 "정말 사람이 봐야 할 것"에만 집중**할 수 있다는 점입니다. AI가 못 잡는 영역(비즈니스 정합성, 장기 설계 영향, 팀 컨텍스트)에 사람의 시간을 쓰는 것이 새로운 리뷰의 표준입니다.

진행 중인 프로젝트의 리뷰 프로세스와 팀 규모를 알려주시면, 그에 맞는 서브에이전트 셋과 GitHub Actions 워크플로 예시까지 구체적으로 작성해드릴 수 있습니다.
