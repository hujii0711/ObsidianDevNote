환경 셋업 단계는 "본격적인 개발 직전에, 모든 사람(과 AI)이 같은 규칙 위에서 일할 수 있도록 토대를 만드는" 단계입니다. 흔히 간과되지만, **이 단계의 완성도가 이후 개발 속도와 코드 일관성을 좌우합니다.**

특히 Claude Code 환경에서는 이 단계가 더더욱 중요합니다. 사람은 "관례적으로 이렇게 짠다"는 암묵지를 갖고 있지만, AI는 디스크에 적힌 규칙과 기존 코드 패턴만을 따라갑니다. 첫 단추를 잘 끼우지 않으면 파일마다 스타일이 흔들리고, 이미 만든 코드와 일관성 없는 새 코드가 계속 생성됩니다.

## 환경 셋업 단계의 구체적 작업

### 1. 레포지토리 초기화 (Repository Setup)

- **Git 레포 생성**: 로컬 `git init` 또는 GitHub/GitLab에서 생성
- **브랜치 전략 결정**: `main` 단일 / Git Flow / Trunk-based / GitHub Flow
- **기본 브랜치 보호 규칙**: PR 필수, 리뷰 필수, 강제 푸시 금지
- **`.gitignore` 작성**: 언어/프레임워크별 템플릿 활용 (gitignore.io 추천)
- **`README.md` 초안**: 프로젝트 이름, 한 줄 설명, 셋업 방법, 실행 방법

산출물: 깨끗한 빈 레포 + 기본 문서

### 2. 폴더 구조 생성 (Project Skeleton)

설계 단계에서 정한 폴더 구조를 실제로 만듭니다.

```
project-root/
  src/
    features/
    shared/
    app/
  tests/
  docs/
  scripts/
  .github/
    workflows/
```

각 폴더에 `README.md`나 `.gitkeep`을 두면, 빈 폴더도 Git에 기록되고 폴더의 목적을 설명할 수 있습니다.

### 3. 패키지 매니저 & 의존성 초기화

- **패키지 매니저 선택**: npm / pnpm / yarn / bun (JS), pip / poetry / uv (Python) 등
- **버전 고정 방식**: lockfile 커밋 (반드시), 정확한 버전 vs 범위 버전
- **Node/Python 버전 고정**: `.nvmrc`, `.python-version`, `package.json`의 `engines` 필드
- **핵심 의존성 설치**: 프레임워크, 라이브러리

**팁**: 의존성은 처음부터 다 깔지 말고 필요할 때마다 추가하는 게 좋습니다. 그래야 사용 이유를 명확히 기억할 수 있습니다.

### 4. 언어/프레임워크 설정

각 언어/프레임워크에 맞는 설정 파일들을 준비합니다.

- **TypeScript**: `tsconfig.json` (strict mode 권장, path alias 설정)
- **빌드 도구**: Vite, Webpack, esbuild, tsup 등의 설정
- **프레임워크 설정**: Next.js의 `next.config.js`, Vue의 `vite.config.ts` 등
- **path alias 설정**: `@/components/Button`처럼 깔끔하게 import할 수 있도록

### 5. 코드 품질 도구 (Linter & Formatter)

이 부분이 **Claude Code 환경에서 가장 중요한 셋업** 중 하나입니다.

- **Linter**: ESLint(JS/TS), Ruff/Flake8(Python), golangci-lint(Go)
    - 규칙 세트 결정 (recommended, airbnb, standard 등)
    - 프로젝트 특화 규칙 추가
- **Formatter**: Prettier(JS/TS), Black/Ruff(Python), gofmt(Go)
    - 들여쓰기, 따옴표, 줄 길이 통일
- **EditorConfig**: `.editorconfig`로 에디터 간 기본 설정 통일
- **타입 체커**: TypeScript의 `strict: true`, Python의 mypy/pyright

**한 번에 자동 적용되도록** 스크립트를 만들어두세요:

```json
"scripts": {
  "lint": "eslint . --fix",
  "format": "prettier --write .",
  "typecheck": "tsc --noEmit",
  "check": "npm run lint && npm run typecheck && npm run format"
}
```

Claude에게 "작업 끝나면 `npm run check`를 실행해서 통과시켜줘"라고 시킬 수 있게 됩니다.

### 6. Git Hooks 설정 (Pre-commit 검증)

커밋 전에 자동으로 품질 검사를 돌리는 장치입니다.

- **Husky** + **lint-staged** (JS/TS 생태계의 표준)
- **pre-commit** (Python/언어 무관)

전형적인 훅 구성:

- 커밋 전: lint, format, 타입 체크
- 푸시 전: 빠른 단위 테스트

이게 있으면 AI가 망가진 코드를 커밋하는 사고를 막을 수 있습니다.

추가로 **commit message 컨벤션**도 정합니다:

- Conventional Commits (`feat:`, `fix:`, `docs:` 등) 권장
- commitlint로 검증 자동화

### 7. 환경 변수 관리 (Environment Variables)

- **`.env.example` 작성**: 필요한 환경 변수의 목록과 형식 (값은 더미)
- **`.env`는 .gitignore에**: 절대 커밋되지 않도록
- **환경별 분리**: `.env.development`, `.env.production`
- **타입 안전한 환경 변수 로딩**: `zod` + `dotenv` 조합, T3 Env 등
- **시크릿 관리 정책**: 로컬은 `.env`, 프로덕션은 호스팅 플랫폼의 시크릿 매니저

`.env.example`을 잘 만들어두면, 새로 합류한 사람(또는 새 세션의 Claude)도 무엇이 필요한지 즉시 파악할 수 있습니다.

### 8. 테스트 환경 셋업

테스트 코드 작성은 나중이지만, **테스트 인프라는 지금** 깔아둡니다.

- **테스트 러너 설치**: Vitest / Jest / pytest / Go test
- **테스트 설정 파일**: `vitest.config.ts`, `jest.config.js`
- **테스트 유틸리티**: Testing Library, MSW(API 모킹), Faker 등
- **E2E 도구**: Playwright / Cypress (필요 시)
- **샘플 테스트 1개**: "테스트가 실제로 돌아간다"는 것을 증명하는 최소 예시
- **커버리지 도구 설정** (선택)

### 9. CI/CD 파이프라인 골격

배포는 나중이지만, **CI는 첫날부터** 켜두는 게 좋습니다.

- **CI 플랫폼 선택**: GitHub Actions / GitLab CI / CircleCI
- **기본 워크플로 작성**: PR마다 lint + typecheck + test 자동 실행
- **상태 배지를 README에 추가**: 빌드 상태 가시화
- **(나중에) 배포 워크플로**: 배포 단계에서 추가

전형적인 PR 체크 워크플로:

1. 의존성 설치 (캐시 활용)
2. Lint
3. Type check
4. Test
5. (선택) Build

### 10. 데이터베이스 환경

DB를 쓰는 프로젝트라면:

- **로컬 DB 실행 방법**: Docker Compose 권장
- **`docker-compose.yml` 작성**: DB + Redis 등을 한 번에 띄울 수 있게
- **ORM/쿼리 빌더 셋업**: Prisma, Drizzle, SQLAlchemy 등
- **초기 스키마 마이그레이션 도구 설정**
- **시드(seed) 데이터 스크립트**: 개발 시 사용할 더미 데이터

`docker-compose up`만으로 개발 환경이 뜨도록 만들어두면, 새 합류자의 진입 장벽이 크게 낮아집니다.

### 11. 개발 서버 & 핫 리로드

- **개발 서버 실행 명령**: `npm run dev` 같은 표준 명령
- **포트 컨벤션**: 프론트 3000, 백 4000 같은 약속
- **HMR(Hot Module Replacement) 확인**
- **프록시 설정**: 프론트→백 호출 시 CORS 회피 설정

### 12. 로깅 & 디버깅 도구

- **로거 선택**: pino, winston(Node), structlog(Python) 등 (`console.log` 대신)
- **로그 포맷 컨벤션**: JSON 로그 vs 사람이 읽는 형식, 개발/프로덕션 분리
- **소스맵 설정**: 프로덕션에서도 에러 추적 가능하게
- **에러 추적 도구**: Sentry 등 초기 설치 (선택)
- **디버거 설정**: VSCode `launch.json` 예시 제공

### 13. 에디터 / IDE 설정

- **`.vscode/settings.json`**: 공유할 에디터 설정
    - 저장 시 자동 포맷
    - 권장 확장 프로그램 (`.vscode/extensions.json`)
- **`.vscode/launch.json`**: 디버깅 설정
- **에디터별 권장 플러그인 목록 문서화**

이게 있으면 새 사람이 레포 열자마자 추천 확장이 뜨고, 저장만 해도 코드가 자동 정리됩니다.

### 14. Claude Code 전용 셋업

여기가 핵심입니다. Claude Code를 활용할 거라면 다음 파일들을 반드시 만드세요.

- **`CLAUDE.md` (프로젝트 루트)**: Claude Code가 매번 자동으로 읽는 파일
    
    - 프로젝트 한 줄 설명
    - 사용 기술 스택
    - 폴더 구조 원칙
    - 명명 규칙
    - 코드 스타일 핵심 규칙
    - **자주 쓰는 명령어** (`npm run dev`, `npm run check` 등)
    - **절대 하면 안 되는 것 목록**
    
    예시:
    
    ```markdown
    # Project Conventions
    
    ## Stack
    Next.js 14 (App Router) + TypeScript + Prisma + PostgreSQL
    
    ## Folder Structure
    - `src/features/` : 기능별 모듈
    - `src/shared/` : 공통 유틸/컴포넌트
    
    ## Conventions
    - 파일명: kebab-case
    - 컴포넌트명: PascalCase
    - any 타입 금지, unknown 사용
    - default export 금지, named export 사용
    
    ## Commands
    - 개발: `pnpm dev`
    - 검사: `pnpm check`
    - 테스트: `pnpm test`
    
    ## Never Do
    - console.log 커밋 금지
    - 직접 SQL 작성 금지 (Prisma만 사용)
    - 새 의존성 추가 전 반드시 확인 요청
    ```
    
- **`docs/` 폴더**: 기획/설계 문서를 모두 여기에
    
- **`.cursorrules` 또는 유사 파일**: 다른 AI 도구도 같은 규칙을 따르도록 (선택)
    
- **샘플 코드 한두 개**: 모범 패턴이 될 컴포넌트/API/테스트 예시

### 17. "Hello World" 통합 테스트

마지막으로 **모든 게 연결되어 동작하는지 검증**합니다.

- 새 머신에서 레포 클론 → 환경 변수 설정 → 의존성 설치 → 개발 서버 실행 → 페이지 열림
- DB 연결 확인 (간단한 SELECT)
- API → DB → 응답 흐름 한 번 통과
- 테스트 1개 통과
- CI 워크플로 1회 성공

이게 끝나야 환경 셋업 완료입니다. "기본 골격이 도는 상태"에서 개발 단계로 넘어가야 합니다.

## Claude Code 관점의 특별 강조

1. **모든 검증을 한 명령으로**: `pnpm check` 하나로 lint + typecheck + test가 다 돌도록 만들어두면, Claude에게 "작업 끝나면 check 통과시켜줘"라고 지시할 수 있습니다.
    
2. **명령어를 `CLAUDE.md`에 적기**: AI는 디스크에 적힌 것만 신뢰합니다. "테스트는 `pnpm test:unit`" 같은 정보를 적어두지 않으면 매번 다르게 추측합니다.
    
3. **샘플 코드의 힘**: 잘 짜인 컴포넌트/API 핸들러/테스트를 하나씩 만들어두면, Claude가 그 패턴을 기계적으로 복제합니다. 글로 컨벤션을 100줄 적는 것보다, 잘 짠 예제 1개가 훨씬 효과적입니다.
    
4. **린터를 엄격하게**: AI는 린터가 잡아주는 만큼만 일관성을 유지합니다. 규칙을 빡빡하게 잡아두면 AI의 변덕을 시스템이 대신 막아줍니다.
    
5. **`.env.example`의 정확성**: 누락된 환경 변수 때문에 헤매는 경우가 많습니다. 모든 키를 빠짐없이 적어두세요.

## 한 가지 조언

환경 셋업은 **"하루 안에 끝낸다"는 마음가짐**으로 접근하세요. 너무 완벽하게 하려고 하면 일주일이 지나도 코드 한 줄을 안 쓰게 됩니다.

작은 프로젝트라면:

- Git + `.gitignore` + 폴더 구조
- ESLint + Prettier + Husky
- `.env.example`
- 샘플 테스트
- `CLAUDE.md` + `README.md`

이 정도만 해도 충분합니다. 나머지는 필요할 때 추가하면 됩니다.

큰 프로젝트나 팀 작업이라면 위 17개 항목을 다 챙기는 게 결국 시간을 아낍니다. 셋업 부실로 인한 손실은 프로젝트 후반으로 갈수록 기하급수적으로 커집니다.

혹시 사용하실 기술 스택(Next.js, FastAPI, Flutter 등)을 알려주시면, 그 스택에 맞는 환경 셋업 체크리스트와 실제 설정 파일 예시(`.eslintrc`, `tsconfig.json`, `CLAUDE.md` 등)를 구체적으로 작성해드릴 수 있습니다.
