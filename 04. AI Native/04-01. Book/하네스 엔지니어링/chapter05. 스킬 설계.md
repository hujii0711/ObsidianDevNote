
- 스킬 호출 방법
1) description 매칭
2) /skill-name으로 직접 호출
3) 프론트매터에 path:`["src/api/**/*.ts]` 같은 경로 기반 트리거 설정

- description 작성 3단계(Pushy 3단계 공식)

| 단계        | 목적                             | 핵심 질문                             |
| --------- | ------------------------------ | --------------------------------- |
| 1. 동사 나열  | 스킬이 다루는 동작 범위를 클로드가 찾기 쉽게 만든다. | 이 스킬은 어떤 동작을 처리하는가                |
| 2. 트리거 상황 | 호출 여부를 판단할 기준을 클로드에게 제공한다.     | 사용자가 어떤 말이나 파일을 꺼낼 때 이 스킬을 써야 하는가 |
| 3. 경계 조건  | 이 스킬과 다른 스킬의 역할을 구분한다.         | 언제는 이 스킬이고, 언제는 다른 스킬인가           |
- description은 스킬이 호출될지 결정하는 입구이고, SKILL.md 본문은 호출 이후의 첫 분기를 책임지는 라우터이며, workflow/와 references/는 분기 이후의 실행을 맡는 공간이다. 세 층이 각기 다른 시점에 로드되기 때문에 스킬이 아무리 커져도 일상적인 컨텍스트 비용은 거의 늘지 않는다.

- Progressive Disclosource 적용(lazy loading)
컨텍스트는 공공재이므로 단순한 파일 분리 관례가 아니라 설계 원칙이다.
1) Layer1(프론트매터): 스킬이 호출되든 안 되든 세션이 열릴 때마다 항상 컨텍스트에 올라온다. 다른 스킬이 30개든 50개든 마찬가지이다. 그래서 짧을수록 좋다.
	-> 이 스킬을 호출할 것인가: 클로드가 본문을 읽기 전에 판단하는 데 필요한 최소 정보만 담는다.
2) Layer2(SKILL.md): 이 스킬이 실제로 호출됐을 때만 컨텍스트에 올라온다. 500줄을 넘기면 그만큼 다른 작업에 쓸 공간이 줄어드니, 본문은 가능한 간결하게 유지한다.
	-> 호출했다면 어떻게 수행하는가: 모든 호출에 공통으로 적용되는 절차와 원칙을 담는다.
3) Layer3(workflows, references): 해당 조건이 맞을 때만 열린다. 파일이 수천 줄이어도 열리지 않으면 컨텍스트 비용이 전혀 들지 않는다.
	특정 조건에서 무엇을 추가로 참고하는가: 조건부 상세, 도메인별 분기, 대형 템플릿을 담는다.
