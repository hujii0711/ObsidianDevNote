
# 5. 테스트 단계 상세 가이드

Claude Code를 활용한 앱 개발 — 테스트 단계에서 해야 할 작업을 파트별로 정리합니다.

---

## 파트 1. 테스트 전략 수립

### 테스트 피라미드 이해 `필수`

테스트는 비용과 속도에 따라 세 계층으로 나뉩니다. 아래 비율을 기준으로 작성합니다.

```
         /\
        /E2E\          ← 적게 (10%) : 느리고 비용 높음
       /------\
      /통합테스트\      ← 중간 (20%) : 서비스 간 연동 검증
     /----------\
    /  단위테스트  \    ← 많이 (70%) : 빠르고 비용 낮음
   /--------------\
```

### 테스트 도구 선정 `필수`

기술 스택에 맞는 테스트 도구를 확정합니다.

| 계층      | JavaScript/TypeScript | Python         |
| ------- | --------------------- | -------------- |
| 단위 테스트  | Jest, Vitest          | pytest         |
| 통합 테스트  | Supertest, Jest       | pytest + httpx |
| E2E 테스트 | Playwright, Cypress   | Playwright     |
| 커버리지    | Istanbul (Jest 내장)    | pytest-cov     |

```bash
claude -p "이 프로젝트 기술 스택에 맞는 테스트 도구와 설정 파일 작성해줘"
```

## 파트 2. 단위 테스트 (Unit Test)

가장 작은 단위(함수, 클래스, 컴포넌트)가 단독으로 올바르게 동작하는지 검증합니다.

### 백엔드 단위 테스트 `필수`

```bash
# 서비스 레이어 테스트 생성
claude -p "
UserService의 단위 테스트를 작성해줘.
- 외부 의존성(DB, 외부 API)은 모두 Mock 처리
- 성공 케이스, 실패 케이스, 엣지 케이스 모두 포함
- Jest 사용, AAA 패턴(Arrange-Act-Assert) 준수
"

# 유틸리티 함수 테스트
claude -p "
src/utils/ 디렉터리의 모든 유틸 함수에 대한 단위 테스트 작성해줘.
입력값 경계값 테스트 반드시 포함할 것
"
```

테스트 작성 시 반드시 포함해야 할 케이스는 다음과 같습니다.

```
- 정상 동작 케이스 (Happy path)
- 잘못된 입력값 케이스 (Invalid input)
- 경계값 케이스 (Boundary)
- 예외 발생 케이스 (Exception)
- null / undefined 처리 케이스
```

### 프론트엔드 단위 테스트 `필수`

```bash
# 컴포넌트 테스트
claude -p "
LoginForm 컴포넌트 테스트를 작성해줘.
- React Testing Library 사용
- 렌더링, 유저 인터랙션, 폼 유효성 검사 모두 테스트
- API 호출은 MSW로 Mock 처리
"

# 커스텀 훅 테스트
claude -p "
useAuth 훅 테스트를 작성해줘.
- renderHook 사용
- 로그인 성공/실패/로딩 상태 모두 테스트
"
```

### 커버리지 측정 및 기준 설정 `필수`

```bash
# 커버리지 실행
npm test -- --coverage

# jest.config.js에 커버리지 기준 설정
claude -p "
jest.config.js에 커버리지 임계값 설정을 추가해줘.
기준: 전체 80%, 핵심 비즈니스 로직 90%
기준 미달 시 CI에서 실패하도록 설정
"
```

## 파트 3. 통합 테스트 (Integration Test)

여러 모듈이 함께 동작할 때 올바르게 연동되는지 검증합니다.

### API 통합 테스트 `필수`

실제 DB와 연결해서 API 엔드포인트 전체 흐름을 테스트합니다.

```bash
claude -p "
인증 API 통합 테스트를 작성해줘.
- Supertest 사용, 실제 테스트 DB 연결
- POST /auth/login → JWT 발급 → GET /auth/me 전체 흐름 테스트
- 테스트 전후 DB 초기화 로직 포함
- 테스트용 fixtures 데이터 생성
"
```

### 테스트 DB 격리 설정 `필수`

프로덕션 DB와 완전히 분리된 테스트 전용 DB를 사용합니다.

```bash
# .env.test 파일 생성
claude -p "
테스트 전용 환경변수 파일 .env.test를 작성해줘.
테스트 DB URL, 테스트용 JWT 시크릿 등 포함
테스트 시작 전 마이그레이션, 종료 후 초기화 스크립트도 함께
"
```

### 서비스 간 연동 테스트 `권장`

외부 API, 메시지 큐, 캐시 등 외부 서비스와의 연동을 검증합니다.

```bash
claude -p "
이메일 발송 서비스 연동 테스트를 작성해줘.
- 실제 이메일 발송 대신 Mock 서버 사용
- 발송 성공/실패/재시도 로직 모두 테스트
"
```

## 파트 4. E2E 테스트 (End-to-End Test)

실제 브라우저에서 유저 시나리오 전체를 검증합니다.

### Playwright 설정 `필수`

```bash
# Playwright 초기화
npx playwright install

claude -p "
playwright.config.ts 설정 파일 작성해줘.
- 로컬, CI 환경 모두 지원
- Chrome, Firefox, Safari 크로스 브라우저 테스트
- 실패 시 스크린샷, 비디오 자동 저장
- 테스트 재시도 횟수 설정
"
```

### 핵심 유저 시나리오 E2E 테스트 `필수`

MVP의 핵심 기능을 유저 관점에서 처음부터 끝까지 테스트합니다.

```bash
claude -p "
다음 시나리오의 E2E 테스트를 Playwright로 작성해줘.

시나리오 1: 회원가입 → 로그인 → 핵심 기능 사용 → 로그아웃
시나리오 2: 잘못된 비밀번호로 로그인 시도 → 에러 메시지 확인
시나리오 3: 비로그인 상태로 보호된 페이지 접근 → 로그인 페이지 리다이렉트

각 시나리오마다 성공 기준을 명확히 검증할 것
"
```

### 시각적 회귀 테스트 `권장`

UI 변경 시 의도치 않은 시각적 변화를 감지합니다.

```bash
claude -p "
Playwright로 주요 페이지의 스크린샷 비교 테스트를 설정해줘.
기준 스크린샷 생성 → 변경 후 비교 → 차이 시각화 방법 포함
"
```

## 파트 5. 특수 테스트

### 성능 테스트 `권장`

API 응답 시간과 동시 접속 처리 능력을 검증합니다.

```bash
claude -p "
k6로 로그인 API 부하 테스트 스크립트를 작성해줘.
- 동시 사용자 100명 시뮬레이션
- 평균 응답 시간 200ms 이하 기준
- 에러율 1% 이하 기준
- 결과 리포트 출력 포함
"
```

### 보안 테스트 `권장`

일반적인 보안 취약점을 자동으로 검사합니다.

```bash
claude -p "
다음 보안 항목을 코드에서 검사해줘.
- SQL 인젝션 취약점
- XSS 취약점
- 인증 누락된 엔드포인트
- 민감 정보 로그 출력
- 하드코딩된 시크릿 값
발견된 취약점은 파일명, 라인 번호, 심각도와 함께 보고해줘
"
```

### 접근성 테스트 `권장`

웹 접근성 기준(WCAG) 준수 여부를 검사합니다.

```bash
claude -p "
Playwright와 axe-core를 사용해서 주요 페이지의 접근성 테스트를 작성해줘.
WCAG 2.1 AA 기준, 위반 항목은 심각도와 수정 방법 포함
"
```

## 파트 6. 서브에이전트로 테스트 병렬 실행

개발 단계와 마찬가지로 테스트도 역할별 서브에이전트로 병렬 실행할 수 있습니다.

### 테스트 에이전트 분담 구조

```
메인 에이전트
├── 단위 테스트 에이전트    → 백엔드 서비스/유틸 단위 테스트
├── 컴포넌트 테스트 에이전트 → 프론트엔드 컴포넌트 테스트
├── API 통합 테스트 에이전트 → 엔드포인트 통합 테스트
└── E2E 테스트 에이전트     → 유저 시나리오 E2E 테스트
```

### 병렬 실행 스크립트

```bash
# scripts/test-agents.sh
#!/bin/bash

echo "=== 테스트 서브에이전트 병렬 실행 ==="

# 단위 테스트 에이전트
claude -p "
역할: 백엔드 테스트 엔지니어
작업: src/modules/ 하위 모든 서비스 파일의 단위 테스트 작성
도구: Jest, 외부 의존성 Mock 처리
기준: 커버리지 80% 이상, 모든 케이스 통과
결과: logs/unit-test-result.md에 저장
" > logs/unit-agent.log 2>&1 &

# 통합 테스트 에이전트
claude -p "
역할: API 테스트 엔지니어
작업: docs/api-spec.md의 모든 엔드포인트 통합 테스트 작성
도구: Supertest, 테스트 DB 사용
기준: 모든 엔드포인트 성공/실패 케이스 커버
결과: logs/integration-test-result.md에 저장
" > logs/integration-agent.log 2>&1 &

# E2E 테스트 에이전트
claude -p "
역할: E2E 테스트 엔지니어
작업: 핵심 유저 시나리오 5개 E2E 테스트 작성
도구: Playwright, Chrome 기준
기준: 모든 시나리오 통과, 실패 시 스크린샷 저장
결과: logs/e2e-test-result.md에 저장
" > logs/e2e-agent.log 2>&1 &

wait

echo "=== 모든 테스트 에이전트 완료 ==="

# 결과 통합 및 리포트 생성
claude -p "
logs/ 디렉터리의 모든 테스트 결과 파일을 읽고
전체 테스트 현황 리포트를 docs/test-report.md로 작성해줘.
통과/실패 수, 커버리지, 개선 필요 항목 포함
"
```

## 파트 7. 버그 수정 프로세스

테스트에서 발견된 버그를 체계적으로 수정합니다.

### 버그 수정 순서

```
1. 버그 재현 테스트 먼저 작성 (실패하는 테스트)
2. 버그 원인 분석
3. 최소 범위로 수정
4. 작성한 테스트 통과 확인
5. 기존 테스트 전체 재실행으로 회귀 확인
```

### Claude Code로 버그 분석

```bash
# 에러 로그 분석
cat logs/error.log | claude -p "이 에러의 원인을 분석하고 수정 방법을 알려줘"

# 실패한 테스트 분석
claude -p "
다음 테스트가 실패하고 있어:
[실패 로그 붙여넣기]

원인을 분석하고 수정 방법을 제안해줘.
수정 시 다른 테스트에 영향을 주지 않도록 주의할 것
"

# 회귀 테스트 실행
claude -p "버그 수정 후 관련 모듈의 전체 테스트를 실행하고 결과를 보고해줘"
```

## 테스트 단계 완료 체크리스트

리뷰 단계로 넘어가기 전에 아래 항목을 모두 완료해야 합니다.

- [ ] 단위 테스트 전체 통과 및 커버리지 80% 이상
- [ ] API 통합 테스트 전체 통과
- [ ] 핵심 유저 시나리오 E2E 테스트 통과
- [ ] 발견된 버그 전체 수정 완료
- [ ] 보안 취약점 검사 완료
- [ ] 성능 기준 통과 확인
- [ ] 테스트 리포트 문서화 완료
- [ ] CI 파이프라인에서 자동 테스트 실행 확인

---

> **핵심 포인트**: 테스트는 버그를 잡는 것이 목적이 아니라 **버그가 프로덕션에 도달하지 못하게 막는 방어선**입니다. Claude Code로 테스트를 빠르게 작성할 수 있지만, 테스트 케이스의 범위와 기준은 사람이 직접 검토해야 합니다. 특히 경계값과 예외 케이스는 Claude가 놓치기 쉬우므로 반드시 추가로 확인하세요.
