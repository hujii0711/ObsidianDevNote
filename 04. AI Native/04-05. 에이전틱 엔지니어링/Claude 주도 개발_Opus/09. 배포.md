배포 단계는 "잘 만든 코드를 실제 사용자에게 안전하게 전달하는" 단계입니다. 개발의 마지막이 아니라, **운영의 시작점**이기도 합니다. 이 단계의 핵심 가치는 "빠르게 자주 배포하되, 문제가 생기면 즉시 되돌릴 수 있는 능력"입니다.

Claude Code 환경에서는 배포 단계의 의미가 한 단계 더 중요해집니다. AI가 코드 변경을 빠르게 만들어내는 만큼 **배포 횟수도 늘어나기 때문**입니다. 사람이 일주일에 한 번 배포하던 시대의 절차로는 감당이 안 됩니다. 자동화와 안전장치가 필수입니다.

## 배포 단계의 구체적 작업

### 1. 배포 전 최종 점검 (Pre-deployment Checklist)

머지된 코드라도 배포 직전에 다시 확인합니다.

- **모든 CI 체크 통과 확인**
- **테스트 커버리지 임계값 충족**
- **변경 로그(CHANGELOG) 작성**
- **마이그레이션 필요 여부 확인** (DB 스키마, 환경 변수, 인프라)
- **롤백 계획 명시** (문제 시 어떻게 되돌릴 것인가)
- **의존성 변경 검토** (새 라이브러리, 버전 업데이트)
- **시크릿/환경 변수 동기화** (스테이징 → 프로덕션)
- **외부 서비스 의존성 확인** (계약, 쿼터, 결제 상태)

### 2. 배포 환경 구성 (Environment Setup)

여러 환경을 명확히 분리합니다.

- **로컬(Local)**: 개발자 머신
- **개발(Development)**: 공유 개발 환경
- **스테이징(Staging)**: 프로덕션과 동일한 구성으로 최종 검증
- **프로덕션(Production)**: 실제 사용자

각 환경의 차이점을 최소화해야 "스테이징에서 됐는데 프로덕션에서 안 되는" 문제를 방지합니다.

**환경별로 분리해야 할 것**:

- DB
- API 키, 시크릿
- 외부 서비스 엔드포인트
- 도메인/SSL 인증서
- 로깅/모니터링 채널

### 3. CI/CD 파이프라인 구축

배포는 **사람이 손으로 하는 작업이 아니라 자동화된 파이프라인**이 되어야 합니다.

**일반적인 파이프라인 단계**:

```
코드 푸시
  ↓
1. 빌드 (Build)
   - 의존성 설치
   - 컴파일/번들링
   - 빌드 아티팩트 생성
  ↓
2. 검증 (Verify)
   - 린트, 타입체크, 테스트
   - 보안 스캔
   - 라이선스 체크
  ↓
3. 아티팩트 저장 (Artifact)
   - Docker 이미지 빌드
   - 컨테이너 레지스트리 푸시
   - 또는 정적 파일 빌드
  ↓
4. 스테이징 배포 (Deploy to Staging)
   - 자동 배포
   - 스모크 테스트
  ↓
5. 프로덕션 배포 (Deploy to Production)
   - 수동 승인 또는 자동
   - 점진적 롤아웃
  ↓
6. 사후 검증 (Post-deploy verification)
   - 헬스 체크
   - 핵심 메트릭 모니터링
```

**도구**: GitHub Actions, GitLab CI, CircleCI, Jenkins, ArgoCD (K8s)

### 4. 배포 전략 (Deployment Strategy)

어떻게 새 버전을 사용자에게 노출할지가 핵심입니다.

#### 4-1. Recreate (재시작 배포)

- 모든 인스턴스 종료 후 새 버전 시작
- 다운타임 발생
- 단순하지만 프로덕션에는 부적합

#### 4-2. Rolling Update (점진적 교체)

- 인스턴스를 순차적으로 새 버전으로 교체
- 다운타임 없음
- 잠시 두 버전이 공존 (호환성 필요)
- Kubernetes 기본 전략

#### 4-3. Blue-Green Deployment

- 동일한 환경 두 개(Blue/Green) 운영
- 새 버전을 비활성 환경에 배포 → 검증 → 트래픽 전환
- 롤백이 즉각적 (트래픽 다시 돌리기만 하면 됨)
- 인프라 비용 2배

#### 4-4. Canary Release

- 새 버전을 소수 사용자(1%, 5%, 10%...)에게만 노출
- 메트릭 보면서 점진적 확대
- 문제 발견 시 영향 최소화
- 가장 안전하지만 구현 복잡도 높음

#### 4-5. Feature Flag (기능 플래그)

- 코드는 배포하되 기능은 플래그로 제어
- 배포와 릴리스 분리 (배포는 기술, 릴리스는 비즈니스)
- A/B 테스트, 점진적 활성화, 즉시 비활성화 가능
- 도구: LaunchDarkly, Unleash, GrowthBook

**선택 기준**:

- 소규모 / 사이드 프로젝트: Rolling Update
- 중요 서비스: Blue-Green 또는 Canary
- 자주 실험: Feature Flag

### 5. 데이터베이스 마이그레이션

코드 배포보다 **DB 변경이 더 위험**합니다. 신중해야 합니다.

**원칙**:

- **하위 호환성 유지**: 새 코드와 이전 코드가 동시에 동작 가능해야 함
- **단계 분리**:
    1. 컬럼 추가 (이전 코드도 동작)
    2. 새 컬럼 사용 시작 (양쪽 코드 호환)
    3. 이전 컬럼 사용 중단
    4. 이전 컬럼 삭제 (나중에)
- **마이그레이션 도구**: Prisma Migrate, Alembic, Flyway, Liquibase
- **백업 필수**: 마이그레이션 직전 스냅샷
- **트랜잭션 사용**: 가능한 경우
- **큰 테이블 주의**: 락이 오래 걸리는 작업은 분할

**위험한 작업과 안전한 대안**:

- ❌ `ALTER TABLE`로 컬럼 타입 변경 → ✅ 새 컬럼 추가 → 데이터 복사 → 전환
- ❌ 컬럼 삭제 → ✅ 사용 중단 → 충분히 기다림 → 삭제
- ❌ 큰 테이블에 인덱스 추가 → ✅ `CREATE INDEX CONCURRENTLY`

### 6. 환경 변수 & 시크릿 관리

- **시크릿은 절대 코드에 두지 않기**
- **시크릿 관리 도구 사용**: AWS Secrets Manager, HashiCorp Vault, Doppler, 1Password
- **환경 변수 검증**: 부팅 시 필수 변수 누락되면 즉시 실패 (Fail Fast)
- **시크릿 로테이션**: 정기적으로 갱신
- **접근 권한 최소화**: 누가/어떤 서비스가 어떤 시크릿에 접근하는지

### 7. 점진적 롤아웃 (Progressive Rollout)

큰 변경일수록 천천히 노출합니다.

**전형적인 단계**:

1. **Internal**: 내부 직원만 (dogfooding)
2. **Beta**: 일부 자원자 (1%)
3. **Gradual**: 5% → 25% → 50% → 100%
4. **각 단계마다**:
    - 핵심 메트릭 모니터링
    - 에러율 비교
    - 사용자 피드백 수집
    - 문제 발견 시 즉시 중단/롤백

### 8. 헬스 체크 & 스모크 테스트

배포 직후 자동으로 검증합니다.

**헬스 체크 엔드포인트**:

- `/health` (liveness): 서버가 살아있는가
- `/ready` (readiness): 트래픽 받을 준비됐는가
- DB, 캐시, 외부 의존성 연결 확인

**스모크 테스트**: 핵심 경로 자동 검증

- 로그인 가능한가
- 메인 페이지 로드되는가
- 주요 API 응답하는가

이게 실패하면 자동 롤백이 발동되어야 합니다.

### 9. 모니터링 & 알림 설정

배포 직후가 가장 위험한 시간입니다. 즉시 알아챌 수 있어야 합니다.

**메트릭 종류 (4 Golden Signals)**:

- **Latency**: 응답 시간
- **Traffic**: 요청량
- **Errors**: 에러율
- **Saturation**: 자원 포화도 (CPU, 메모리, 디스크)

**도구**:

- 인프라/앱: Datadog, New Relic, Grafana + Prometheus
- 에러 추적: Sentry, Bugsnag
- 로그: Datadog Logs, Loki, ELK
- 사용자 행동: PostHog, Mixpanel, Amplitude
- 가동 시간: Better Uptime, Pingdom

**알림 채널**: Slack, PagerDuty, OpsGenie

**알림 원칙**:

- 진짜 행동이 필요한 것만 알림
- 알림 피로도(alert fatigue) 경계
- 심각도별 채널 분리 (critical은 페이저, info는 슬랙)

### 10. 롤백 계획 & 실행

**롤백은 옵션이 아니라 필수 능력**입니다.

- **롤백 명령이 한 줄이어야 함**: `make rollback` 또는 GitHub Actions 한 번 클릭
- **롤백 RTO(Recovery Time Objective)**: 목표 시간 정의 (예: 5분 이내)
- **DB 마이그레이션 롤백 전략**: 마이그레이션이 하위 호환이면 그냥 이전 코드로 돌아가도 됨
- **자동 롤백 트리거**: 에러율 임계값 초과 시 자동 롤백
- **롤백 연습**: 정기적으로 테스트

### 11. 릴리스 노트 & 커뮤니케이션

- **CHANGELOG**: 기술적 변경 사항
- **릴리스 노트**: 사용자 관점의 변화 (블로그, 인앱 공지)
- **내부 공지**: 팀/CS/마케팅에 변경 사항 공유
- **상태 페이지(Status Page)**: 사용자에게 가시화 (statuspage.io, Instatus)
- **점검 공지**: 다운타임 있으면 사전 안내

### 12. 배포 후 검증 (Post-deploy Verification)

배포 완료가 끝이 아닙니다.

- **15분~1시간 모니터링**: 핵심 메트릭 확인
- **에러 트렌드 비교**: 배포 전후
- **성능 회귀 확인**: 응답 시간 변화
- **사용자 피드백 채널 확인**
- **외부 의존성 영향**: 우리 변경이 다른 시스템에 영향 주지 않는지

### 13. 사후 회고 & 문서화

문제가 있었거나 큰 배포였다면:

- **포스트모템(Postmortem)**: 문제 분석, 학습 사항 정리
- **블레임리스(Blameless) 문화**: 사람 탓 아닌 시스템/프로세스 개선
- **체크리스트 업데이트**: 다음 배포에 반영
- **자동화 개선**: 사람이 한 작업을 자동화로

### 14. 보안 & 컴플라이언스

- **시크릿 스캔**: 배포 아티팩트에 시크릿 없는지
- **취약점 스캔**: Docker 이미지, 의존성
- **감사 로그(Audit Log)**: 누가 언제 무엇을 배포했는지
- **권한 관리**: 누가 프로덕션에 배포할 수 있는지
- **컴플라이언스 요구사항**: GDPR, PCI-DSS, HIPAA 등

### 15. 비용 모니터링

배포가 인프라 비용에 영향을 줄 수 있습니다.

- **새 서비스/리소스의 비용 예측**
- **트래픽 증가에 따른 비용 알림**
- **사용하지 않는 리소스 정리**

## 서브에이전트 활용 방안

배포 단계는 **자동화 가능한 작업과 판단이 필요한 작업이 섞여 있습니다**. 서브에이전트는 사람이 매번 신경 쓰기 힘든 검증과 모니터링 분석을 담당하기에 적합합니다.

### 패턴 1: 배포 전 점검관 (Pre-deploy Auditor)

**역할**: "배포 직전에 모든 체크리스트 항목 자동 점검"

검토 항목:

- 변경된 파일 중 DB 마이그레이션 있는가 → 호환성 분석
- 새 환경 변수가 있는가 → 모든 환경에 설정되었는지 확인
- 시크릿이 코드에 들어가지 않았는가
- CHANGELOG가 갱신되었는가
- 외부 API 변경/의존성 변경 영향
- 이전 배포와의 차이점 요약

출력: "배포 가능" / "주의 필요" / "배포 금지" + 이유

### 패턴 2: 릴리스 노트 작성자 (Release Note Writer)

**역할**: "머지된 PR 목록을 받아 사용자 관점의 릴리스 노트 작성"

시스템 프롬프트:

> "당신은 제품 매니저다. 다음 PR 목록을 받아 사용자가 이해할 수 있는 릴리스 노트를 작성하라. 기술 용어 대신 사용자가 얻는 가치 관점으로 표현하라. 카테고리(새 기능, 개선, 버그 수정)로 분류하라."

**효과**: 매 릴리스마다 릴리스 노트 작성에 들이는 시간이 사라집니다.

### 패턴 3: 마이그레이션 안전성 검사관 (Migration Safety Checker)

**역할**: "DB 마이그레이션 SQL을 받아 위험도 평가"

체크 항목:

- 락이 오래 걸릴 작업 (`ALTER TABLE`, 인덱스 생성)인가
- 큰 테이블에 영향을 주는가
- 하위 호환이 되는가
- 트랜잭션 안에서 안전하게 실행 가능한가
- 롤백 가능한가

출력: 위험도 점수 + 권장 실행 시간 + 안전 대안

### 패턴 4: 배포 영향 분석가 (Deploy Impact Analyzer)

**역할**: "이번 배포가 어떤 사용자/기능에 영향을 줄지 분석"

PR 모음을 받아:

- 영향 받는 API 엔드포인트 목록
- 영향 받는 UI 화면
- 영향 받는 사용자 세그먼트
- 권장 모니터링 메트릭
- 권장 롤아웃 전략 (Canary 5% vs Full)

### 패턴 5: 모니터링 분석가 (Monitoring Analyst)

**역할**: "배포 후 메트릭을 받아 이상 징후 식별"

배포 전후의 메트릭을 비교 입력으로 받아:

- 에러율 변화
- 응답 시간 변화
- 트래픽 패턴 변화
- 자원 사용량 변화
- 의심 패턴 (특정 엔드포인트만 느려짐 등)

출력: "정상" / "주의 관찰" / "롤백 권장" + 근거

### 패턴 6: 인시던트 응답 보조자 (Incident Response Helper)

**역할**: "장애 발생 시 빠른 원인 분석 보조"

입력:

- 에러 로그
- 최근 배포 이력
- 메트릭 이상치
- 사용자 신고 내용

출력:

- 가장 가능성 높은 원인 후보
- 영향 범위 추정
- 권장 즉시 조치 (롤백, 트래픽 차단, 캐시 클리어)
- 디버깅 시작점 (확인할 로그/메트릭)

**중요**: 실제 결정은 사람이 합니다. AI는 빠른 1차 분석만.

### 패턴 7: 포스트모템 작성 보조자 (Postmortem Drafter)

**역할**: "장애 정보를 받아 포스트모템 초안 작성"

입력:

- 타임라인 (몇 시에 무엇이 일어났는가)
- 영향 범위
- 원인 분석
- 대응 조치

출력: 표준 포스트모템 템플릿에 맞춘 초안

- 요약
- 타임라인
- 근본 원인
- 영향
- 해결 조치
- 재발 방지책

**원칙**: 블레임리스(blameless) 톤 강제. 사람 탓 표현 금지.

### 패턴 8: 보안 사후 점검자 (Security Post-deploy Auditor)

**역할**: "배포 후 보안 관점에서 확인"

체크:

- 새 API 엔드포인트의 인증 적용 여부
- 새 환경 변수에 민감 정보 마스킹
- 외부 노출 포트/엔드포인트
- 로그에 민감 정보 누출 가능성
- 의존성 취약점 새로 발견된 것

### 패턴 9: 비용 영향 분석가 (Cost Impact Analyzer)

**역할**: "배포가 인프라 비용에 미치는 영향 추정"

체크:

- 새로 추가된 리소스 (DB, 캐시, 큐)
- 트래픽 증가 예상
- 외부 API 호출 증가 (유료 API)
- 스토리지 사용량 증가
- 월간 비용 영향 추정

### 패턴 10: 롤백 의사결정 보조자 (Rollback Decision Helper)

**역할**: "이상 상황에서 롤백할지 판단 보조"

입력:

- 현재 메트릭 상황
- 영향 범위
- 롤백 비용 (다운타임, 데이터 손실 위험)
- 픽스 가능 시간 추정

출력: 롤백 vs 핫픽스 vs 모니터링 지속 판단 + 근거

### 실전 워크플로: 배포 파이프라인에서 서브에이전트 활용

```
1. PR 머지 → main 브랜치 업데이트
2. Pre-deploy Auditor 자동 실행
   → 점검 결과 Slack 채널에 게시
3. CI 빌드 & 테스트 통과
4. Migration Safety Checker (마이그레이션 있을 때)
   → 안전성 보고서
5. Deploy Impact Analyzer
   → 영향 분석, 권장 롤아웃 전략 제안
6. Release Note Writer
   → 릴리스 노트 초안 생성, 사람이 검토
7. 스테이징 배포 자동 진행
8. 스모크 테스트 통과
9. 프로덕션 배포 (Canary 5%)
10. Monitoring Analyst가 5분 간격으로 메트릭 분석
    → "정상" / "주의" / "롤백 권장" 보고
11. 정상이면 단계적 확대 (25% → 50% → 100%)
12. 완전 배포 후 30분간 Monitoring Analyst 계속 감시
13. Security Post-deploy Auditor 실행
14. Cost Impact Analyzer로 비용 영향 보고
15. 문제 발생 시 Incident Response Helper 호출
    → 사람이 의사결정 후 조치
16. (문제 있었다면) Postmortem Drafter가 초안 작성
```

이렇게 구성하면 **사람은 진짜 의사결정에만 집중**하고, 반복 작업과 1차 분석은 서브에이전트가 처리합니다.

### 서브에이전트 운영 팁 (배포 단계 특화)

1. **`.claude/agents/deploy/` 디렉토리로 분리**:
    
    ```
    .claude/agents/deploy/
      pre-deploy-auditor.md
      release-note-writer.md
      migration-safety-checker.md
      deploy-impact-analyzer.md
      monitoring-analyst.md
      incident-response-helper.md
      postmortem-drafter.md
      rollback-decision-helper.md
    ```
    
2. **AI에게 절대 자동 실행 권한 주지 않기**:
    
    - 분석, 보고, 추천은 AI
    - **실제 배포/롤백 명령은 사람**
    - 자동 롤백은 명확한 규칙(에러율 임계값)으로만, AI 판단으로 X
3. **출력은 행동 가능하게**: "에러율이 증가했다"가 아니라 "에러율 5% 증가, 주된 원인은 /api/checkout 엔드포인트, 롤백 권장"
    
4. **컨텍스트로 줄 자료**:
    
    - 이전 배포 기록
    - 정상 메트릭 기준선
    - 회사 SLO/SLA
    - 인시던트 대응 플레이북
5. **사람의 마지막 검토 필수**: 특히 릴리스 노트, 포스트모템 같은 외부에 나가는 문서는 반드시 사람이 검토 후 발행.
    
6. **AI 한계 인정**:
    
    - 비즈니스 영향의 무게 판단 어려움
    - 조직 정치적 맥락 모름
    - 처음 보는 장애 패턴은 약함
    - **고객 커뮤니케이션은 사람**이 직접

## 한 가지 조언

배포 단계에서 가장 중요한 원칙은 **"배포를 지루하게 만들어라(Make Deployments Boring)"** 입니다.

배포가 영웅적이고 긴장되는 이벤트라면, 그건 프로세스가 잘못된 것입니다. 좋은 배포는:

- 작고 자주 일어나고
- 자동화되어 있고
- 실패해도 5분 안에 되돌릴 수 있고
- 누구나 할 수 있어야 합니다

특히 Claude Code 환경에서는 **배포 빈도가 사람 손 시대보다 훨씬 높아집니다**. 하루에 5번 배포하는 게 일상이 될 수 있습니다. 그러려면:

1. **모든 것을 자동화**: 사람이 손으로 하는 일은 결국 실수가 납니다
2. **작은 변경 단위**: 큰 배포는 위험. 작은 PR을 자주
3. **빠른 롤백**: 안전망이 있어야 빠르게 움직일 수 있음
4. **모니터링 우선**: 문제를 빨리 알아챌 수 있어야 빨리 움직임
5. **AI는 보조, 결정은 사람**: 자동화의 한계를 명확히 인지

배포는 개발 라이프사이클의 **마지막이 아니라 다음 사이클의 시작**입니다. 사용자에게 도달한 코드에서 얻는 피드백, 메트릭, 인시던트가 다음 기획의 입력이 됩니다. 그래서 배포 단계의 모니터링과 회고가 잘 되어야 전체 사이클이 건강해집니다.

진행 중인 프로젝트의 배포 환경(클라우드 종류, K8s 사용 여부, 트래픽 규모 등)을 알려주시면, 그에 맞는 구체적인 CI/CD 파이프라인 예시와 서브에이전트 정의 파일까지 작성해드릴 수 있습니다.
