개발 단계는 설계 문서를 실제 동작하는 코드로 옮기는 단계입니다. 하지만 "그냥 코드 짜는 단계"로 생각하면 위험합니다. 이 단계는 사실 **작은 사이클의 반복**입니다: 작업 분해 → 구현 → 검증 → 커밋 → 다음.

특히 Claude Code 환경에서는 개발 단계가 "AI에게 일을 시키는 방식"의 문제로 바뀝니다. AI의 출력은 입력의 품질을 그대로 반영하기 때문에, **무엇을, 어떻게, 어느 단위로 시키느냐**가 결과 품질을 결정합니다. 여기에 더해 **서브에이전트(Sub-agent)** 를 활용하면 단일 세션의 컨텍스트 한계를 넘어 병렬·역할 분담 작업이 가능해집니다.

## 개발 단계의 구체적 작업

### 1. 작업 분해 (Task Breakdown)

설계 문서의 큰 기능들을 **하루 안에 끝낼 수 있는 단위**로 잘게 쪼갭니다.

- **에픽(Epic) → 스토리(Story) → 태스크(Task)** 계층 구조
- 각 태스크 조건:
    - 1~4시간 안에 완료 가능
    - 독립적으로 테스트 가능
    - 명확한 완료 기준(Definition of Done)
- **의존성 정리**: A가 끝나야 B를 시작할 수 있는 관계 명시
- **이슈 트래커에 등록**: GitHub Issues, Linear, Jira

좋은 태스크 예시:

- ✅ "User 모델 생성 + 마이그레이션 작성"
- ✅ "POST /api/auth/signup 구현 (이메일 중복 검증 포함)"
- ❌ "회원 시스템 만들기" (너무 큼)

**Claude Code 관점**: AI에게 시키는 단위가 곧 태스크 단위입니다. 한 번에 5개 기능을 시키면 품질이 떨어지지만, 한 가지 명확한 태스크는 매우 잘 처리합니다.

### 2. 브랜치 생성 & 작업 시작

- **이슈 단위 브랜치**: `feature/user-signup`, `fix/login-error`
- **명명 규칙 준수**: 환경 셋업에서 정한 컨벤션
- **베이스 브랜치 최신화**: `git pull origin main` 먼저
- **컨텍스트 정리**: 관련 문서/이슈 다시 읽기

### 3. 구현 전 컨텍스트 로딩

코드를 짜기 전에 멈춰서 다음을 확인합니다.

- 이 기능이 영향 주는 기존 코드는 어디인가?
- 비슷한 패턴으로 이미 구현된 코드가 있는가? (있다면 그 패턴 따르기)
- 관련 데이터 모델/API 스펙은 최신인가?
- 엣지 케이스는 무엇이 있는가?

Claude Code에 작업을 시킬 때 이 컨텍스트를 **명시적으로** 전달합니다:

> "이 기능을 구현해줘. 참고: `src/features/auth/login.ts`의 패턴, `docs/api-spec.md`의 /signup 정의, User 모델은 `prisma/schema.prisma`에 있음."

### 4. 테스트 우선 또는 동시 작성

가능하면 **테스트를 먼저 또는 동시에** 작성합니다. AI는 명세가 테스트로 주어질 때 훨씬 정확하게 구현합니다.

흐름:

1. 수용 기준을 테스트 코드로 변환
2. 테스트 실패 확인 (Red)
3. 통과하는 최소 구현 (Green)
4. 리팩토링 (Refactor)

엄격한 TDD가 부담스럽다면 최소한 "구현 직후 테스트 작성"을 원칙으로 합니다.

### 5. 구현 (Implementation)

- **작게 커밋, 자주 커밋**: 한 커밋 = 한 논리적 변경
- **기존 패턴 따르기**: 새 패턴은 의식적으로만 도입
- **YAGNI(You Aren't Gonna Need It)**: 지금 필요 없는 추상화 금지
- **명명에 신경 쓰기**: 변수/함수 이름이 코드 품질의 절반
- **주석은 "왜"에 집중**: "무엇"은 코드가 말해준다

**Claude Code와 작업할 때**:

- 큰 모듈은 "인터페이스 먼저 → 구현 다음"으로 단계 분리
- 변경 후 항상 `git diff`를 사람이 검토
- AI가 "구현 완료"라고 해도 실제로 실행해보기 전엔 신뢰 X

### 6. 점진적 검증 (Incremental Verification)

한 태스크 안에서도 작은 단위로 검증을 끼워 넣습니다.

- 함수 하나 작성 → 단위 테스트 실행
- API 하나 추가 → curl/Postman으로 호출
- UI 컴포넌트 → 스토리북/브라우저에서 직접 확인

"30분 코딩 후 한 번에 디버깅"보다 "5분 코딩 후 즉시 검증"이 훨씬 빠릅니다.

### 7. 셀프 코드 리뷰

PR 올리기 전에 **본인이 먼저 리뷰**합니다.

- `git diff`로 전체 변경사항 훑기
- "내가 리뷰어라면 뭐라고 할까?" 시점으로 보기
- 디버그 코드, console.log, 주석 처리된 코드 정리
- 변수명/함수명 마지막 점검
- 누락된 에러 처리 확인

Claude Code에 별도 세션을 열어 "이 diff를 시니어 엔지니어 관점에서 비판적으로 리뷰해줘"라고 시키면 매우 유용합니다.

### 8. 커밋 & PR 생성

- **Conventional Commits 준수**: `feat:`, `fix:`, `refactor:` 등
- **커밋 메시지에 "왜"를 적기**: "무엇"은 diff가 말해준다
- **PR 설명 충실히**: 변경 이유, 테스트 방법, 스크린샷
- **셀프 체크리스트 통과 후 리뷰 요청**

### 9. 작업 로그 / 결정 기록

작업하며 내린 비자명한 결정은 짧게라도 기록합니다.

- 코드 주석 (TODO/FIXME/NOTE)
- PR 설명
- `docs/decisions/`에 ADR 추가
- `CLAUDE.md`에 새로 정해진 규칙 반영

이 기록이 다음 세션의 Claude(또는 동료)에게 컨텍스트가 됩니다.

## 서브에이전트(Sub-agent) 활용 방안

Claude Code의 강력한 기능 중 하나가 서브에이전트입니다. 메인 에이전트가 작업을 진행하면서, **격리된 컨텍스트를 가진 보조 에이전트에게 특정 작업을 위임**할 수 있습니다.

### 왜 서브에이전트를 써야 하는가

1. **컨텍스트 분리**: 메인 세션이 무거운 탐색/조사로 컨텍스트 창을 낭비하지 않게 됨
2. **전문화**: 역할별로 시스템 프롬프트를 다르게 줘서 특화된 응답을 얻음
3. **병렬성**: 독립적인 작업들을 동시에 처리
4. **재사용성**: 자주 쓰는 역할을 정의해두고 반복 호출

### 개발 단계에서 유용한 서브에이전트 패턴

#### 패턴 1: 코드 탐색 전용 에이전트 (Code Explorer)

**역할**: "이 기능과 관련된 기존 코드를 찾아서 요약 보고"

큰 코드베이스에서 메인 에이전트가 일일이 파일을 열어보면 컨텍스트가 금세 가득 찹니다. 탐색 전용 서브에이전트에게 "결제 로직과 관련된 모든 파일과 핵심 함수를 정리해줘"라고 위임하면, 결과 요약만 메인으로 돌아옵니다.

**예시 시나리오**:

> 메인 에이전트: "주문 환불 기능을 추가해야 해. 먼저 환불 관련 기존 코드를 조사해야 하는데..." → Code Explorer 서브에이전트 호출 → 서브: 결제/주문/환불 관련 파일 목록 + 핵심 함수 시그니처 + 데이터 흐름 요약 반환 → 메인: 요약본만 받아서 깨끗한 컨텍스트로 구현 시작

#### 패턴 2: 테스트 작성 전용 에이전트 (Test Writer)

**역할**: "주어진 함수/모듈에 대한 테스트 케이스 작성"

메인이 구현에 집중하고, 테스트 작성은 별도 에이전트에 위임합니다. 시스템 프롬프트에 다음을 박아둡니다:

- 사용 프레임워크 (Vitest/Jest 등)
- 테스트 컨벤션 (AAA 패턴, 명명 규칙)
- 커버해야 할 케이스 종류 (정상/엣지/에러)

#### 패턴 3: 코드 리뷰어 에이전트 (Code Reviewer)

**역할**: "이 diff를 시니어 엔지니어 관점에서 비판"

매우 효과적인 패턴입니다. 구현 직후 변경된 코드를 리뷰어 서브에이전트에 넘기면, 생성한 세션과 다른 시각에서 문제점을 찾아냅니다.

시스템 프롬프트 예시:

> "당신은 까다로운 시니어 엔지니어다. 다음 관점에서 비판적으로 리뷰하라: 버그 가능성, 보안 이슈, 성능 문제, 가독성, 컨벤션 일치, 테스트 누락. 칭찬은 생략하고 개선점만 지적하라."

#### 패턴 4: 디버거 에이전트 (Debugger)

**역할**: "에러 메시지/스택 트레이스/재현 단계를 받고 원인 분석"

버그 추적은 컨텍스트가 폭발하기 쉬운 작업입니다. 디버거 에이전트에 격리시키면 메인이 깔끔하게 유지됩니다.

위임할 때 함께 넘길 정보:

- 에러 메시지/스택 트레이스
- 재현 단계
- 관련 코드 경로
- 최근 변경 사항 (`git log`)

#### 패턴 5: 문서화 에이전트 (Documenter)

**역할**: "구현된 코드를 받아 README/API 문서/주석 작성"

구현이 끝난 코드를 넘기면 사용자 관점의 문서를 만들어줍니다. 메인은 다음 기능으로 넘어가고, 문서 작성은 백그라운드로 처리하는 그림이 됩니다.

#### 패턴 6: 마이그레이션/리팩토링 에이전트

**역할**: "특정 패턴을 일괄 변경"

예: "프로젝트 전체에서 `var`를 `const`로 바꾸기", "모든 API 호출에 에러 처리 추가". 반복적이지만 컨텍스트가 많이 필요한 작업에 적합합니다.

#### 패턴 7: 보안 감사 에이전트 (Security Auditor)

**역할**: "주어진 코드에서 보안 취약점 식별"

전용 시스템 프롬프트에 OWASP Top 10, 일반적인 취약 패턴을 명시해두고, 주기적으로 PR이나 특정 모듈을 감사하게 합니다.

### 서브에이전트 활용 원칙

1. **명확한 단일 책임**: 한 에이전트에 너무 많은 역할을 주지 말 것. "테스트 작성+실행+수정"보다 "테스트 작성"만.
    
2. **입력과 출력 형식을 정의**: 위임 시 무엇을 주고 무엇을 받을지 정해두면 결과를 메인에서 활용하기 쉽습니다.
    
3. **`.claude/agents/` 폴더에 정의 저장**: Claude Code는 프로젝트별 서브에이전트 정의를 지원합니다. 팀 전체가 같은 에이전트 셋을 공유할 수 있습니다.
    
    예시 구조:
    
    ```
    .claude/
      agents/
        code-explorer.md
        test-writer.md
        code-reviewer.md
        debugger.md
        security-auditor.md
    ```
    
4. **시스템 프롬프트는 구체적으로**: "테스트를 작성해줘"보다 "Vitest로 AAA 패턴, 파일명 `*.test.ts`, 정상/엣지/에러 케이스 각 1개 이상"이 훨씬 좋습니다.
    
5. **메인 에이전트의 컨텍스트 관리**: 서브에이전트에게 위임할 작업은 **결과 요약만** 메인이 받습니다. 메인이 모든 중간 과정을 추적할 필요 없습니다.
    
6. **병렬 실행 활용**: 독립적인 조사/작업은 여러 서브에이전트에 동시 위임 가능합니다. "프론트 패턴 조사"와 "백엔드 패턴 조사"를 동시에.
    

### 실전 워크플로 예시: "결제 환불 기능 추가"

```
1. 메인 에이전트가 작업 시작
2. → Code Explorer 서브에이전트: "결제/환불 관련 기존 코드 조사"
   → 요약 보고 받음
3. → 메인이 구현 계획 수립, 인터페이스 설계
4. → Test Writer 서브에이전트: "환불 함수의 테스트 케이스 작성"
   → 테스트 파일 받음
5. → 메인이 실제 구현 (테스트 통과 목표)
6. → Code Reviewer 서브에이전트: "이 diff를 리뷰"
   → 지적 사항 받음
7. → 메인이 수정
8. → Security Auditor 서브에이전트: "결제 관련이라 보안 점검"
   → 취약점 보고 받음
9. → 메인이 최종 마무리, 커밋, PR
```

메인 에이전트의 컨텍스트는 거의 "구현"에만 집중되어, 깨끗하게 유지됩니다.

### 서브에이전트의 한계

- **위임 비용**: 호출마다 약간의 오버헤드 발생. 사소한 작업은 직접 처리가 빠름.
- **결과 검증 필요**: 서브의 출력도 사람이 검증해야 함. 무한 위임은 책임 분산만 일으킴.
- **컨텍스트 단절**: 서브는 메인의 모든 맥락을 모름. 필요한 정보를 명시적으로 전달해야 함.

작은 작업: 직접 처리 / 큰 작업·반복 작업·맥락 많은 작업: 서브에이전트로 위임 — 이게 기준입니다.

## 개발 단계 체크리스트

- [ ] 작업이 1~4시간 단위로 분해되었는가
- [ ] 이슈 트래커에 등록되었는가
- [ ] 작업 시작 전 관련 문서/코드를 다시 읽었는가
- [ ] 테스트를 먼저 또는 동시에 작성했는가
- [ ] 작게, 자주 커밋했는가
- [ ] 점진적으로 실행/검증했는가
- [ ] 셀프 리뷰를 거쳤는가
- [ ] 디버그 코드/console.log를 제거했는가
- [ ] 커밋 메시지가 컨벤션을 따르는가
- [ ] PR 설명이 충실한가
- [ ] 비자명한 결정을 기록했는가
- [ ] (선택) 서브에이전트로 리뷰/보안/테스트 한 번 더 확인했는가

## 한 가지 조언

개발 단계에서 가장 흔한 실수는 **"한 번에 너무 많이 시키는 것"** 입니다. 사람이든 AI든, 작업 단위가 크면 품질이 떨어집니다.

- 사람이 한 번에 짤 수 있는 단위 < 30분
- AI에게 한 번에 시킬 수 있는 단위 < 200줄 내외 변경
