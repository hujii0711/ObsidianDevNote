**설계 및 AI 컨텍스트 정의 단계**는 기획 단계에서 만든 제품 요구사항 명세서(`prd.md`)를 바탕으로, 집을 짓기 위한 '기술 도면'을 그리고 클로드 코드(Claude Code)가 움직일 '작업 가이드라인'을 치는 과정입니다.

AI 에이전트는 컨텍스트(맥락)를 먹고 자라기 때문에, 이 단계에서 아키텍처와 규칙을 얼마나 촘촘하게 정의하느냐에 따라 개발 단계에서 AI가 내뱉는 코드의 품질이 완전히 달라집니다. 이 단계에서 수행해야 할 5가지 구체적인 작업을 소개해 드립니다.

---

## 설계 및 AI 컨텍스트 정의의 5가지 핵심 작업

### 1. 기술 스택 및 아키텍처 확정

어플리케이션을 지탱할 기술적 기반을 결정합니다. 프레임워크, 상태 관리 라이브러리, DB, 스타일링 도구 등을 명확히 해야 클로드가 엉뚱한 라이브러리를 임포트하는 불상사를 막을 수 있습니다.

- **Frontend:** React (Next.js App Router), Vue, Flutter 등
    
- **Backend / DB:** Node.js (NestJS), Python (FastAPI) / PostgreSQL, MongoDB 등
    
- **인프라/서비스:** Supabase, Firebase, AWS 등
    

### 2. 폴더 및 디렉토리 구조 표준화

프로젝트의 표준 폴더 구조를 미리 짜놓고 클로드에게 이 구조 내에서만 파일을 생성하도록 강제해야 합니다. 그렇지 않으면 클로드가 자기 마음대로 편리한 곳에 파일을 난사하게 됩니다.

코드 스니펫

```
src/
├── app/                  # Next.js App Router 레이어
├── components/           # 재사용 가능한 UI 컴포넌트
│   ├── common/           # Button, Input 등 공통 컴포넌트
│   └── domain/           # 특정 도메인(유저, 결제 등)에 종속된 컴포넌트
├── hooks/                # 커스텀 훅
├── services/             # API 비즈니스 로직
├── types/                # TypeScript 타입 정의 파일
└── utils/                # 공통 유틸리티 함수
```

### 3. 데이터 모델링 및 DB 스키마 설계

데이터의 흐름과 저장 방식을 정의합니다. SQL 테이블 구조나 ORM(Prisma, Drizzle, Mongoose 등) 스키마를 이 단계에서 미리 코드로 작성해 둡니다.

- 클로드에게 "prd.md를 참고해서 Prisma 스키마 파일(`schema.prisma`)을 먼저 작성해줘"라고 지시하여 이 단계를 자동화할 수도 있습니다. 스키마가 먼저 확정되어야 배포 및 API 개발이 매끄러워집니다.
    

### 4. 핵심 데이터 타입 및 API 인터페이스 정의 (TypeScript)

TypeScript를 사용한다면 앱 전반에서 사용할 핵심 데이터의 `interface`나 `type`을 먼저 선언해야 합니다. AI에게 이 타입 정의 파일들을 먼저 읽히면, 프론트엔드와 백엔드를 개발할 때 데이터 구조가 안 맞아 발생하는 휴먼 에러(및 AI 에러)를 90% 이상 예방할 수 있습니다.

- _예시:_ `types/user.ts`, `types/order.ts` 등을 먼저 생성하여 데이터 스펙을 박아둡니다.
    

### 5. AI 가이드라인 파일 작성 (★핵심)

클로드 코드가 프로젝트를 분석할 때 가장 먼저 읽고 엄격하게 준수해야 할 규칙(Rule of Game)을 파일로 작성합니다. 프로젝트 루트 디렉토리에 `.clauderules` 또는 `ai_rules.md` 같은 이름으로 저장합니다.

> 💡 **클로드 코드 전용 규칙 파일 예시 (`.clauderules`)**
> 
> Markdown
> 
> ```
> # 프로젝트 코딩 가이드라인
> 
> ## 1. 기술 스택 및 라이브러리 제약
> - UI 컴포넌트는 반드시 Tailwind CSS와 Shadcn UI만 사용한다.
> - 상태 관리는 Zustand를 사용하며, Redux는 절대 사용하지 않는다.
> - 모든 API 요청은 `services/api.ts`에 정의된 커스텀 Axios 인스턴스를 통한다.
> 
> ## 2. 코딩 스타일 및 컨벤션
> - 모든 컴포넌트는 함수형 컴포넌트(`const 컴포넌트 = () => {}`)로 작성한다.
> - 컴포넌트 파일 하나당 하나의 컴포넌트만 포함하며, 화살표 함수를 지향한다.
> - 비동기 처리는 항상 `try-catch` 블록으로 감싸고 로그는 `utils/logger.ts`를 사용한다.
> 
> ## 3. 작업 절차 규칙
> - 파일을 새로 생성하거나 수정하기 전에, 관련된 기존 파일의 구조를 반드시 `cat`이나 `grep`으로 먼저 확인하라.
> - 파괴적인 변경(기존 로직 수정)이 필요할 때는 코드 수정 전에 사용자에게 먼저 바꿀 방향을 제안하고 컨펌을 받아라.
> ```
