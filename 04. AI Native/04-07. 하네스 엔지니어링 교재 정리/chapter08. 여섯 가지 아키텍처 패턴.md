- 파이프라인 - 순서가 의미를 만든다
- 팬아웃.팬인 - 같은 입력, 다른 관점
- 전문가 풀 - 라우터 + 전문가
- 생성/검증 - 만들고 검사하고 다시 만든다
- 감독자 - 런타임 동적 분배
- 계층적 위임 - 총괄 -> 팀장 -> 실무자
	실무에서는 1단계(총괄 -> 팀장)는 에이전트 팀으로 두고, 2단계(팀장 -> 실무자)는 서브에이전트롤 구성하는 방식이 흔하다. 1단계는 실시간 조율이 필요하고, 2단계는 결과 반환만 필요하기 때문이다.

- 실제 하네스는 Phase마다 다른 패턴을 쓰고, Phase 간 경계를 `_workspace/` 파일로 잇는다. 실무에서는 단일 패턴보다 복합 패턴이 기본값이다.
Phase 1 팬아웃: 세 설계자가 같은 기능을 다른 층위로 동시에 설계
Phase 2 파이프라인: 백엔드 먼저, 프론트가 뒤따름
Phase 3 팬아웃: 두 테스트 병렬
Phase 4 생성-검증: QA가 발견한 이슈를 구현자에게 돌려보내는 루프

- 패턴 전환 신호

| 현재 패턴   | 전환 신호                                | 다음 패턴  |
| ------- | ------------------------------------ | ------ |
| 단일 에이전트 | 컨텍스트 폭발, 세션 중단 반발                    | 파이프라인  |
| 파이프라인   | 독립적 작업을 순차 처리하여 시간 낭비                | 팬아웃.팬인 |
| 팬아웃.팬인  | 작업별 다른 전문성 필요, 동일 역할로 한계             | 전문가 풀  |
| 전문가 풀   | 산출물 품질 편차, 검증 부재                     | 생성-검증  |
| 생성-검증   | 에이전트 간 실시간 조율 필요, 동적 작업 할당           | 감독자    |
| 감독자     | 단일 감독자가 5 ~ 10명 초과, 도메인이 서브팀으로 분해 가능 | 계층적 위임 |

- 감독자 패턴 표준 워크플로우 6단계

| 단계  | 동작                            | 도구          |
| --- | ----------------------------- | ----------- |
| 1   | 전체 대상 파일 목록 수집                | Glob / Read |
| 2   | 복잡도 추정(크기.의존성)                | 감독자         |
| 3   | 작업을 큐로 등록(의존성 포함)             | TaskCreate  |
| 4   | 워커들이 남은 작업을 가져가겠다고 선점(claim)  | TaskUpdate  |
| 5   | 성공 -> 다음 작업 / 실패 -> 원인 확인.재할당 | SendMessage |
| 6   | 모든 작업 완료 -> 리더가 통합 테스트        | 감독자         |
핵심은 4단계의 claim이다. 여기서 claim은 '이 작업은 제가 가져가겠습니다.'라고 작업 소유권을 확보하는 동작이다. (감독자가 A는 1번 하세요 라고 지시하지 않는다.)
