연결된 Google 서비스들이 있으니 실제 워크플로와 연동 가능한 플랜을 설계해드리겠습니다. 다만 이슈 트래킹과 PR은 GitHub/GitLab 기반이라 별도 연동이 필요한 부분도 함께 짚겠습니다.---

### 전체 흐름을 단계별로 설계하면

---

### Phase 1 — 이슈 등록 (이슈 에이전트)

오케스트레이터가 요청을 받으면 이슈 에이전트에게 구조화된 이슈 생성을 위임합니다. 핵심은 **이슈에 충분한 컨텍스트를 담아야 코드 에이전트가 별도 질문 없이 바로 구현에 들어갈 수 있다**는 점입니다.

```python
# 이슈 에이전트 출력 형식
issue_payload = {
    "title": "로그인 후 /dashboard 리디렉션 누락",
    "body": """
## 재현 조건
1. 이메일/비밀번호 로그인
2. 성공 응답 수신
3. /login에 머무름 (기대: /dashboard)

## 수용 기준 (코드 에이전트 체크리스트)
- [ ] redirectTo 파라미터 처리
- [ ] 세션 토큰 쿠키 설정
- [ ] E2E: 로그인 → /dashboard 도달 확인

## 관련 파일
- `src/auth/login.ts`
- `src/middleware/session.ts`
    """,
    "labels": ["bug", "auth", "priority:high"],
    "assignees": ["claude-code-agent"]
}
```

이슈에 `수용 기준`을 체크리스트 형식으로 넣어두면 PR 생성 시 자동으로 연결됩니다.

---

### Phase 2 — 코드 에이전트 구현 + PR 생성

코드 에이전트는 이슈 번호를 브랜치명에 포함시켜 GitHub가 자동으로 이슈와 PR을 연결하게 합니다.

```bash
# 브랜치 명명 규칙 (이슈 자동 연결)
git checkout -b fix/42-login-redirect

# PR 본문에 Closes 키워드 → 머지 시 이슈 자동 close
gh pr create \
  --title "fix: 로그인 후 /dashboard 리디렉션 누락 수정" \
  --body "Closes #42

## 변경 사항
- redirectTo 쿼리 파라미터 처리 로직 추가
- 세션 미들웨어 쿠키 설정 경로 수정

## 테스트 범위
- [ ] 유닛: session.test.ts
- [ ] E2E: auth.spec.ts → login-redirect 시나리오" \
  --draft  # 처음엔 draft로 생성, E2E 통과 후 ready로 전환
```

PR을 처음에 **draft**로 생성하는 것이 핵심입니다. E2E 에이전트가 통과 신호를 보낸 뒤에 `ready for review`로 전환해야 리뷰 에이전트와 인간 리뷰어가 불완전한 PR을 보는 일이 없습니다.

```python
# E2E 통과 후 오케스트레이터가 draft 해제
if e2e_result["status"] == "passed":
    gh_api.pull_requests.update(
        pr_number=pr["number"],
        draft=False  # ready for review 전환
    )
    # 이 시점에 리뷰 에이전트 트리거
    trigger_review_agent(pr_number=pr["number"])
```

### Phase 3 — 리뷰 에이전트 (자동 1차 리뷰)

리뷰 에이전트는 PR diff를 분석해서 세 가지 역할을 합니다.

**자동 통과 판정** — 변경 범위가 작고 이슈 체크리스트가 전부 충족된 경우:

```python
review_result = {
    "action": "approve",
    "body": """
✅ 자동 리뷰 통과

체크리스트:
- [x] redirectTo 파라미터 처리 확인
- [x] 세션 쿠키 설정 경로 수정 확인  
- [x] E2E auth.spec.ts 통과 (2/2)
- [x] 기존 테스트 회귀 없음

변경 범위: 2 files, +34 -8 lines → 인간 리뷰 불필요 임계값 이하
    """
}
```

**수정 요청** — 규칙 위반이나 누락 항목이 있는 경우:

```python
review_result = {
    "action": "request_changes",
    "comments": [
        {
            "path": "src/auth/login.ts",
            "line": 47,
            "body": "⚠️ CLAUDE.md 규칙 위반: catch 블록에서 에러를 삼키고 있습니다.\n"
                    "AppError를 throw하거나 logger.error를 사용해야 합니다."
        }
    ]
}
```

**인간 리뷰 에스컬레이션** — 변경 범위가 크거나 아키텍처 결정이 포함된 경우:

```python
if changed_files > 10 or "architecture" in issue["labels"]:
    notify_human_reviewer(
        pr_number=pr["number"],
        reason="변경 범위 초과 또는 설계 결정 포함 — 인간 리뷰 필요"
    )
```

### Phase 4 — 수정 루프 (코드 에이전트 재진입)

리뷰 에이전트의 코멘트가 코드 에이전트에게 다시 들어갈 때, **코멘트를 그대로 붙여넣는 것이 아니라 구조화된 수정 지시**로 변환해야 합니다.

```python
# 리뷰 코멘트 → 코드 에이전트 재지시 변환
def build_fix_prompt(review_comments):
    return f"""
이전 PR #{pr_number}에서 다음 수정이 요청됐습니다:

{chr(10).join([
    f"파일: {c['path']}:{c['line']}\n문제: {c['body']}"
    for c in review_comments
])}

수정 후 기존 테스트가 깨지지 않는지 확인하고,
같은 PR 브랜치에 커밋해주세요.
"""
```

수정이 완료되면 E2E 에이전트 → 리뷰 에이전트 순서로 다시 트리거합니다. 이 루프는 최대 3회를 넘지 않도록 제한을 두는 것이 안전합니다. 3회 초과 시 인간에게 에스컬레이션합니다.

### Phase 5 — 머지 후 CLAUDE.md 규칙 보강

가장 중요한 단계입니다. 리뷰에서 반복적으로 지적된 패턴이 있다면 다음 이슈부터는 처음부터 맞게 작성되도록 규칙으로 굳혀야 합니다.

````python
# 수정 요청 패턴 집계 → 규칙 후보 생성
def extract_rule_candidates(merged_prs, window_days=14):
    patterns = Counter()
    for pr in merged_prs:
        for comment in pr.review_comments:
            if comment.author == "review-agent":
                patterns[comment.category] += 1
    
    # 임계값 초과 시 규칙 후보 등록
    return [p for p, count in patterns.items() if count >= 3]

# CLAUDE.md 자동 PR 생성
rule_pr_body = """
## 자동 규칙 보강

지난 14일간 리뷰에서 3회 이상 반복된 패턴:

### 에러 핸들링 (5회 지적)
```typescript
// ❌ 금지
catch (e) { console.log(e) }

// ✅ 필수
catch (e) { logger.error(e); throw new AppError(e) }
````

근거 이슈: #38, #41, #42, #45, #47 """

```

이렇게 하면 **이슈 → PR → 리뷰 → 수정 → 규칙**으로 이어지는 루프가 완전히 닫히고, 같은 실수가 반복될수록 오히려 시스템이 더 강해지는 구조가 됩니다.
```
