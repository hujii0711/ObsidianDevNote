
좋은 지적이에요. 이번 답변에서 파인튜닝을 뺀 건 의도적이었는데, 이유를 설명드릴게요.

**지금 문제의 본질은 "지식 검색" 문제이지 "스타일/패턴 학습" 문제가 아니기 때문이에요**

15k 프롬프트 문제의 핵심은:
- 매번 관련 없는 정보까지 다 들어가서 비용/성능이 낭비됨
- 질문에 필요한 부분만 골라 넣고 싶음

**파인튜닝이 이 문제를 해결 못 하는 이유**

1. **파인튜닝해도 문서를 "다시 넣어야 하는 문제"는 그대로**
 - 파인튜닝은 모델 가중치에 지식/패턴을 "체화"시키는 것이지, 매 요청마다 프롬프트에 문서를 넣는 구조 자체를 없애주지 않음
 - 오히려 "파인튜닝했으니 문서 안 넣어도 되지 않나?"라고 착각하기 쉬운데, 이게 정확히 다음 항목의 문제로 이어짐

2. **환각(hallucination) 위험 증가**
 - 파인튜닝은 지식을 정확히 "저장"하는 게 아니라 패턴을 학습하는 것에 가까움
 - API 시그니처, 파라미터명, 정확한 사용법 같은 **사실 기반 정보**는 파인튜닝만으로는 부정확하게 기억되거나 그럴듯하게 지어낼(confabulate) 위험이 큼
 - 반면 RAG는 실제 문서를 검색해서 근거로 제시하므로 답변의 사실 정확도가 높고, 출처 추적도 가능

3. **업데이트 대응력 차이**
 - 프레임워크 문서가 바뀔 때마다 RAG는 벡터DB만 갱신하면 되지만, 파인튜닝은 재학습이 필요함
 - 사내 프레임워크는 계속 업데이트될 가능성이 높으므로 유지보수 비용 차이가 큼

4. **지금 문제(15k 토큰 비효율)와 직접 관련 없음**
 - 파인튜닝은 "모델이 얼마나 잘 아는가"의 문제를 다루지, "프롬프트에 뭘 얼마나 넣는가"의 구조적 비효율 문제는 다루지 않음
 - 이 질문에서 필요한 건 정확히 RAG가 겨냥하는 문제였음

**파인튜닝이 유용한 경우는 따로 있어요**
- 특정 코딩 스타일/컨벤션을 "체화"시키고 싶을 때
- 반복되는 응답 포맷이나 톤을 일관되게 만들고 싶을 때
- RAG로 검색된 컨텍스트를 "어떻게 활용해서 답변할지"의 패턴을 학습시키고 싶을 때 (RAG + 파인튜닝 병행)

**정리하면**: 첫 답변에서 말씀드렸듯 실무에서는 RAG를 기본으로 깔고 필요시 파인튜닝을 더하는 조합이 일반적인데, 이번 15k 프롬프트 문제는 명확히 "검색/컨텍스트 관리" 이슈였기 때문에 RAG 중심으로 답변드렸어요. 파인튜닝은 이 특정 문제의 해결책이라기보다는 별도 축의 개선(스타일/일관성)에 가깝습니다.
