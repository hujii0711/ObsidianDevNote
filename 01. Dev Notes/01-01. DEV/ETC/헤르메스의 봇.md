
**봇 = 새로운 에이전트가 아니라 "메인 에이전트의 재구성"** Bot Mode의 핵심 가치는 새로운 에이전트 인프라를 추가하는 것이 아니라, 기존 프로필을 역할별로 구분해 반복적으로 사용하기 쉽게 만드는 데 있습니다. Bot Mode에서 봇은 별도의 핵심 객체가 아니라, 기존 Hermes Agent 프로필을 봇처럼 표시하고 관리하는 UI 계층일 뿐입니다.

그러니까 "여러 봇을 만든다"는 게 사실은:
- 완전히 독립적인 여러 개의 AI를 새로 돌리는 게 아니라
- **같은 헤르메스 코어(AIAgent 클래스)**를 프로필 단위로 여러 벌 인스턴스화해서, 각각 다른 모델·메모리·스킬·자격 증명을 물려주는 것

**왜 "메인 에이전트와 유사"하게 느껴지는가** 플랫폼에 독립적인 코어 구조로, 하나의 AIAgent 클래스가 CLI, 게이트웨이, ACP, 배치, API 서버를 모두 담당하며, 플랫폼 차이는 에이전트 자체가 아니라 진입점에만 있습니다. 즉 봇이든, CLI에서 직접 쓰는 "메인" 세션이든, 내부적으로 돌아가는 엔진은 완전히 동일합니다. 다른 건 껍데기(진입점)와 설정값(프로필)뿐입니다.

**비유하자면** 윈도우에서 같은 프로그램을 서로 다른 사용자 계정으로 여러 개 로그인해 쓰는 것과 비슷합니다. 프로그램(엔진) 자체는 하나지만, 계정(프로필)마다 바탕화면·설정·파일이 따로 있는 것처럼요. "메인 에이전트"라는 것도 사실 default 프로필로 실행되는 봇 중 하나일 뿐이고, 다른 봇들과 본질적으로 다르지 않습니다.

그래서 여러 봇을 운영해도 인프라나 리소스가 몇 배로 늘어나는 게 아니라, 같은 엔진 위에 설정(프로필)만 여러 벌 얹는 구조라서 상대적으로 가볍게 확장할 수 있는 겁니다.

---

헤르메스(Hermes Agent, Nous Research의 오픈소스 AI 에이전트)에 텔레그램·디스코드·슬랙 같은 메신저 봇을 등록하면, 그 봇은 **"메시징 게이트웨이"** 역할을 합니다. 구체적으로는 이렇습니다.

**1. 에이전트로 가는 입구(entry point)** 봇 자체가 지능을 갖는 게 아니라, CLI에서만 쓰던 헤르메스 에이전트를 해당 메신저에 연결해주는 다리 역할을 합니다. 플랫폼에 독립적인 코어 구조로, 하나의 AIAgent 클래스가 CLI, 게이트웨이, ACP, 배치, API 서버를 모두 담당하며, 플랫폼별 차이는 에이전트 자체가 아니라 진입점에만 있습니다.

**2. 상시 대기 + 비동기 작업 창구** 노트북을 닫아도 계속 작업할 수 있게 해주며, 단순히 메신저에서 채팅하는 것을 넘어 비동기 작업 창구 역할도 합니다. 예약된 리서치나 보고 작업을 백그라운드에서 수행하고 결과를 봇을 통해 전달받는 식입니다.

**3. 하나의 에이전트, 여러 메신저로 접근** 대화 기록은 채팅방마다 따로 관리되지만, 같은 헤르메스 홈 디렉터리를 쓰는 한 메모리·스킬·설정·모델 선택은 공통으로 이어집니다. 그래서 텔레그램에서는 운영 보고를 받고, 디스코드에서는 협업하고, 슬랙에서는 알림만 받는 식으로 메신저별 역할을 나눠 쓸 수 있습니다.

**4. 예약 작업 결과 전달 채널** 자연어나 cron 문법으로 예약한 프롬프트 실행 결과를 데스크탑뿐 아니라 텔레그램, 디스코드, 슬랙, 이메일 등으로 전달하는 역할도 합니다.

**5. 보안/접근 제어 지점** 봇을 등록할 때 허용된 사용자 ID를 지정해야 하는데, 허용 사용자 ID 없이 봇을 열어두면 누구나 봇에 메시지를 보낼 수 있어 본인 ID만 허용하는 것이 권장됩니다.

정리하면, 봇 등록은 "새로운 에이전트를 만드는 것"이 아니라 **기존 헤르메스 에이전트에 메신저 인터페이스 하나를 붙이는 작업**이며, 이를 통해 언제 어디서든 같은 에이전트(같은 메모리·페르소나·스킬)에 접근하고 예약 작업 결과를 실시간으로 받아볼 수 있게 됩니다.

여러 봇을 등록할 때는 "많이 만들기"보다 **"역할의 경계를 명확히 나누기"**가 핵심 전략입니다. 실무 가이드와 공식 문서를 종합하면 다음과 같은 전략이 적절합니다.

**1. 역할(직무) 기준으로 분리하기** Bot Mode를 효과적으로 활용하려면 봇을 많이 만드는 것보다 역할의 경계를 명확히 정해야 하며, 필요한 모델·스킬·메모리·자격 증명이 뚜렷하게 다를 때만 별도 봇을 만드는 것이 유용합니다. 반대로 설정은 같고 질문 주제만 다르다면 새 봇보다 같은 봇 안의 새 세션이 더 단순합니다. 예: 조사용 봇, 코딩용 봇, 문서 작성용 봇처럼 목적이 분명한 봇을 한 번 구성해두고 반복 재사용하는 방식입니다.

**2. 봇마다 최적 모델을 다르게 고정** 각 봇은 고유한 설정, 고정 모델, 메모리, 스킬, 자격 증명, 채팅 기록을 가진 독립된 프로필입니다. 예를 들어 리서치 봇은 검색·추론에 강한 모델, 코딩 봇은 코드 특화 모델, 일상 비서 봇은 응답 속도가 빠른 저비용 모델처럼 역할에 맞게 모델을 다르게 물려두는 전략이 유효합니다.

**3. 메모리·컨텍스트 오염 방지** 목적별 에이전트 분리는 코딩 보조용, 리서치용, 개인 비서용 등 역할별로 메모리·스킬·config가 섞이지 않게 운영하기 위함입니다. 업무용 봇에 개인 일정 이야기가 섞이거나, 리서치 봇 메모리에 코드 컨텍스트가 쌓이는 걸 막아줍니다.

**4. 메신저/계정별 토큰 분리** 같은 머신에서 텔레그램·디스코드·슬랙 봇을 각각 다른 계정·토큰으로 동시에 띄울 때는 프로파일별로 .env를 두면 토큰 충돌 없이 운영할 수 있습니다.

**5. 봇 간 협업(멀티 에이전트 팀) 구조** 봇은 모든 모델을 쓸 수 있고 서로 통신도 가능하며, 한 번 만든 전문 봇을 계속 재사용할 수 있습니다. 실제로 CEO/CTO/PM/개발/QA처럼 계층적 역할을 가진 여러 봇이 서로 메시지를 주고받으며 협업하는 팀 구조로 운영하는 사례도 있습니다. 예를 들어 총괄(퍼실리테이터) 봇이 하위 전문 봇들에게 작업을 위임하고 결과를 취합하는 식입니다.

**6. 위험한 실험은 복제본으로** 설정 대수술이나 새 모델 전환처럼 위험할 수 있는 변경을 시도하기 전에 현재 프로파일을 그대로 복제해두면, 잘못돼도 원본은 그대로 남습니다.

**실전 정리 팁**

- 먼저 자주 반복하는 업무를 나열하고, 각 업무에 메모리·도구가 정말 분리되어야 하는지 판단하는 것이 출발점입니다.
- 봇 이름·아바타를 역할에 맞게 지정해두면, 여러 세션을 일일이 열어보지 않아도 어떤 봇이 무슨 역할을 맡았는지 한눈에 파악할 수 있습니다.

**권장 시작 구성 예시**: ① 리서치/뉴스 봇(검색 강점 모델), ② 코딩/개발 봇(코드 특화 모델), ③ 개인 비서/일정 봇(빠르고 저렴한 모델) — 이렇게 3개 정도로 시작해서 필요에 따라 세분화하는 것이 과도한 인프라 증식 없이 관리하기 좋은 방식입니다.
