
LangGraph에서 말하는 <mark style="background:#fff88f">그래프(Graph)는 단순히 작업을 연결한 그림이 아니라, AI가 어떤 상태에서 어떤 작업을 수행하고, 그 결과에 따라 다음에 무엇을 할지 결정하는 구조라고 이해</mark>하면 가장 정확합니다.

근본적인 의미를 이해하려면 수학의 그래프 이론부터 시작해서, 프로그램의 제어 흐름, 마지막으로 AI 에이전트까지 연결해 보는 것이 좋습니다.

## 1. 그래프의 근본적인 의미

수학과 컴퓨터 과학에서 그래프는 기본적으로 두 가지 요소로 구성됩니다.

- 노드(Node): 어떤 대상이나 상태, 작업을 나타내는 점
- 엣지(Edge): 노드 사이의 관계나 이동 경로를 나타내는 연결선

## 그래프의 가장 단순한 형태
```
    [A: 입력]
        |
        v
    [B: 처리]
        |
        v
    [C: 출력]
```

A, B, C는 노드이고, 화살표는 노드 사이의 관계 및 이동 방향을 나타냅니다.
여기서 중요한 점은 그래프 자체는 작업을 실행하지 않는다는 것입니다.
<mark style="background:#fff88f">그래프는 무엇이 존재하고, 무엇이 무엇과 연결되어 있으며, 어떤 경로로 이동할 수 있는지를 표현하는 구조입니다. </mark>실제 실행은 그래프를 해석하고 순회하는 프로그램이 담당합니다.

예를 들어 지도도 그래프가 될 수 있습니다.

- 노드: 서울역, 판교역, 강남역
- 엣지: 역 사이의 철도 연결
- 실행 주체: 실제로 경로를 탐색하는 알고리즘

지도에 역과 철도가 그려져 있다고 기차가 자동으로 움직이지는 않습니다. 그래프는 구조를 정의하고, 실행 주체가 그 구조를 따라 움직입니다.

이 개념이 LangGraph를 이해하는 출발점입니다.

## 2. 그렇다면 일반적인 프로그램도 그래프인가?

그렇습니다. 사실 일반적인 프로그램의 실행 흐름도 그래프로 표현할 수 있습니다.
예를 들어 다음 코드를 생각해 보겠습니다.

```
function process(question) {
  const result = search(question);

  if (result.length > 0) {
    return generateAnswer(result);
  }

  return askForMoreInformation();
}
```

이 코드는 다음과 같은 실행 그래프로 해석할 수 있습니다.
```
       [질문 입력]
            |
            v
       [검색 실행]
            |
            v
   [검색 결과가 있는가?]
         /       \
       예          아니오
       |             |
       v             v
 [답변 생성]   [추가 정보 요청]
       |             |
       v             v
    [종료]         [종료]
```

여기서 핵심은 두 가지입니다.

첫째, 그래프는 순서만 표현하는 것이 아닙니다. 조건에 따라 서로 다른 경로로 이동하는 것도 표현할 수 있습니다.

둘째, 프로그램의 흐름을 그래프로 표현하면 작업을 추가하거나, 분기를 바꾸거나, 반복 경로를 만드는 일을 명시적으로 설계할 수 있습니다.

다만 모든 프로그램이 반드시 그래프 자료구조를 직접 만들어 실행하는 것은 아닙니다. 그래프는 프로그램의 제어 흐름을 이해하는 하나의 모델이기도 합니다.

## 3. LangGraph는 기존 프로그램의 그래프와 무엇이 다른가?

<mark style="background:#fff88f">LangGraph의 차별점은 그래프를 단순한 실행 순서가 아니라 상태(State)를 공유하며 실행되는 AI 워크플로의 구조로 활용</mark>한다는 것입니다.

LangGraph의 주요 개념을 연결하면 다음과 같습니다.

| 개념               | 근본적인 의미                                  |
| ---------------- | ---------------------------------------- |
| State            | 현재 작업 전체가 공유하는 데이터와 진행 상황                |
| Node             | 상태를 읽고 작업을 수행하는 함수                       |
| Edge             | 작업이 끝난 뒤 다음에 이동할 경로                      |
| Conditional Edge | 현재 상태나 결과에 따라 다음 경로를 결정하는 규칙             |
| Checkpointer     | 실행 상태를 저장하여 재개하거나 대화 이력을 유지할 수 있도록 하는 기능 |

이를 한 문장으로 표현하면 다음과 같습니다.

LangGraph = 상태를 중심으로 노드의 실행과 이동 경로를 관리하는 런타임 구조

여기서 상태가 특히 중요합니다.

예를 들어 사내 문서를 검색하는 AI를 만든다고 해 보겠습니다.

처음에는 상태에 질문만 존재합니다.

```
state = {
    "question": "WebSquare 설정 방법은?",
    "documents": [],
    "answer": ""
}
```

검색 노드가 실행되면 검색 결과가 상태에 추가됩니다.

```
state = {
	"question": "WebSquare 설정 방법은?",
	"documents": ["설정 문서 A", "설정 문서 B"],
	"answer": ""
}
```

답변 생성 노드가 실행되면 답변이 추가됩니다.

```
state = {
	"question": "WebSquare 설정 방법은?",
	"documents": ["설정 문서 A", "설정 문서 B"],
	"answer": "설정 파일에서 해당 속성을 변경합니다."
}
```

각 노드는 상태를 기반으로 작업하고, 그 결과가 다음 노드의 작업에 영향을 줍니다.

실제 LangGraph에서는 상태 스키마와 각 노드의 반환값을 통해 상태 변경을 관리합니다. 위 코드는 개념을 설명하기 위해 전체 상태를 직접 갱신한 예시입니다.

## 4. 그래프가 단순한 파이프라인을 넘어서는 순간

AI 시스템에서 그래프의 진정한 가치는 실행 도중에 다음 행동을 바꿀 수 있다는 점에서 드러납니다.

### 예시: 검색 결과의 품질에 따라 행동하는 AI

```
       [질문 입력]
            |
            v
       [질문 분석]
            |
            v
       [문서 검색]
            |
            v
       [검색 결과 평가]
          /       \
       충분함      부족함
         |           |
         v           v
    [답변 생성]  [검색 조건 수정]
         |           |
         v           v
       [종료]     [문서 검색]
                     |
                     +-----> [검색 결과 평가]
```

재검색 경로는 다시 검색 노드로 연결될 수 있습니다. 종료 조건을 설정하지 않으면 반복이 길어질 수 있습니다.

일반적인 파이프라인은 다음과 같이 고정되어 있습니다.

`입력 → 검색 → 답변 생성 → 종료`

반면 LangGraph에서는 다음과 같은 흐름을 설계할 수 있습니다.

`입력 → 검색 → 평가 → (답변 생성 또는 재검색) → 평가 → ...`

이 구조에서는 실행 경로가 처음부터 완전히 고정되어 있지 않습니다. 실행 중에 만들어진 상태와 조건에 따라 다음 단계가 달라질 수 있습니다.

단, 그래프가 스스로 판단하는 것은 아닙니다. 분기 조건을 작성자가 정의하거나, 노드에서 LLM을 호출해 판단 결과를 얻고, 그래프의 제어 규칙이 그 결과에 따라 경로를 선택하는 것입니다.

## 5. 가장 근본적인 관점: 그래프는 AI의 사고 과정인가?

여기서는 개념을 구분해야 합니다.

- 그래프 구조는 가능한 작업과 이동 경로를 정의합니다.
    
- 상태는 현재까지 얻은 정보와 작업 결과를 담습니다.
    
- LLM은 주어진 입력을 바탕으로 답변하거나 다음 행동을 판단할 수 있습니다.
    
- 실행 엔진은 정해진 제어 규칙에 따라 노드를 호출하고 상태 변경과 경로 이동을 처리합니다.
    

즉, 그래프 그 자체가 AI의 사고 과정은 아닙니다.

예를 들어 LLM에게 "검색을 더 해야 할까?"라고 질문하고, LLM이 `재검색`이라고 반환했다고 해 보겠습니다.

이때 역할은 다음처럼 분리됩니다.

1. LLM이 재검색이 필요하다고 판단합니다.
    
2. 그 판단 결과가 상태에 반영됩니다.
    
3. 조건부 엣지가 상태를 확인합니다.
    
4. 그래프 실행기가 재검색 노드를 실행합니다.
    

이것이 LangGraph를 이해할 때 중요한 관점입니다. LLM의 판단과 프로그램의 실행 제어를 분리하고, 둘을 그래프 구조로 결합하는 것입니다.

## 6. LangGraph와 일반적인 함수 호출, 그리고 MCP의 관계

사용하는 기술을 구분하면 그래프의 의미가 더 명확해집니다.

|기술|핵심 역할|비유|
|---|---|---|
|Python 함수|개별 작업 수행|도구 하나|
|MCP|AI 애플리케이션과 외부 도구·데이터 사이의 표준화된 연결|도구를 사용할 수 있는 연결 규격|
|LangGraph|작업 순서, 분기, 반복, 상태 전이 관리|작업을 지휘하는 실행 계획|
|LLM|언어 이해, 생성, 판단|주어진 맥락에서 판단하는 모델|

예를 들어 로컬 Qwen 모델과 사내 문서 검색 시스템을 연결한다고 합시다.

- Qwen은 질문을 분석하고 답변을 생성합니다.
    
- MCP 서버는 검색 API 같은 외부 기능을 모델을 사용하는 애플리케이션에 노출할 수 있습니다.
    
- LangGraph는 검색할 시점, 검색 결과를 평가할 시점, 다시 검색할지 또는 답변을 생성할지를 관리할 수 있습니다.
    

MCP가 반드시 필요한 것은 아닙니다. 검색 함수를 Python에서 직접 호출해도 됩니다. 반대로 MCP를 사용한다고 해서 LangGraph가 반드시 필요한 것도 아닙니다.

둘은 서로 다른 문제를 해결합니다.

## 결론: 그래프를 근본적으로 어떻게 이해해야 할까?

저는 LangGraph를 이해할 때 다음 세 가지 층위를 구분하는 것이 가장 중요하다고 봅니다.

1. 구조의 관점
그래프는 어떤 작업들이 있고, 어떤 작업끼리 연결될 수 있는지를 표현합니다.

2. 상태의 관점
상태는 현재까지 무엇을 알고 있고, 어떤 결과를 얻었으며, 다음 판단에 필요한 정보가 무엇인지를 표현합니다.

3. 실행의 관점
실행 엔진은 상태와 제어 규칙에 따라 노드를 실행하고, 다음 노드로 이동하며, 필요한 경우 반복하거나 종료합니다.

결국 LangGraph에서 그래프를 사용한다는 것은 단순히 여러 AI를 연결한다는 의미가 아닙니다.

AI 시스템의 작업 구조와 실행 경로를 명시적으로 모델링하고, 상태에 따라 실행을 제어할 수 있도록 만든다는 의미입니다.

이 관점으로 보면 LangGraph는 단순한 AI 라이브러리라기보다, LLM을 포함하는 복잡한 프로그램의 실행 흐름을 관리하는 프레임워크에 가깝습니다.
