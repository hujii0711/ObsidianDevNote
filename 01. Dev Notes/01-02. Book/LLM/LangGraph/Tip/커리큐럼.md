
LangGraph의 최신 버전 기준으로 커리큘럼을 짜기 위해 먼저 현재 상태를 확인해볼게요.

## 먼저 알아둘 현재 상황 (2026년 11월 기준)

커리큘럼 순서에 영향을 주는 변화가 있어서 먼저 정리합니다.

- langgraph는 2026-09-21에 1.2.12가 릴리스되었고, 현재 1.2.x 계열이 이어지고 있습니다.
- LangGraph v1은 안정성에 초점을 둔 릴리스로, 핵심 그래프 API와 실행 모델은 그대로 두고 타입 안정성과 개발 편의성을 다듬었습니다. 그래서 예전 튜토리얼의 그래프 기본 개념(State, Node, Edge)은 여전히 유효합니다.
- `langgraph.prebuilt`의 `create_react_agent`는 deprecated 되었고, LangChain의 `create_agent`로 대체되었습니다. 오래된 블로그 코드를 따라 하면 이 부분에서 막힐 수 있습니다.
- LangGraph는 저수준 런타임이고, LangChain은 그 위에 올라간 고수준 API입니다. LangChain 1.0은 `create_agent`와 함께 요약, 승인 절차, PII 마스킹 같은 동작을 끼워 넣는 미들웨어 시스템을 도입했습니다.

따라서 학습 순서는 **LangChain 1.0 (create_agent) → LangGraph 직접 구현** 으로 가는 것이 효율적입니다. 높은 수준에서 먼저 동작을 이해한 뒤, 그 아래 런타임을 직접 다루는 방식입니다.

## 0단계. 선수 지식 점검

**목표:** LangGraph 자체가 아니라 그 밑바닥에 깔린 지식 때문에 막히지 않도록 하기

- **Python 중급**: `TypedDict`, `dataclass`, `typing`(`Annotated`, `Literal`, `Optional`), 제너레이터, 데코레이터
- **Pydantic v2**: `BaseModel`, 검증, 스키마 생성 (구조화 출력과 도구 스키마의 기반)
- **async/await**: `asyncio`, `async for`, 이벤트 루프 개념
- **LLM 기초**: 프롬프트 구성, system/user/assistant 메시지, 토큰·컨텍스트 윈도우, temperature
- **Tool calling 개념**: 모델이 함수 호출을 "요청"하고, 실제 실행은 애플리케이션이 하는 구조
- **환경 구성**: `uv` 또는 `venv`, `.env` 관리, API 키 다루기

**체크포인트:** LLM API를 직접 호출해 tool calling 한 사이클(모델 요청 → 함수 실행 → 결과 전달 → 최종 답변)을 프레임워크 없이 구현해보기

## 1단계. LangChain 1.0 기초

**목표:** 모델·도구·메시지를 다루고 `create_agent`로 동작하는 에이전트 만들기

**학습 항목**

1. 모델 초기화: `init_chat_model`, 공급자별 클래스(`ChatOpenAI`, `ChatAnthropic` 등)
2. 메시지 타입: `HumanMessage`, `AIMessage`, `SystemMessage`, `ToolMessage`, 표준 content blocks
3. 도구 정의: `@tool` 데코레이터, docstring과 타입 힌트가 스키마가 되는 원리, `args_schema`
4. 구조화 출력: Pydantic 모델, `with_structured_output`, `response_format`(ToolStrategy / ProviderStrategy)
5. `create_agent`: `model`, `tools`, `system_prompt`, `middleware`, `checkpointer` 파라미터
6. 미들웨어 기초: 요약, 승인, PII 마스킹 등 내장 미들웨어 사용 → 커스텀 미들웨어 작성(훅 위치 이해)

**실습**

- 날씨/계산/검색 도구 3개를 가진 에이전트 만들기
- 같은 에이전트를 모델 공급자만 바꿔서 실행해보기
- 구조화 출력으로 JSON 스키마에 맞는 결과 받기

## 2단계. LangGraph 핵심 개념

**목표:** 그래프를 직접 설계하고 실행 흐름을 완전히 예측할 수 있게 되기

**학습 항목**

1. **State**: `TypedDict`/Pydantic 기반 상태 스키마, input/output 스키마 분리
2. **Reducer**: `Annotated[list, add_messages]`, 커스텀 reducer, 상태 업데이트가 "덮어쓰기"인지 "누적"인지 구분
3. **Node**: 상태를 받아 부분 업데이트를 반환하는 함수, `RunnableConfig` 수신
4. **Edge**: 일반 엣지, 조건부 엣지(`add_conditional_edges`), `START`/`END`
5. **Command**: 노드에서 상태 업데이트와 라우팅(`goto`)을 동시에 처리
6. **Send API**: 동적 병렬 실행(map-reduce 패턴)
7. **컴파일과 실행**: `compile()`, `invoke`, `stream`, `ainvoke`
8. **실행 모델**: Pregel 스타일 super-step, 병렬 노드 실행 순서, `recursion_limit`
9. **Runtime context**: 그래프 실행 시 전달하는 설정값(사용자 ID, DB 연결 등)
10. **그래프 시각화**: Mermaid 출력으로 구조 확인

**실습**

- ReAct 루프(LLM 노드 → 도구 노드 → 조건부 엣지로 반복)를 `create_agent` 없이 직접 구현
- 직접 만든 것과 `create_agent` 결과를 비교하며 내부 구조 이해
- 병렬 노드 두 개가 같은 상태 키를 갱신할 때 reducer 유무에 따른 차이 실험

**체크포인트:** 그래프 그림만 보고 상태가 어떻게 변할지 설명할 수 있어야 함

## 3단계. 워크플로·에이전트 설계 패턴

**목표:** "언제 에이전트가 필요하고 언제 고정 워크플로로 충분한지" 판단하는 감각 기르기

**학습 항목 (Anthropic의 "Building effective agents" 분류와 LangGraph 공식 가이드 참고)**

1. **Prompt chaining**: 단계별 순차 처리, 중간 검증 게이트
2. **Routing**: 입력을 분류해 전문 경로로 분기
3. **Parallelization**: 독립 작업 동시 실행, 투표/앙상블
4. **Orchestrator-worker**: 계획 수립 후 워커에 동적 분배 (`Send` 활용)
5. **Evaluator-optimizer**: 생성 → 평가 → 개선 루프
6. **ReAct 에이전트**: 도구 호출 루프
7. **Plan-and-execute / Reflection**: 계획 분리, 자기 검토
8. LangGraph 공식 "Thinking in LangGraph" 가이드로 문제를 노드 단위로 쪼개는 사고법 익히기

**실습**

- 같은 문제(예: 고객 문의 처리)를 워크플로 방식과 에이전트 방식으로 각각 구현해 비용·안정성·지연 비교
- 이전 질문에서 다룬 **"도구 내부 LLM 호출 vs 별도 노드"** 를 직접 두 가지로 구현해 트레이스 차이 확인

---

## 4단계. 영속성·메모리·Human-in-the-loop

**목표:** 중단되어도 이어지고, 사람이 개입할 수 있고, 사용자를 기억하는 에이전트 만들기

**학습 항목**

1. **Checkpointer**: `InMemorySaver` → SQLite → Postgres, `thread_id` 개념
2. **Durable execution**: 서버가 재시작되어도 노드 단위로 저장된 상태에서 정확히 이어서 실행되는 구조, 재실행 시 부작용(side effect)이 중복되지 않도록 설계하는 법
3. **Interrupt와 Resume**: `interrupt()`, `Command(resume=...)`, 승인/수정/거부 패턴. 중단과 재개에는 체크포인터와 thread ID가 필요하다는 점 확인
4. **State 조회/수정**: `get_state`, `update_state`, 상태 히스토리
5. **Time travel**: 과거 체크포인트로 되돌아가 분기 실행
6. **단기 메모리**: 대화 히스토리 관리 (트리밍, 요약, 메시지 삭제)
7. **장기 메모리**: Store 인터페이스, 네임스페이스, 사용자별 프로필/선호 저장, 의미 기반 검색
8. **메모리 유형 구분**: semantic / episodic / procedural

**실습**

- 위험한 도구(결제, 메일 발송) 실행 전 사람 승인을 받는 에이전트
- 대화를 껐다 켜도 사용자 이름과 선호를 기억하는 에이전트
- 같은 `thread_id`와 다른 `thread_id`에서 동작 차이 확인

---

## 5단계. 스트리밍·서브그래프·멀티에이전트

**목표:** 사용자 경험을 개선하고 복잡한 시스템을 모듈화하기

**학습 항목**

1. **스트리밍 모드**: `values`, `updates`, `messages`(토큰 단위), `custom`, `debug` 및 조합 사용
2. **이벤트 스트리밍**: `astream_events`, 도구 진행 상황 표시
3. **서브그래프**: 그래프를 노드로 포함, 부모-자식 상태 매핑, 상태 스키마가 다를 때의 변환
4. **멀티에이전트 패턴**
    - Supervisor (중앙 조율자가 하위 에이전트에 위임)
    - Handoff / Swarm (에이전트끼리 제어권 이전)
    - Hierarchical (다단계 계층)
    - 에이전트를 도구로 감싸 호출하는 방식 (1번째 질문과 직접 연결되는 주제)
5. **멀티에이전트의 함정**: 컨텍스트 중복 전달, 책임 불명확, 비용 폭증 → "단일 에이전트 + 좋은 도구"로 충분한 경우 판단하기
6. **오류 처리**: 도구 에러를 모델에 돌려주기, 재시도 정책(`RetryPolicy`), 폴백 모델

**실습**

- 리서처 + 작성자 + 검토자 3개 서브에이전트를 가진 supervisor 시스템
- 토큰 단위 스트리밍과 도구 진행 상태를 함께 보여주는 간단한 CLI 또는 웹 UI

---

## 6단계. RAG·컨텍스트 엔지니어링·MCP

**목표:** 에이전트에 지식과 외부 연결을 붙이고, 컨텍스트를 의도적으로 관리하기

**학습 항목**

1. **RAG 기초**: 문서 로딩 → 분할 → 임베딩 → 벡터 스토어 → 검색
2. **Agentic RAG**: 검색 필요 여부 판단, 쿼리 재작성, 검색 결과 관련성 평가, 재검색 루프
3. **고급 검색**: 하이브리드 검색(BM25 + 벡터), 리랭킹, 메타데이터 필터
4. **컨텍스트 엔지니어링**: 무엇을 프롬프트에 넣고 뺄지, 도구 결과 요약/압축, 긴 컨텍스트 열화 문제
5. **MCP(Model Context Protocol)**: MCP 서버의 도구를 에이전트에 연결 (`langchain-mcp-adapters`)
6. **도구 설계 원칙**: 명확한 이름과 설명, 적은 수의 겹치지 않는 도구, 에러 메시지도 모델이 읽는다는 점 고려

**실습**

- 사내 문서(또는 공개 문서) 기반 Agentic RAG 에이전트
- 공개 MCP 서버 하나를 연결해 도구로 사용

---

## 7단계. 평가·관측성·테스트

**목표:** "잘 되는 것 같다"에서 "측정해서 안다"로 넘어가기

**학습 항목**

1. **LangSmith 트레이싱**: 실행 트리 읽기, 비용·지연·토큰 분석, 메타데이터와 태그
2. **데이터셋과 평가**: 골든 데이터셋 구축, 평가자(rule-based / LLM-as-judge), 오프라인 평가
3. **에이전트 평가 관점**: 최종 답변 품질뿐 아니라 **도구 호출 궤적(trajectory)** 도 평가
4. **회귀 테스트**: 프롬프트나 모델을 바꿀 때 성능 변화 추적
5. **단위 테스트**: 노드 함수와 라우팅 함수를 LLM 없이 테스트, 가짜(fake) 모델 사용
6. **LLM-as-judge의 한계**: 편향, 일관성, 보정 방법

**실습**

- 20~50개 케이스의 평가 데이터셋을 만들고 모델/프롬프트 변경 전후 비교
- 라우팅 노드에 대한 결정적(deterministic) 단위 테스트 작성

---

## 8단계. 프로덕션 배포·운영

**목표:** 데모를 서비스로 바꾸기

**학습 항목**

1. **로컬 개발 서버**: `langgraph.json`, `langgraph dev`, LangGraph Studio로 시각적 디버깅
2. **배포 옵션**: 자체 호스팅(FastAPI 등으로 감싸기) vs LangSmith 배포 — 비용·운영 부담 비교
3. **영속 저장소**: Postgres 체크포인터/스토어, 커넥션 풀, 마이그레이션
4. **동시성과 비동기**: async 그래프, 장시간 실행 작업, 백그라운드 실행
5. **안전장치(가드레일)**: 입력/출력 검증, PII 처리, 도구 권한 최소화, 프롬프트 인젝션 대응, 위험 작업 승인
6. **신뢰성**: 타임아웃, 재시도, 서킷 브레이커, `recursion_limit`, 토큰/비용 상한
7. **비용 최적화**: 작은 모델 라우팅, 프롬프트 캐싱, 컨텍스트 압축
8. **버전 관리**: 프롬프트·그래프 스키마 변경 시 기존 체크포인트와의 호환성
9. **보안**: API 키 관리, 사용자별 데이터 격리(thread/namespace 설계)

---

## 캡스톤 프로젝트 제안 (택 1)

1. **고객 지원 에이전트**: 분류 라우팅 + Agentic RAG + 위험 작업 사람 승인 + 사용자 장기 메모리
2. **리서치 어시스턴트**: orchestrator-worker로 병렬 조사 + 작성/검토 루프 + 출처 인용
3. **업무 자동화 에이전트**: MCP로 캘린더/문서/이슈 트래커 연결 + 승인 흐름 + 평가 데이터셋

공통 요구사항: Postgres 체크포인터, 스트리밍 UI, LangSmith 평가 세트, 비용/지연 대시보드

- **순서 고수**: 2단계(그래프 직접 구현)를 건너뛰고 바로 멀티에이전트로 가면 디버깅이 매우 어려워집니다.
- **버전 확인**: 튜토리얼 날짜를 보고, `create_react_agent`나 `langgraph.prebuilt`가 보이면 구버전 자료라는 신호로 보세요.
- **공식 문서 우선**: 1.0 때 문서가 전면 개편되었으므로 `docs.langchain.com`의 LangGraph / LangChain 섹션이 가장 정확합니다.
- **트레이스를 습관적으로 보기**: 처음부터 LangSmith를 켜두고 모든 실험의 실행 트리를 읽는 습관이 가장 큰 실력 차이를 만듭니다.
- **단순하게 시작**: 에이전트가 필요 없는 문제에 에이전트를 쓰지 않는 판단력이 3단계의 핵심입니다.

이 커리큘럼을 주차별 체크리스트가 있는 문서로 정리해드릴 수도 있고, 사용 목적(예: 사내 챗봇, 데이터 분석 에이전트)을 알려주시면 그에 맞게 단계 비중을 조정해드릴 수도 있어요.
