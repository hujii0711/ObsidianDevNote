LangGraph에서 **노드(node)**와 **에이전트(agent)**는 같은 층위의 개념이 아닙니다. 노드는 그래프를 구성하는 기본 단위이고, 에이전트는 그 노드와 엣지를 조합해 만든 **하나의 그래프(또는 그래프 안의 노드)**입니다.

## 계층 구조

```
그래프 (StateGraph)
 ├─ State (공유 데이터)
 ├─ 노드 (Node)  ← 함수 하나
 │    ├─ 일반 Python 함수
 │    ├─ LLM 호출 함수
 │    ├─ ToolNode (도구 실행)
 │    └─ 서브그래프 (= 다른 에이전트 전체)
 └─ 엣지 (Edge)  ← 노드 간 연결 (일반 / 조건부)
```

## 각 개념의 위치

| 개념       | 정체                          | 역할            |
| -------- | --------------------------- | ------------- |
| **노드**   | `State`를 받아 업데이트를 반환하는 함수   | 작업의 최소 단위     |
| **엣지**   | 노드 사이의 연결                   | 다음에 실행할 노드 결정 |
| **그래프**  | 노드 + 엣지 + State의 묶음         | 전체 워크플로       |
| **에이전트** | LLM이 도구를 호출하며 반복(루프) 하는 그래프 | 스스로 판단하는 워크플로 |

## 에이전트의 내부 구조

`create_agent`로 만든 에이전트를 펼쳐 보면 결국 노드 두 개와 조건부 엣지로 이뤄진 그래프입니다.

```
START → model 노드 ──(tool_calls 있음)──→ tools 노드 ─┐
            ↑                                          │
            └──────────────────────────────────────────┘
            │
            └─(tool_calls 없음)──→ END
```

- **model 노드**: LLM을 호출해 응답 또는 도구 호출을 생성
- **tools 노드**: 요청된 도구를 실행해 결과를 메시지로 추가
- **조건부 엣지**: 마지막 메시지에 `tool_calls`가 있는지로 분기

즉 에이전트는 "노드의 상위 개념"이 아니라 **노드들을 특정 패턴(ReAct 루프)으로 연결한 그래프**입니다.

## 계층이 중첩되는 경우: 서브그래프

컴파일된 에이전트(그래프)는 다른 그래프의 **노드로 추가**할 수 있습니다. 이때 계층이 생깁니다.

```python
# 하위: 리서치 에이전트 (자체가 그래프)
research_agent = create_agent(model, tools=[search_tool])

# 상위: 오케스트레이션 그래프
builder = StateGraph(State)
builder.add_node("research", research_agent)   # 에이전트를 노드로 사용
builder.add_node("write", write_node)
builder.add_edge(START, "research")
builder.add_edge("research", "write")
builder.add_edge("write", END)
```

이 경우 관계는 다음과 같습니다.

```
상위 그래프
 ├─ research 노드 = 에이전트(서브그래프)
 │    ├─ model 노드
 │    └─ tools 노드
 └─ write 노드 = 일반 함수
```

멀티 에이전트 시스템도 이 방식으로 만듭니다. 슈퍼바이저 그래프가 각 전문 에이전트를 노드로 두고 어디로 보낼지 결정합니다.

## 정리

- **노드**는 가장 작은 실행 단위(함수)입니다.
- **에이전트**는 노드와 엣지를 LLM 루프 형태로 구성한 **그래프**입니다.
- 그래프는 컴파일하면 **다른 그래프의 노드**가 될 수 있으므로, 에이전트는 상위 그래프 입장에서는 하나의 노드로 보입니다.
- 서브그래프와 상위 그래프의 State 스키마가 다르면, 노드 함수 안에서 입력/출력을 변환한 뒤 서브그래프를 `invoke`하는 방식으로 연결합니다.

`create_agent`의 내부 노드 이름(`model`, `tools` 등)은 LangChain/LangGraph 버전에 따라 다를 수 있으니, 실제 구조는 `print_graph_ascii(agent)`처럼 시각화해서 확인해 보시길 권합니다.

---

"에이전트 = LLM 루프 형태로 구성한 그래프"라는 말은 세 부분으로 나눠서 보면 이해하기 쉽습니다.

1. **그래프**: 노드(작업)와 엣지(연결)로 이루어진 구조
2. **LLM 루프**: 모델이 "생각 → 행동 → 관찰"을 반복하는 동작 방식
3. **구성한다**: 이 반복 동작을 노드와 엣지로 표현해서 만든다는 뜻

## 1. 먼저, 루프가 필요한 이유

LLM 한 번 호출로 끝나는 경우는 에이전트가 아닙니다.

```
질문 → LLM → 답변        (단순 호출, 에이전트 아님)
```

에이전트는 LLM이 **스스로 판단해서 도구를 쓰고, 그 결과를 보고 다시 판단**합니다.

예를 들어 "서울 날씨 알려줘"라고 물으면 이런 일이 벌어집니다.

```
1. LLM: "날씨를 모르니 weather 도구를 호출해야겠다"  → 도구 호출 요청
2. 도구: weather("서울") 실행 → "맑음, 18도"
3. LLM: 도구 결과를 보고 "서울은 맑고 18도입니다"  → 최종 답변
```

여기서 중요한 점은 **LLM이 몇 번 도구를 호출할지 미리 정해져 있지 않다**는 것입니다. 질문이 복잡하면 도구를 3번, 5번 호출할 수도 있습니다. 그래서 "정해진 횟수만큼 순서대로 실행"이 아니라 **"끝낼 때까지 반복"** 하는 구조가 필요하고, 이것이 루프입니다.

## 2. 루프를 그래프로 표현하기

이 반복 동작을 노드와 엣지로 옮기면 다음과 같습니다.

```
        ┌────────────────────────────┐
        ↓                            │
START → model 노드 ──(도구 호출 있음)──→ tools 노드
            │
            └──(도구 호출 없음)──→ END
```

|구성 요소|종류|하는 일|
|---|---|---|
|`model`|노드|LLM을 호출. 결과는 "최종 답변" 또는 "도구를 써달라는 요청"|
|`tools`|노드|LLM이 요청한 도구를 실제로 실행하고 결과를 메시지에 추가|
|`model → tools / END`|**조건부 엣지**|마지막 메시지에 `tool_calls`가 있으면 tools로, 없으면 END로|
|`tools → model`|일반 엣지|도구 실행이 끝나면 항상 model로 돌아감|

**루프가 만들어지는 지점은 `tools → model` 엣지입니다.** 이 엣지가 실행 흐름을 뒤로 되돌려서 같은 노드를 다시 실행하게 만듭니다. 그리고 **루프가 끝나는 지점은 조건부 엣지**입니다. LLM이 "더 이상 도구가 필요 없다"고 판단해서 도구 호출 없이 답변하면 END로 빠집니다.

## 3. State는 어떻게 쓰이나

루프를 돌 때마다 대화 내용이 `messages`에 쌓이고, 이것이 다음 LLM 호출의 입력이 됩니다. 이때 앞서 배운 `add_messages` reducer가 쓰입니다.

```python
class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
```

"서울 날씨 알려줘"를 실행하면 `messages`가 이렇게 변합니다.

|단계|실행된 노드|`messages`에 추가되는 것|
|---|---|---|
|시작|-|`HumanMessage("서울 날씨 알려줘")`|
|1|`model`|`AIMessage(tool_calls=[weather("서울")])`|
|2|`tools`|`ToolMessage("맑음, 18도")`|
|3|`model`|`AIMessage("서울은 맑고 18도입니다")` ← 도구 호출 없음 → END|

덮어쓰기가 아니라 **누적**되기 때문에, 두 번째로 `model`이 호출될 때는 "내 질문, 내가 한 도구 호출 요청, 도구 결과"를 모두 볼 수 있습니다. 이 누적된 기록이 LLM이 다음 판단을 내리는 근거가 됩니다.

## 4. 직접 구현해 보기

`create_agent`가 해주는 일을 직접 그래프로 만들면 다음과 같습니다.

```python
from langchain_core.tools import tool
from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.prebuilt import ToolNode, tools_condition


@tool
def weather(city: str) -> str:
    """도시의 날씨를 알려준다."""
    return f"{city}: 맑음, 18도"


llm = init_chat_model("openai:gpt-4o-mini").bind_tools([weather])


# 노드 1: LLM 호출
def model_node(state: MessagesState):
    return {"messages": [llm.invoke(state["messages"])]}


builder = StateGraph(MessagesState)
builder.add_node("model", model_node)
builder.add_node("tools", ToolNode([weather]))   # 노드 2: 도구 실행

builder.add_edge(START, "model")
builder.add_conditional_edges("model", tools_condition)  # 조건부 엣지: tools 또는 END
builder.add_edge("tools", "model")                       # 루프를 만드는 엣지

agent = builder.compile()

result = agent.invoke({"messages": [("user", "서울 날씨 알려줘")]})
```

여기서 `tools_condition`은 마지막 메시지에 `tool_calls`가 있으면 `"tools"`를, 없으면 `END`를 반환하는 미리 만들어진 조건 함수입니다.

## 5. 앞에서 본 "고정 순서 그래프"와의 차이

|구분|고정 순서 그래프 (앞의 `node_a → node_b`)|에이전트 그래프|
|---|---|---|
|실행 경로|항상 같음|**LLM의 판단에 따라 달라짐**|
|노드 실행 횟수|각 1번|`model`, `tools`가 **여러 번** 실행될 수 있음|
|종료 시점|마지막 노드 도달|LLM이 도구 호출을 멈출 때|
|엣지|일반 엣지만|**조건부 엣지 + 되돌아가는 엣지**|

즉 "에이전트"라고 부르는 이유는 그래프 구조 자체보다, **다음에 무엇을 할지(도구를 쓸지, 끝낼지)를 LLM이 결정한다**는 점에 있습니다. 그래프는 그 결정이 실행될 수 있도록 길을 깔아 놓은 것이고, 루프는 그 길이 뒤로 이어져 있다는 의미입니다.

## 한 줄 정리

> 에이전트 = **"LLM이 판단하는 노드"**와 **"도구를 실행하는 노드"**를 **조건부 엣지**와 **되돌아가는 엣지**로 이어서, LLM이 "이제 충분하다"고 할 때까지 반복하도록 만든 그래프

참고로 무한 루프를 막기 위해 LangGraph에는 `recursion_limit`(기본값 25) 설정이 있어서, 노드 실행 횟수가 이 한도를 넘으면 오류를 냅니다. 에이전트가 도구를 너무 많이 호출하는 상황을 방지하는 안전장치입니다.
