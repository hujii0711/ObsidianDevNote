
`shorts_graph`의 장기 메모리 구조를 코드 기준으로 정리했습니다. 장기 메모리는 LangGraph `Store` 한 곳(`memory.sqlite`)에 두 종류를 저장합니다. 하나는 사용자 선호(목소리·속도·맺음말·금칙어)이고, 다른 하나는 이미 영상으로 만든 기사 URL입니다. 그래프의 첫 노드 `load_memory`가 읽고, 마지막 노드 `save_memory`가 씁니다.

### 1. 저장 구조 — [memory/store.py](shorts_graph/memory/store.py)

| 구역(namespace)                | 키              | 값                                       | 용도               |
| ---------------------------- | -------------- | --------------------------------------- | ---------------- |
| `("prefs", user_id)`         | `"default"` 하나 | `{voice, rate, outro, banned_words}` 전체 | 사용자 선호           |
| `("used_articles", user_id)` | 기사 URL         | `{title, query, thread_id, created_at}` | 같은 기사로 다시 만들지 않기 |


함수 네 개가 Store를 다룹니다. 모두 `BaseStore`를 인자로 받으므로 SQLite든 메모리든 같은 코드로 돕니다.
- `load_prefs` ([store.py:56](shorts_graph/memory/store.py#L56)): `DEFAULT_PREFS`를 깊은 복사한 뒤 저장된 값을 덮어씁니다. 저장된 것이 없으면 기본값이 나옵니다(맺음말 `outro`는 빈 문자열이라 붙지 않음).
- `save_prefs` ([store.py:68](shorts_graph/memory/store.py#L68)): 바꿀 항목만 담은 patch를 `validate_prefs_patch`로 먼저 검사합니다. 모르는 키나 voice·rate 형식 오류는 `ValueError`로 막습니다. 통과하면 기존 값과 합친 **전체 dict**를 `put`합니다.
- `used_urls` ([store.py:79](shorts_graph/memory/store.py#L79)): `store.search(namespace, limit=10_000)`로 키(URL) 목록을 받습니다. 벡터 인덱스는 없고, 구역 안의 항목을 나열하는 용도로만 씁니다.
- `remember_article` ([store.py:84](shorts_graph/memory/store.py#L84)): URL을 키로 `put`합니다.

### 2. LangGraph 연동 방식

세 군데에서 이어집니다.

**① 컴파일할 때 Store를 주입** — [graph.py:65](shorts_graph/graph.py#L65), [graph.py:135](shorts_graph/graph.py#L135)
```python
graph = StateGraph(ShortsState, context_schema=Ctx)
...
graph.compile(checkpointer=checkpointer, store=store)
```

**② 실행할 때 `context`로 사용자 ID 전달** — [cli/main.py:174](shorts_graph/cli/main.py#L174)
```python
graph.stream(inp, cfg, stream_mode=["updates","custom"], context=Ctx())
```

**③ 노드는 `Runtime`으로 둘 다 받음** — [memory/nodes.py:17-24](shorts_graph/memory/nodes.py#L17-L24)
```python
def load_memory(state, runtime: Runtime[Ctx]):
    uid = runtime.context.user_id        # context_schema → runtime.context
    prefs = load_prefs(runtime.store, uid)  # compile(store=) → runtime.store
```

노드 시그니처에 `runtime: Runtime[Ctx]`를 적으면 LangGraph가 자동으로 넣어 줍니다. 그래서 노드 코드는 Store 구현(SQLite·InMemory)을 모릅니다.

**체크포인터와 Store의 차이** ([cli/main.py:139-158](shorts_graph/cli/main.py#L139-L158)):

| | Checkpointer (`SqliteSaver`) | Store (`SqliteStore`) |
|---|---|---|
| 파일 | `outputs/checkpoints.sqlite` | `outputs/memory.sqlite` |
| 범위 | thread_id 하나(실행 하나) | 모든 실행이 함께 씀 |
| 담는 것 | `ShortsState` 전체, interrupt 위치 | 선호, 사용한 기사 |
| 역할 | interrupt 후 `resume`, 실패 후 이어 가기 | 다음 실행에 남길 기억 |

### 3. 실행 흐름

```
start ─▶ load_memory ──────────▶ guard_input ─▶ search ─▶ ... ─▶ render ─▶ save_memory ─▶ END
          │ Store 읽기             │ prefs.        │ used_urls              │ Store 쓰기
          │ state.prefs            │ banned_words  │ 기사 제외              │ remember_article(url)
          │ state.used_urls        │ 로 검색어 검사                         │ status=done
```

`load_memory`는 Store의 값을 **상태(state)로 복사**합니다. 그 뒤 노드들은 Store를 다시 읽지 않고 `state["prefs"]`만 봅니다.

| 노드 | 쓰는 값 | 위치 |
|---|---|---|
| `guard_input` | `banned_words` → 검색어 금칙어 검사 | [research/nodes.py:23](shorts_graph/research/nodes.py#L23) |
| `search` | `used_urls` → 이미 쓴 기사 빼기. 모두 빠지면 `failed` | [research/nodes.py:93-98](shorts_graph/research/nodes.py#L93-L98) |
| `write_script` | `outro` → 대본 끝에 붙이기 | [script/nodes.py:61](shorts_graph/script/nodes.py#L61) |
| `guard_script` | `banned_words` → 대본 금칙어 검사 | [script/nodes.py:93](shorts_graph/script/nodes.py#L93) |
| `approve_script`(edit) | `outro` → 사람이 고친 대본에서 떼었다 다시 붙이기 | [review/nodes.py:131](shorts_graph/review/nodes.py#L131) |
| `scene_audio` | `voice`, `rate` → TTS. `DEFAULT_PREFS`와 다시 합쳐 빠진 키를 막음 | [media/nodes.py:81](shorts_graph/media/nodes.py#L81) |

`save_memory`는 `render`가 성공해야만 실행됩니다. 그래서 취소·거부·실패한 실행의 기사는 기록되지 않고, 다음 검색에서 다시 후보로 나옵니다.

### 4. 그래프 밖에서 선호 읽기·쓰기

```
웹 PrefsPanel ─▶ GET/PUT /api/prefs ─▶ uv run -m shorts_graph prefs [--set '{...}']
                 (shorts_web/app/api/prefs/route.ts)      └▶ _prefs(): load_prefs / save_prefs
                                                              └▶ stdout: {"type":"prefs","prefs":{...}}
```

- [cli/main.py:233](shorts_graph/cli/main.py#L233)의 `_prefs`는 그래프를 실행하지 않습니다. `session.store`를 직접 부릅니다.
- 검사에 실패하면 `ValueError`가 `GraphError`로 바뀝니다. 그러면 error 이벤트가 나가고, 웹은 400을 돌려줍니다.
- `prefs` 명령은 `run.lock`을 잡지 않습니다. 잠금은 `start`와 `resume`에만 있습니다([cli/main.py:254](shorts_graph/cli/main.py#L254)).

### 5. 테스트

- `InMemoryStore`로 바꿔 넣습니다. [tests/fixtures.py:84](shorts_graph/tests/fixtures.py#L84)의 `fake_runtime()`이 `Runtime(context=Ctx(...), store=InMemoryStore())`를 만들어 노드를 단독으로 시험합니다.
- [tests/memory/test_store.py](shorts_graph/tests/memory/test_store.py)는 기본값, 병합, 잘못된 patch 거부, 사용자별 분리를 검사합니다.
- [tests/test_graph.py:53-70](shorts_graph/tests/test_graph.py#L53-L70)은 그래프 전체를 돌립니다. 첫 실행이 기사를 기록하는지, 같은 Store로 다시 돌릴 때 그 기사가 빠지는지 확인합니다.

### 6. 알아 둘 점과 한계

1. **실행 중에 선호를 바꿔도 그 실행에는 적용되지 않습니다.** `prefs`는 `load_memory`에서 상태로 복사되고 체크포인트에 저장됩니다. `resume`은 `load_memory`를 다시 돌리지 않습니다. 그래서 대본 승인을 기다리는 동안 웹에서 목소리를 바꿔도, 그 실행은 시작할 때의 목소리를 씁니다. 바뀐 값은 다음 `start`부터 적용됩니다.
2. **사용자 ID는 사실상 `"local"` 하나입니다.** `_stream`과 `_prefs` 모두 `Ctx()`를 기본값으로만 만들고, CLI에 user_id 옵션이 없습니다. namespace는 사용자별로 나뉘어 있어서 확장할 준비는 되어 있습니다.
3. **사용한 기사 기록은 계속 쌓이기만 합니다.** 지우는 명령이나 TTL이 없고, `used_urls`는 최대 10,000건까지만 읽습니다. 다시 만들고 싶은 기사가 있어도 지금은 `memory.sqlite`를 직접 고쳐야 합니다.
4. **선호는 키 하나에 통째로 덮어씁니다.** `save_prefs`는 읽고, 합치고, 전체를 씁니다. 동시에 두 번 쓰면 나중 것이 이깁니다. 사용자가 한 명인 로컬 도구라 지금은 문제가 되지 않습니다.
5. **Store를 의미 검색에는 쓰지 않습니다.** `SqliteStore`를 `index` 설정 없이 열기 때문에 `search`는 나열만 합니다. "비슷한 주제의 기사를 이미 다뤘는지"를 판단하려면 임베딩 인덱스를 따로 붙여야 합니다.
6. **폴더 간 import 규칙**: 다른 기능 폴더 중 `memory`를 직접 import하는 곳은 `media → memory`(`DEFAULT_PREFS`) 하나뿐입니다. 나머지는 `state["prefs"]`만 읽습니다. 이 방향은 [tests/test_isolation.py](shorts_graph/tests/test_isolation.py)가 검사합니다.

이 중 하나를 고치고 싶으면(예: `resume` 때 선호 다시 읽기, 사용한 기사 지우기 명령) 말씀해 주세요. 설계부터 잡겠습니다.

## checkpointer thread_id


아니요. Store의 접근 키는 `(namespace, key)`이고, 그 안에 thread_id는 들어가지 않습니다. thread_id는 체크포인터의 키입니다.

**Store의 키 구성** ([memory/store.py](shorts_graph/memory/store.py))

| 데이터 | namespace | key |
|---|---|---|
| 선호 | `("prefs", user_id)` | `"default"` |
| 사용한 기사 | `("used_articles", user_id)` | 기사 URL |

**실제 `memory.sqlite`의 테이블 구조**
```sql
CREATE TABLE store (
    prefix text NOT NULL,   -- namespace를 '.'으로 이은 값
    key    text NOT NULL,
    value  text NOT NULL,   -- JSON
    ...
    PRIMARY KEY (prefix, key)
);
```
실제 행은 이렇게 들어 있습니다.
```
used_articles.local | https://www.bbc.com/korean/articles/cm2l4y591rlpo | {"title": ..., "thread_id": ..., ...}
```
namespace `("used_articles", "local")`는 `prefix = "used_articles.local"`로 저장되고, URL이 `key`가 됩니다.

**thread_id가 쓰이는 곳**
- 체크포인터의 키입니다. `{"configurable": {"thread_id": ...}}`로 넘기고([cli/main.py:161](shorts_graph/cli/main.py#L161)), `checkpoints.sqlite`에서 실행 하나의 상태를 찾는 데 씁니다.
- Store에서는 **값 안의 필드**로만 남습니다. `save_memory`가 기사 정보에 `"thread_id"`를 함께 적어서([memory/nodes.py:47](shorts_graph/memory/nodes.py#L47)), 이 기사가 어느 실행에서 영상이 됐는지 추적할 수 있게 합니다. 이 값으로 조회하지는 않습니다.

이렇게 나눈 이유는 범위가 다르기 때문입니다. 체크포인트는 실행 하나에 묶이므로 thread_id로 찾습니다. Store는 모든 실행이 함께 쓰는 기억이라 사용자(user_id) 단위로 찾습니다. 그래서 새 thread로 `start`해도 이전 실행에서 저장한 선호와 사용한 기사가 그대로 보입니다.

## checkpointer

체크포인터는 `outputs/checkpoints.sqlite`에 테이블 두 개로 저장됩니다. `checkpoints`는 단계마다 찍는 상태 스냅숏이고, `writes`는 각 노드가 돌려준 값과 interrupt·resume 기록입니다. 아래 예시는 실제 실행 하나(`20261115-004946`)를 열어 확인한 내용입니다.

### 1. 접근 키

```
(thread_id, checkpoint_ns, checkpoint_id)
```
- **thread_id**: 실행 하나. CLI가 `{"configurable": {"thread_id": ...}}`로 넘깁니다([cli/main.py:161](shorts_graph/cli/main.py#L161)).
- **checkpoint_ns**: 서브그래프용 구역입니다. 이 프로젝트에는 서브그래프가 없어서 항상 `''`입니다.
- **checkpoint_id**: 시간순으로 정렬되는 UUID입니다(`1f1e0430-...`). 행마다 `parent_checkpoint_id`가 있어 직전 체크포인트와 연결 리스트를 이룹니다.

### 2. `checkpoints` 테이블: 단계마다 한 행

```sql
thread_id, checkpoint_ns, checkpoint_id, parent_checkpoint_id,
type,        -- 'msgpack' (직렬화 형식)
checkpoint,  -- BLOB: 아래 구조
metadata     -- JSON: {"source": "input"|"loop", "step": N, "parents": {}}
```

`checkpoint` BLOB을 풀면 다음과 같습니다.

| 키 | 내용 |
|---|---|
| `channel_values` | **`ShortsState` 전체** (`query`, `prefs`, `candidates`, `article`, `script`, `scenes`, `status` …) 그리고 `branch:to:<노드>` 같은 내부 채널 |
| `channel_versions` | 필드(채널)마다 마지막으로 바뀐 버전 |
| `versions_seen` | 노드마다 어떤 버전까지 읽었는지. 다음에 실행할 노드를 정하는 데 씁니다 |
| `updated_channels`, `v`, `ts`, `id` | 이번 단계에서 바뀐 채널, 형식 버전(4), 시각, id |

`channel_values`에는 매번 상태 전체가 들어갑니다. 그래서 이 실행의 BLOB은 첫 행 416B에서 마지막 행 31KB까지 커졌습니다. 기사 본문(`candidates[].source_text`)과 장면 목록이 쌓이기 때문입니다.

### 3. `writes` 테이블: 노드가 돌려준 값

```sql
thread_id, checkpoint_ns, checkpoint_id,  -- 이 노드가 시작한 기준 체크포인트
task_id, task_path, idx,
channel,   -- 어느 상태 필드에 쓰는지
type, value
```

노드가 `{"prefs": ..., "used_urls": ...}`를 돌려주면 **필드마다 한 행**이 생깁니다. 특별한 채널도 섞여 있습니다.

| channel | 뜻 |
|---|---|
| `query`, `prefs`, `article` … | 일반 상태 필드 갱신 |
| `branch:to:guard_input` 등 | 다음에 실행할 노드 표시(엣지나 `Command(goto=)`) |
| `__interrupt__` (idx −3) | `interrupt()`에 넘긴 질문 내용. `snap.interrupts`가 여기서 나옵니다 |
| `__resume__` (idx −4) | `Command(resume=답)`으로 들어온 사용자 답 |

### 4. 실제 실행 하나의 흐름

| step | 실행된 것 | writes에 남은 channel |
|---|---|---|
| −1 (`input`) | 시작 상태 | `query`, `auto`, `output_dir`, `status`, `script_attempts`, `feedback`, `branch:to:load_memory` |
| 0 | `load_memory` | `prefs`, `used_urls` ← **Store에서 읽은 값이 여기서 상태로 복사됨** |
| 1 | `guard_input` | `query` |
| 2 | `search` | `candidates` (12KB) |
| 3 | `pick_article` | `__interrupt__` → (resume 후) `__resume__`, `article` |
| 4 | `write_script` | `script_body`, `script`, `script_source` |
| 5 | `guard_script` | `guard` |
| 6 | `approve_script` | `__interrupt__`, `__resume__`(edit), `script_source: human` → `guard_script`로 |
| … | 다시 검사하고 승인 | |
| 14 | `save_memory` | `status: done`, `message` |

이 실행은 체크포인트 16행으로 끝났습니다. 다른 실행들도 5~18행입니다.

### 5. 코드가 읽는 방식

CLI는 테이블을 직접 읽지 않습니다. `graph.get_state(cfg)`가 돌려주는 `StateSnapshot`만 씁니다.

| 필드 | 출처 | 쓰는 곳 |
|---|---|---|
| `created_at` | 최신 체크포인트가 있는지 | `start`: 이미 있는 thread_id면 거부. `resume`: 없는 thread_id면 거부 ([cli/main.py:187-206](shorts_graph/cli/main.py#L187-L206)) |
| `interrupts` | `__interrupt__` writes | `resume`: 질문 종류(`kind`)를 보고 `--input` 검사 ([cli/main.py:207-215](shorts_graph/cli/main.py#L207-L215)) |
| `next` | `versions_seen`과 `branch:to:*`로 계산 | 질문은 없는데 남은 노드가 있으면, 실패한 실행으로 보고 `--input` 없이 이어 감 |
| `values` | `channel_values` | `status`, `final_event` 이벤트 ([cli/events.py](shorts_graph/cli/events.py)) |

### 6. 이어 가기가 동작하는 방식

- **interrupt**: 노드가 `interrupt()`를 부르면 새 체크포인트 없이 `__interrupt__` write만 남기고 멈춥니다. `resume`하면 `__resume__`이 기록되고, **그 노드가 처음부터 다시 실행됩니다.** 이번에는 `interrupt()`가 답을 돌려줍니다. 그래서 `interrupt()`보다 앞에 있는 코드는 두 번 실행됩니다.
- **실패 후 재개**: 노드 하나가 예외로 죽어도, 앞에서 끝난 노드들의 결과는 체크포인트에 남아 있습니다. `resume`하면 실패한 노드부터 다시 돕니다. 노드 *안에서* 장면별로 건너뛰는 판단은 체크포인터가 아니라 파일로 합니다. 음성(`audio_path`·words.json)이나 이미지 jpg가 이미 있으면 재사용합니다([media/nodes.py:1](shorts_graph/media/nodes.py#L1), [media/nodes.py:149](shorts_graph/media/nodes.py#L149)).

### 7. 알아 둘 점

1. **선호가 상태 안에 고정됩니다.** 디코드해 보니 `channel_values.prefs`에 `rate: '+10%'`와 outro가 그대로 들어 있습니다. `resume`은 이 값을 읽으므로, 실행 도중 Store의 선호를 바꿔도 그 실행에는 반영되지 않습니다.
2. **지우는 기능이 없습니다.** 끝난 실행의 체크포인트도 계속 남습니다. 지금은 수십 KB 수준이지만, 실행이 쌓이면 파일이 커집니다.

### `_Session`

`_Session`은 CLI 명령 하나가 실행되는 동안 **저장소 두 개를 열어 두고, 그 저장소가 연결된 그래프를 만들어 주는 작은 묶음**입니다([cli/main.py:139-158](shorts_graph/cli/main.py#L139-L158)).

### 하는 일 세 가지

**1. 저장소 두 개를 엽니다** (`__init__`)
```python
self.checkpointer = stack.enter_context(SqliteSaver.from_conn_string(".../checkpoints.sqlite"))
self.store        = stack.enter_context(SqliteStore.from_conn_string(".../memory.sqlite"))
self.store.setup()
```
- `from_conn_string`은 컨텍스트 매니저라서 `with` 블록 안에서만 연결이 살아 있습니다. `_Session`은 직접 닫지 않고 바깥에서 받은 `ExitStack`에 등록합니다. 그래서 `_run`의 `with ExitStack()` 블록이 끝나면 두 DB 연결이 자동으로 닫힙니다.
- `store.setup()`은 `store` 테이블과 인덱스를 만들거나 마이그레이션합니다. 체크포인터는 처음 쓸 때 스스로 준비하므로 따로 부르지 않습니다.

**2. 같은 저장소에 연결된 그래프를 만듭니다** (`graph(deps)`)
```python
return build_graph(deps, checkpointer=self.checkpointer, store=self.store)
```
저장소는 세션에 고정되어 있고, deps만 호출할 때 고릅니다. 이 차이를 이용하는 곳이 `_start`와 `_resume`입니다.

```python
snap = session.graph(offline_deps()).get_state(cfg)   # ① 외부 호출 없이 상태만 확인
...검사 통과...
_stream(session.graph(deps_factory()), inp, ...)      # ② 그다음에 실제 deps로 실행
```
`get_state`는 체크포인터만 읽으면 되므로, 외부 호출을 막아 둔 `offline_deps()`로 충분합니다. 무거운 `default_deps()`(.env 읽기, tavily·LLM import)는 thread_id 중복 검사나 interrupt 입력 검사를 **통과한 다음에만** 부릅니다. 잘못된 입력이면 LLM을 준비하기 전에 바로 오류를 냅니다. `status`는 `offline_deps()`만 쓰고, `prefs`는 그래프 없이 `session.store`를 직접 씁니다.

**3. 수명을 명령 하나로 한정합니다**
CLI 프로세스 하나가 명령 하나를 처리하고, `_Session`도 그동안만 있습니다. 웹이 CLI를 매번 새로 띄우므로 연결이 오래 남지 않습니다.

### `_run`에서의 순서 — [cli/main.py:253-263](shorts_graph/cli/main.py#L253-L263)

```python
with ExitStack() as stack:
    if args.command in ("start", "resume"):
        stack.enter_context(run_lock(out_root))   # 1. 잠금
    session = _Session(stack, out_root)           # 2. DB 열기
    ...
# 닫을 때는 역순: DB 닫기 → 잠금 해제
```
- 잠금을 먼저 잡은 뒤에 DB를 엽니다. 다른 실행이 이미 돌고 있으면 DB를 건드리지 않고 종료 코드 2로 끝납니다.
- `ExitStack`은 연 순서의 역순으로 닫습니다. 그래서 DB 연결이 닫힌 다음에 잠금이 풀리고, 다음 실행이 들어왔을 때 앞 실행의 연결이 남아 있는 일이 없습니다.
- `graph` 명령은 이 블록에 들어오지 않으므로 `_Session`을 만들지 않습니다. 그래프 그림에는 저장소가 필요 없습니다.

### 명령별로 쓰는 부분

| 명령 | 잠금 | `checkpointer` | `store` | `graph(...)` |
|---|---|---|---|---|
| `start` | ✓ | 중복 확인, 실행 기록 | 그래프 노드가 사용 | offline → 실제 deps |
| `resume` | ✓ | 상태·interrupt 확인, 실행 기록 | 그래프 노드가 사용 | offline → 실제 deps |
| `status` | — | 상태 읽기 | (연결만 됨) | offline만 |
| `prefs` | — | (열리기만 함) | `load_prefs`/`save_prefs` 직접 호출 | 안 씀 |
| `graph` | — | — | — | 세션 없음 |

### 이렇게 나눈 이유

- **저장소 열고 닫기를 한곳에 모읍니다.** 저장소가 필요한 명령 네 개(`start`·`resume`·`status`·`prefs`)가 같은 방식으로 열고 닫으므로, 파일 경로와 `setup()`을 한 번만 적으면 됩니다.
- **저장소와 deps를 따로 정할 수 있습니다.** 같은 저장소 위에서 offline과 실제 deps를 오갈 수 있습니다.
- **테스트하기 쉽습니다.** `main(out_root=tmp_path, deps_factory=가짜)`로 부르면 세션이 임시 폴더에 SQLite를 열고 가짜 deps로 그래프를 만듭니다. CLI 테스트도 실제 파일 저장소 경로를 그대로 지나갑니다.

`prefs`·`status`는 체크포인터나 Store를 쓰지 않는데도 둘 다 엽니다. 파일 두 개를 여는 비용은 작아서 지금은 문제가 되지 않습니다. 굳이 고친다면 명령에 따라 필요한 것만 여는 방법이 있습니다.

### C. 예: `start` 한 번에 일어나는 저장·조회 순서

```
_Session 생성     → store.setup()                         CREATE TABLE IF NOT EXISTS ...
get_state(offline) → checkpointer.get_tuple                SELECT ... LIMIT 1  (없음 → 새 thread)
graph.stream 시작  → get_tuple, put(step -1)               SELECT / INSERT checkpoints
 load_memory       → store.get, store.search               SELECT FROM store ×2
                   → put_writes(prefs, used_urls) → put    INSERT writes / checkpoints
 ...노드마다 같은 방식으로 put_writes → put...
 pick_article      → put_writes(__interrupt__)             INSERT OR REPLACE writes → 멈춤
final_event       → get_state → get_tuple                  SELECT
```
`resume` 다음 단계들(…→ `save_memory`)에서 `store.put`이 실행되면, `INSERT OR REPLACE INTO store`로 사용한 기사가 기록됩니다.

### D. 코드에서 알 수 있는 점

1. **`used_urls`는 최신순으로 나옵니다.** `search`가 `ORDER BY updated_at DESC`이기 때문입니다. 기록이 10,000건을 넘으면 오래된 URL부터 빠지고, 그 기사는 다시 후보로 나올 수 있습니다.
2. **namespace는 `.`으로 이어 저장됩니다.** 그래서 user_id에 `.`이 들어가면 읽을 때 구역이 잘못 나뉠 수 있습니다. 지금은 user_id가 `"local"`뿐이라 문제가 되지 않습니다.
3. **값의 직렬화 형식이 다릅니다.** Store는 JSON(orjson)이라 `sqlite3`로 바로 읽을 수 있습니다. 체크포인터는 msgpack BLOB이라 `serde.loads_typed`로 풀어야 합니다.
