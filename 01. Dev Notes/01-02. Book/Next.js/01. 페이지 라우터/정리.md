### ▪︎ 서문
Next.js는 Vercel이라는 미국의 스타트업이 만든 웹 개발용 메타 프레임워크이다.
메타 프레임워크란 다른 라이브러리나 프레임워크를 확장해 주는 프레임워크이다.
Next.js는 리액트를 포함하는 메타 프레임워크로써 리액트의 훌륭한 UI 개발 기능에 더해 페이지 라우팅, 서버 사이드 렌더링 등과 같은 기능을 추가로 제공한다. 따라서 Next.js는 리액트의 확장판이라고 말하기도 한다.
라이브러리로서 리액트는 UI를 렌더링하는 기능 외에 추가 기능을 제공하지 않는다.
Next.js를 이용하면 별도의 라이브러리를 찾을 필요 없이 기본 기능만으로도 수준급의 웹 서비스를 구축할 수 있다. 한마디로 리액트가 자동차 엔진이라면 Next.js는 그 엔진을 탑재한 자동차이다.
Next.js는 리액트의 확장판이므로 페이지 UI를 컴포넌트 단위로 구현하고 State와 Props로 이벤트를 구현하는 등 리액트의 기존 문법을 그대로 사용한다. 리액트 사용자는 Next.js에서 제공하는 기능과 개념만 추가로 살펴보면 되므로 빠르게 익힐 수 있다.

### ▪︎ 서버 사이드 렌더링 = 사전 렌더링
사전 렌더링이란 웹 서버에서 미리 자바스크립트 코드를 실행해 개발자가 만든 컴포넌트를 HTML 페이지로 렌더링 하는 것을 말한다.
1) Next.js 웹 서버에 브라우저의 접속 요청이 들어온다.
2) 웹서버는 자바스크립트 코드를 실행해 현재 브라우저가 요청한 페이지를 HTML로 만든다.
3) 만든 HTML 페이지를 브라우저에 보내면서 화면이 렌더링된다.(FCP)
4) 브라우저는 Next.js 서버에서 자바스크립트 번들 파일을 받는다.
5) 브라우저는 자바스크립트 번들 파일을 실행해 이미 화면에 렌더링한 HTML과 자바스크립트를 연결한다. 이 과정이 마치 메말라 있던 HTML에 자바스크립트라는 물을 뿌리는 일과 비슷하다하여 하이드레이션(Hydration)과정, 우리말로는 수화 과정이라고 한다.
6) 하이드레이션이 끝나면 자바스크립트로 구현한 모든 상호 작용 기능이 동작하면서 초기 접속 과정은 마무리된다. 이 시점을 상호 작용이 준비되는 시점, 즉 TTI(Time To Interactive)라고 한다.
✅ 브라우저 요청에 index.html이라는 빈 파일로 응답하던 리액트 웹 서버와는 달리, Next.js 웹 서버는 완성된 HTML로 응답한다. 글 결과 콘텐츠를 화면에 최초로 렌더링하는 시간인 FCP가 빨라지면서 서비스에 대한 사용자 만족도가 높아진다.

### ▪︎ 동적 경로가 있는 페이지 라우팅 설정
`/book/[id].tsx` 또는 `/book/[id]/index.tsx`
id값이 무엇이든 `/book/[id]/index.tsx`의 페이지 컴포넌트를 렌더링한다.(/book/1)

`/book/[...id]/index.tsx` (/book/1/1, book/1/1/1, /book/1/1/1/1)
대괄호에 ...을 사용해 여러 개의 동적 경로를 처리하는 방식을 캐치올 세그먼트라고 한다.

`/book/[[...id]]/index.tsx` (/book, book/1/1/1, /book/1/1/1/1)
URL 파라미터가 없는 경로도 모두 포함하도록 설정할 수 있다. 이 방식을 옵셔널 캐치올 세그먼트라고 한다.

### ▪︎ 네비게이팅(Link 컴포넌트)
페이지를 이동할 때 CSR 방식으로 빠르게 페이지를 전환시킨다. 페이지를 전체 다시 로드하지 않아도 경로 전환이 가능하여 브라우저가 깜빡하지 않는다.
(useRouter().push(/book/1))


### ▪︎ 프리페칭(prefetching)
페이지 전환을 더 빠르게 만듬. 사용자가 페이지를 이동하기 전에 미리 필요한 데이터를 가져오는 기능(자바스크립트 번들)이다.
좀 더 구체적으로 표현하면 프리페칭은 사용자가 링크나 버튼을 클릭해 페이지를 이동하기 전에 현재 페이지에서 이동 가능한 다른 페이지의 데이터를 미리 불러오는 기능이다.
미리 데이터를 프리페칭할 수 있는 페이지는 Link 컴포넌트로 링크가 설정된 페이지들이다.
프로덕션 모드에서만 활성화된다. (useRouter().prefetch(/book/1))

### ▪︎ css import
Next.js는 글로벌 css파일은 오직 `_app.tsx`에서만 import하도록 제한한다.
글로벌 css 제한으로 인해 Next.js의 css 파일은 독립적인 스타일 블록처럼 하나의 컴포넌트에만 적용할 수 있다. `.module.css`로 변경해 파일을 모듈 형식으로 불러오면 된다. 이렇게 하면 css 클래스의 이름은 고유한 이름으로 자동 변환되어 클래스 사이의 이름 충돌을 방지할 수 있다.

### ▪︎ 사전 렌더링 3가지 방식(리액트 컴포넌트로 작성된 자바스크립트 코드를 HTML로 변환하는 과정)
① 서버 사이드 렌더링(SSR: Server Side Rendering)
브라우저의 접속 요청을 받을 때마다 매번 새롭게 사전 렌더링을 진행하는 방식이다.
최신 데이터를 반영하는 데 유리하지만, 데이터 페칭에서 병목이 생기면 응답 속도가 다소 늦어질 수 있다.
- getServerSideProps(): getServerSideProps 함수는 페이지를 SSR 방식으로 동작하도록 설정한다. 페이지 컴포넌트 보다 먼저 실행되어 페이지 컴포넌트에 필요한 데이터를 백엔드 서버에서 불러온다. 이 함수로 데이터를 불러와 반환하면 그 값은 페이지 컴포넌트에 Props로 전달된다.(Next.js 서버에서만 실행되므로 window 객체 사용 불가)

② 정적 사이트 생성(SSG: Static Site Generation)
프로젝트의 빌드 타임에 미리 사전 렌더링을 진행하는 방식이다.
최신 데이터 반영에는 불리하지만, 미리 생성한 페이지를 바로 반환하기 때문에 응답 속도가 매우 빠르다.
- getStaticProps()

③ 중분 정적 재생성(ISR: Incremental Static Regeneration)
SSG 방식으로 생성한 페이지를 주기적으로 재생성하는 방식이다. 빠른 페이지 응답과 동시에 최신 데이터를 반영할 수 있어 첫 번째와 두 번째 장점을 모두 취하는 방식이다.
- getStaticProps()의 revalidate 속성

### ▪︎ 페이지 라우터 최종 정리
① 장점
1) 파일 시스템 기반으로 간편하게 페이지 라우팅을 제공한다.
2) 다양한 방식의 사전 렌더링을 제공한다.

② 라우트 종류
1) 정적 라우트
2) 동적 라우트
3) 캐치올 세그먼트
4) 옵셔널 캐치올 세그먼트

③ 단점
1) 페이지마다 레이아웃 설정이 번거러움
글로벌 레이아웃이 아닌 페이지별로 레이아웃을 적용하려면 페이지 컴포넌트에서 getLayout같은 함수를 메서드로 추가하고 이를 `_app.tsx` 파일의 App 컴포넌트에서 호출해 설정해야 한다. 페이지 컴포넌트마다 getLayout 메서드를 추가하고 App 컴포넌트가 이 메서드를 호출해 적용하는 방식은 페이지 수가 많아지면 관리가 복잡하고 불편하다.
2) 데이터 페칭이 페이지 컴포넌트에 집중됨
기능이 많고 컴포넌트 트리 구조가 복잡한 페이지를 구현할 때는 컴포넌트마다 필요한 데이터를 일일이 Props로 전달해야 하는 부담이 생긴다. 이는 데이터가 필요한 중첩된 컴포넌트의 경우 Props를 전달하는 과정이 계속되면 코드의 가독성과 효율설은 급격히 떨어질 수 있다.
3) JS Bundle에 불필요한 컴포넌트들이 포함됨
페이지 라우터 버전은 페이지를 구성하는 모든 컴포넌트를 자바스크립트 번들에 포함시키니다. 그 결과 필요치 않은 컴포넌트까지 자바스크립트 번들에 포함시켜 브라우저에서 하이드레이션 한다. 하이드레이션 연산이 불필요하게 추가되면 결국 TTI 시점을 지연하기 때문에 사용자의 서비스 만족도는 떨어진다.
(앱 라우터 버전에서 서버 컴포넌트를 사용하여 자바스크립트 번들에서 제외할 수 있다.  자바스크립트 번들에는 상호작용이 필요한 컴포넌트만 포함시킨다.)
