
둘 다 같은 Playwright 엔진으로 실제 Chromium을 띄우지만, 누가 무엇을 위해 브라우저를 조작하느냐가 다릅니다.

|            | `@playwright/test` + `e2e/`  | Playwright MCP                               |
| ---------- | ---------------------------- | -------------------------------------------- |
| **조작 주체**  | 미리 작성한 테스트 코드                | AI 에이전트가 대화 중에 실시간으로                         |
| **목적**     | 회귀 방지: 정해진 동작이 계속 맞는지 자동 확인  | 탐색과 확인: 지금 화면이 어떤지 보고 판단                     |
| **결과물**    | 저장소에 남는 테스트 파일, 통과/실패 리포트    | 대화 안의 관찰 결과(스냅샷, 스크린샷, 클릭 결과). 파일로 남지 않음     |
| **반복성**    | 같은 입력이면 항상 같은 결과. CI에서 매번 실행 | 매번 에이전트가 다르게 조작할 수 있음                        |
| **판정 기준**  | `expect(...)` 단언문이 명시적으로 판정  | 에이전트가 화면을 보고 스스로 판단                          |
| **비용**     | 실행할 때 토큰이 들지 않음, 수십 초        | 단계마다 모델 호출, 느리고 토큰 소모                        |
| **잘 잡는 것** | 상태 규칙 위반, 흐름 깨짐 같은 기능 회귀     | 레이아웃 어긋남, 어색한 문구, 예상 못 한 오류처럼 단언문으로 쓰기 어려운 것 |

**이번 작업에 대입하면**
- 이번에 돌린 건 앞쪽입니다. 누군가 작성한 `pipeline.spec.ts`가 "검색 → 대본 → 장면 → 합성", "stale 표시", "취소" 같은 CLAUDE.md 규칙을 고정된 시나리오로 검증했습니다. 그래서 새 프로젝트 폼이 로딩 상태로 멈추는 버그나 `<Activity>` 문제가 재현 가능한 형태로 드러났습니다.
- 대신 화면 디자인은 확인하지 못했습니다. 버튼 배치가 어색한지, 모바일 스테퍼가 실제로 잘 접히는지, 토큰 색이 의도대로 보이는지는 단언문이 없으면 테스트가 통과해도 모릅니다. 이번 세션에는 Playwright MCP 같은 브라우저 조작 도구가 연결돼 있지 않아서, "디자인을 눈으로 검토하지 않았다"고 말씀드린 이유가 이것입니다.

**함께 쓰는 방법**
1. 새 화면을 만든 직후에는 MCP로 에이전트가 직접 둘러보며 UI 문제를 찾고 고칩니다.
2. 동작이 확정되면 그 흐름을 `e2e/` 테스트로 굳혀서 이후 변경에서 깨지지 않게 합니다.
3. 커밋이나 CI에서는 테스트만 돌립니다. 빠르고, 토큰이 들지 않고, 결과가 결정적입니다.

`e2e/`는 "앞으로도 이렇게 동작해야 한다"는 계약이고, MCP는 "지금 실제로 어떻게 보이고 동작하는가"를 확인하는 눈입니다. CLAUDE.md의 "UI 변경은 dev 서버에서 실제 화면으로 확인한다" 규칙은 MCP 쪽이 더 잘 맞습니다. Playwright MCP를 연결해 주시면 다음 작업부터는 화면도 직접 확인하겠습니다.

---
네, **MCP 없이 프로젝트에 Playwright만 설치해도 충분히 쓸 수 있습니다.** 둘은 같은 Playwright 엔진을 쓰지만 Claude가 다루는 방식이 다릅니다.

## 차이

|프로젝트 의존성 (`npm i -D @playwright/test`)|Playwright MCP|
|---|---|---|
|Claude가 쓰는 방식|테스트·스크립트 코드를 **작성해서 Bash로 실행**하고 결과를 읽음|MCP 도구(`browser_click` 등)를 **한 단계씩 직접 호출**|
|페이지 파악|코드를 실행해 봐야 알 수 있음. 셀렉터를 추측해서 쓰고 실패하면 수정|매 단계 접근성 스냅샷을 받아 **현재 화면을 보고** 다음 동작을 정함|
|결과물|저장소에 남는 테스트 코드라 CI에서 반복 실행 가능|대화 중 조작만 하고, 코드는 따로 만들어 달라고 해야 남음|
|잘 맞는 일|회귀 테스트, CI, 정해진 흐름 검증|처음 보는 화면 탐색, 즉석 디버깅, "열어서 확인해 봐"|
|토큰|실행 로그만 읽어서 적게 듦|스냅샷이 커서 많이 듦|

## 비유하면

- **의존성 설치**: Claude가 자동화 스크립트를 짜서 돌려 보는 방식. 눈을 감고 대본대로 움직이고 결과만 확인합니다.
- **MCP**: Claude가 브라우저 앞에 앉아 화면을 보며 직접 클릭하는 방식.

## 실무 권장

둘은 대체 관계라기보다 **함께 쓰는 관계**입니다.

1. 화면 탐색과 디버깅은 MCP로 하고
2. 확인된 흐름을 `@playwright/test` 코드로 만들어 프로젝트에 남긴 뒤
3. 이후에는 Claude가 `npx playwright test`를 돌려 회귀를 검증합니다.

MCP 없이 의존성만 써도 된다는 의견도 많습니다. Claude Code는 Bash로 스크립트를 짜서 스크린샷을 찍고(`page.screenshot`) 그 이미지를 읽을 수도 있어서, MCP가 하는 일 대부분을 흉내 낼 수 있습니다. 토큰을 아끼려고 일부러 이 방식을 쓰는 사람도 있습니다. 다만 단계마다 스크립트를 새로 쓰고 실행해야 하므로 처음 보는 화면을 탐색할 때는 MCP보다 느리고 시행착오가 많습니다.

정리하면, 테스트 코드를 남기고 CI에서 돌리는 게 목적이면 의존성만으로 충분하고, Claude가 대화 중에 화면을 보며 즉석으로 확인하는 경험을 원하면 MCP가 편합니다.
